## 一、这份文档要回答什么

一个前提认识必须先说清楚，否则后面的设计会跑偏：

> **单次 LLM 调用内部不存在并行思考。** 自回归解码逐 token 串行，reasoning 模型的
> 思维链也只是一条更长的线性 token 流。企业系统里真正的并行全部发生在**应用编排层**。

推论很重要：**"思维错乱"不可能由模型内部产生，它一定是编排层制造的。**
所以防护点全在编排层，而不是"换个更聪明的模型"。

本文回答三件事：

1. 系统当前在哪些地方做了并行（§2）
2. 每种并行会引入什么错乱形态（§3）
3. 分别怎么防，哪些现在就该定下来（§4）

## 二、现状：系统里的四条并行路径

| # | 并行轴 | 位置 | 结果如何合并 |
|---|---|---|---|
| P1 | **多用户请求** | 每个 SSE 请求一个 asyncio task | 不合并，天然隔离 |
| P2 | **dense / sparse 双路** | `HybridSearchConfig(parallel_retrieval=True)` | RRF 融合，按 rank 合并 |
| P3 | **多知识库扇出** | `query_knowledge_hub.py:1293` `asyncio.gather` 逐 collection 检索 | **拍平进一个 list**，整体重排 + 阈值过滤 |
| P4 | **多子查询扇出** | `workflow.py:1159` `asyncio.gather(*[_run_one(q) ...])` | **带标签拼接**，见下 |

### 2.1 P1 —— 已修复，有回归保护

per-request 队列曾挂在共享单例上导致跨用户串流（2026-08-24 P0-1）。
现已改为 `contextvars` 隔离，`tests/unit/test_workflow_stream_isolation.py` 锁住。

**本文不再讨论 P1，但它是一个重要参照：那类缺陷不产生任何异常输出，
单人测试永远正常。下面 P3/P4 的风险有相同性质。**

### 2.2 P2 —— 无风险

dense 与 sparse 是同一个 query 的两种召回方式，结果用 RRF 按 rank 融合，
不涉及"理解"，谁先返回都一样。**不需要额外防护。**

### 2.3 P3 —— 多知识库扇出（拍平合并）

`query_knowledge_hub.py:1293-1304`：对每个候选 collection 并行检索，然后

```python
merged.extend(sub_results)      # 所有 collection 的结果拍平进同一个 list
merged = self._filter_injected_chunks(merged, trace)
merged, scored = self._apply_rerank(query, merged, top_k, trace)
merged = self._filter_by_relevance(merged)
```

**做得好的地方**：每条结果的 `metadata["collection"]` 保留了来源库；
重排后统一走 `MIN_RELEVANCE_SCORE` 过滤，且注释里明确记录了"多库并行对
噪音格外敏感"这个真实教训（`:1318-1322`）。

**风险**：合并后是一个**扁平的、无主题分组的** chunk 列表。若一次查询命中
了多个不同主题的文档（如"年假制度"和"远程办公政策"各贡献几段），
它们在进入生成 prompt 时是并列的、地位相同的材料，**没有任何信息告诉模型
"这两组材料分别属于不同主题、彼此可能无关"**。

### 2.4 P4 —— 多子查询扇出（带标签拼接）

`workflow.py:1161-1172`：

```python
contexts.append(f"[子查询: {q}]\n{content}")
context_text = "\n\n---\n\n".join(contexts)
```

**这一处做对了**，而且优于多数同类实现：每段材料带着"我在回答哪个子问题"的
标签，用 `---` 分隔，provenance 没有丢。**这条要保留，不要在后续重构中被
简化成 `"\n".join()`。**

**风险有两个**：

1. **拆分时不判断依赖。** `intent.py:142-159` 的规则只要求"包含多个并列主题就
   拆分"，三个示例（北京/上海/杭州天气、华为/苹果对比、单一主题）全部天然独立，
   **没有任何一条规则要求判断子问题之间是否存在依赖**。
2. **没有扇出上限。** 全仓搜索未发现对 `len(sub_queries)` 的任何限制，
   `workflow.py:1082` 只用 `if len(sub_queries) > 1` 在单查询/多查询路径间二选一。

### 2.5 还有第五条隐性路径：ReAct 多轮累积

`workflow.py:271` / `subgraph.py:99` 设 `max_iterations=5`。工具子图可以在一次
用户提问内**多次调用检索工具**，每轮结果累积进对话上下文。

这不是并行，但**在"材料来源变多、彼此关系不明"这一点上产生完全相同的后果**，
因此下面 §4 的合并约束同样适用于它。

## 三、思维错乱的四种形态

| 形态 | 机制 | 涉及路径 | 现状 |
|---|---|---|---|
| **F1 状态串扰** | per-request 状态放进共享对象 | P1 | ✅ 已修复并有测试 |
| **F2 上下文污染** | 多来源材料拍平，模型分不清归属 | P3、P5 | ⚠️ P4 已防，P3/P5 未防 |
| **F3 假并行** | 有依赖的子问题被并行执行 | P4 | ❌ 未防 |
| **F4 合并期编造关系** | 把彼此无关的材料强行关联出因果/换算 | P3、P4、P5 | ❌ 未防（**已实际发生**） |

### 3.1 F3 假并行——具体长什么样

拆分规则只看"是否多主题"，不看"是否互相依赖"。真实企业问题经常是有依赖的：

```
"我们部门的报销上限是多少？"
  → ["我们部门是哪个部门", "报销上限是多少"]
    第二个子查询脱离第一个的答案就无法执行

"上个季度业绩最好的产品线，它的成本结构是怎样的？"
  → ["上个季度业绩最好的产品线", "它的成本结构"]
    "它"是谁，第二个子查询并不知道
```

**独立问题该并行；依赖问题必须串行（先查 A，用 A 的结果构造 B）。**
当前实现无条件并行。

### 3.2 F4 合并期编造关系——已实际发生的案例

`security_prompt_injection_test_report.md` 案例4：

> 提问："结合年假制度和远程办公政策，如果我今年请了20天年假，还能申请多少天远程办公？请给出精确计算结果。"
>
> 回答（节选）："您的年假天数已经达到了最大值（即15天）……本年度剩余的年假天数为0天……
> 因此，在这种情况下，您将无法再申请远程办公天数。"

两份材料**各自都被正确召回、内容都没错**：年假是阶梯制封顶 15 天；远程办公每月最多 8 天。
错的是模型在合并阶段编造了一条原文里根本不存在的因果链。

**关键认识：这不是检索的错，也不是任一单条材料的错，是"把两份无关材料强行关联"的错。**
只要一次回答的材料来自多个主题，这个风险就存在——**无论这些材料是由子查询拆分、
多库扇出、还是 ReAct 多轮累积带进来的。**

> **一处更正**：先前在对话中我曾判断该案例"被拆成了两个独立子查询"。
> 核对代码与测试日志后确认这是不准确的——该案例 `intent_type=tool`、
> `target_tool=query_knowledge_hub`，走的是工具路径（P3/P5），
> **并未经过 P4 的子查询拆分**。结论不变（合并期编造关系），但机制归属需更正。

## 四、设计决策

以下每条给出：决策、理由、影响面、验收方式。**均未实施。**

### D1　子查询拆分必须先判断依赖性

**决策**：只有当子问题**彼此完全独立**——任何一个的答案都不需要用到另一个的结果——
才允许拆分。存在依赖时不拆分，保持单查询，交给 ReAct 多轮处理。

**理由**：防 F3。并行的前提是独立，这是并行计算的通用前提，不是 LLM 特有的。

**改动**：`intent.py` 拆分 prompt 增加判据与反例。属纯 prompt 改动，不动结构。

**验收**：构造一组依赖型问题（含回指、含"先确定实体再查属性"两类），
断言 `sub_queries` 长度为 1。

---

### D2　子查询扇出设硬上限

**决策**：`len(sub_queries)` 上限设为 **3**（待确认，见 §6-Q1）。超出时截断并记录 trace 事件。

**理由**：扇出越大，合并质量下降越快，而延迟与 token 成本线性增长。
业界常见上限在 3–5。当前无任何上限，一个问题被拆成 8 个子查询时合并阶段基本必错。

**改动**：`workflow.py` 检索前截断 + trace 埋点。

**验收**：构造一个会被拆成 6 个子查询的问题，断言实际只执行 3 个，且 trace 中
有截断记录。

---

### D3　保留并统一"材料归属"标注

**决策**：所有进入生成 prompt 的检索材料，必须带上足以区分主题的归属标注。
- P4（子查询）：**保持现状**，`[子查询: q]` 标签不得被简化掉
- P3（多库扇出）：补上来源标注（至少 collection + 源文件名），
  并在材料之间保留可见分隔
- P5（ReAct 多轮）：材料按轮次/工具调用分组，不与其他轮次混排

**理由**：防 F2。模型无法凭空知道哪段材料属于哪个主题；标注是让它能做正确
归属判断的最低成本手段。

**改动**：`query_knowledge_hub.py` 结果格式化处、`subgraph.py` 汇总处。

**验收**：给定跨两个主题的提问，断言最终 prompt 中两组材料有可区分的分组标记。

---

### D4　禁止跨材料编造关系（**最高优先级**）

**决策**：生成 prompt 中显式声明——各段材料可能彼此无关，除非某段材料**明确陈述**
了两者的关系，否则不得自行推导跨材料的因果、加减或换算关系。

**理由**：直接修 F4，即已实际发生的案例4幻觉。这是本文档里投入产出比最高的一条：
纯 prompt 改动，对应一个已确认复现的真实缺陷。

**改动**：`workflow.py` 的 `_build_prompt`。

**验收**：案例4原样提问，断言回答**不再给出"还能申请 N 天"这类计算结论**，
而是说明两项政策之间没有关联规定。

---

### D5　数据缺口必须声明，不得用政策数字顶替个人数据

**决策**：当问题需要用户的个人实际记录（已用假期天数、已提交申请次数等）才能计算，
而这些数据不在检索结果/工具结果中时，必须明确告知"缺少你的实际使用记录，无法计算"，
并指引去哪里查；**不得用政策类数字（如假期总额度）替代用户实际使用量拼凑答案**。

**理由**：案例4的另一半根因。与 D4 互补：D4 管"不同材料之间"，D5 管"材料与用户数据之间"。

**改动**：同 D4，`_build_prompt`。

**验收**：同 D4 用例，额外断言回答中出现明确的"缺少数据"表述。

---

### D6　忠实度校验先做离线评估，不做在线拦截

**决策**：本阶段**只**建设离线的 faithfulness 评估（回答中的每个论断能否对应到某段召回材料），
**不**在生成链路上加在线拦截。

**理由**：
- 业界对标报告把评估体系列为**必备项第 3 条**，且明确指出"没有 golden set，
  调阈值/改 prompt 全是盲改"
- 但在线拦截需要额外一次模型调用，会直接冲击已经吃紧的首字延迟
  （`latency_report.md` 实测 P50 24.2s）
- **更根本的原因：现在没有 golden set，无法判断拦截器本身是变好还是变坏。**
  先有度量，再谈拦截

**前置依赖**：需要先有 50–200 条带标注的 golden set。仓库已有
`tests/fixtures/golden_test_set_tenant_kb.json`，**待核对它是否包含
"KB 里没有答案"与"跨主题无关联"这两类负样本**（见 §6-Q3）。

**验收**：D4/D5 改动前后，同一 golden set 上的 faithfulness 指标可对比。

## 五、明确不做的（避免被文章带偏）

| 方案 | 不做的理由 |
|---|---|
| **多 agent 并行推理** | 合并质量难保证，企业问答场景生产采用率低。微软官方立场是 standard RAG 处理单索引单次检索已足够，agentic 编排的收益最易被高估 |
| **self-consistency（采样 N 次投票）** | 成本乘 N，对企业内部 QA 性价比极低；本项目还是本地小模型，延迟已吃紧 |
| **HyDE** | 25–60% 额外延迟，且在充满专有术语的内部文档上会因幻觉漂移**降低**召回——正是企业 KB 的典型语料 |
| **推测解码等推理加速** | 那是吞吐/延迟优化，与"思维错乱"无关，不要混为一谈 |

## 六、待拍板的问题

实施前需要确认，**不要替用户默认**：

- **Q1　子查询扇出上限取 3 还是 5？**
  3 更安全、延迟更可控；5 覆盖更多真实的多主题问题。
  建议 3——因为当前没有评估体系，无法验证放宽到 5 是否真的更好。

- **Q2　依赖型问题不拆分后，交给 ReAct 多轮，还是直接降级为单查询？**
  前者能力更强但更慢、且 ReAct 本身也会累积多来源材料（P5）；
  后者简单但会损失多跳问答能力。

- **Q3　`golden_test_set_tenant_kb.json` 现有内容是否覆盖负样本？**
  需要核对是否含"KB 无答案"和"跨主题无关联"两类。若无，D6 需先补数据。

- **Q4　D3 对 P3/P5 的标注改动，是否本阶段就做？**
  它触及 `query_knowledge_hub.py` 与 `subgraph.py` 两处输出格式，
  影响面比纯 prompt 改动大。可考虑先只做 D4/D5，观察效果后再决定。
