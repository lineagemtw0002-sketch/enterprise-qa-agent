# 企业员工账号体系 · 设计方案

> **状态：设计草案，未实施。零代码改动。**
> **日期**：2026-08-26
> **死期**：2026-11-26。到期未实施则本文作废（`CLAUDE.md` §7.4）。
> **范围**：本文只把**阶段一（批量导入 + 管理端建号）**写到可实施的粒度。
> SSO / SCIM / 席位三档只写清楚**触发条件与影响面**，不写实施细节 ——
> 它们什么时候做取决于客户什么时候提，现在写细了大概率过期。
> **调研依据**：2026-08-26 会话内对 B2B SaaS 身份接入标准的网络调研（§8）。

---

## 1. 三行决策

```
- 决策：账号体系分四档演进。阶段一做「CSV 批量导入 + 一次性激活码 + 停用 +
        席位上限 + 管理端补全」，不做 SSO / SCIM；后三档写明触发条件，
        由客户需求驱动。（席位原本列为待定 O-4，2026-08-26 拍板并入阶段一。）
- 理由：业界标准是「IdP 是唯一事实来源，SaaS 只是同步方」，但那要 SSO+SCIM
        两套协议、约 3–4 周工程量；而目标客户只有 1–3 家、系统里 33 个用户，
        现在建的是「客户在我们系统里管账号」这一档就够用。
        真正不能等的是**批量**：万人企业不接受逐个建号，而 CSV 导入的成本
        是 SCIM 的十分之一，能把这一档撑到客户真正提出 SSO 为止。
- 作废：无（纯增量）。
  影响：user_store / app.py 管理端端点 / frontend admin 组件 /
        CLAUDE.md §3.1（仅在做到第三档 group→role 映射时才实质改动）
```

## 2. 现状（已核实，2026-08-26）

| | 现状 |
|---|---|
| 建账号 | 只有 `POST /api/v1/admin/users`，守卫 `_require_user_admin_tier` |
| 自助注册 | **无**，且不该有（企业场景不需要） |
| 批量 | **无** —— 万人企业接入的最大缺口 |
| 前端 | 已有 `UserRoleAssignment.jsx` / `RoleManagement.jsx` / `OrganizationManagement.jsx` |
| 规模 | users 33 · orgs 6 · roles 18 |
| 停用/离职 | **无停用概念**，只能删除 |
| 席位 | **无概念** |

一处**已经存在**的约束，不是本设计引入的：

> `CLAUDE.md`：token 24 小时不过期、没有登出黑名单。

意味着**任何禁用/删除操作，最多要 24 小时才对已登录用户生效**。
现在没人注意是因为账号都是手工管的；一旦接了 IdP，客户 IT 的预期会变成
"我在 AD 里禁用他，他立刻就没权限"，这条会立刻显形。**见 §6 风险 R-1。**

## 3. 四档演进

| 档 | 内容 | 触发条件 | 量级 |
|---|---|---|---|
| **一** | **CSV 批量导入 + 激活码 + 停用（非删除）+ 席位上限 + 管理端补全** | **现在就该做** | **6–8 天** |
| 二 | OIDC + JIT 自动建号 | 客户提出要用企业账号登录 | 1.5–2 周 |
| 三 | IdP group → 本地 role 映射 | **与第二档同时做，不可拆** | +2–3 天 |
| 四 | SCIM + token 吊销 | 客户问"员工离职怎么处理" | 2–3 周 |

⚠️ **第二、三档不能拆开做。** 只做 OIDC+JIT 会得到"能登录但没有任何知识库权限"
的账号 —— `users.role` 与 `allowed_collections` 都是 `NOT NULL`，
而角色直接携带知识库权限（`CLAUDE.md` §3.1）。自动建号必须同时回答
"给什么角色"，否则每个新员工登进来还是要管理员手工授权，
**SSO 省下的工作又加回来了**。

✅ **第二档的协议选型已经确定：标准 OIDC，不做国内 IM 生态适配。**
用户已确认目标客户**不使用钉钉 / 企业微信 / 飞书**（2026-08-26）。
这一条排除掉的工作量不小 —— 那三家各有自家的授权码流变体、
各自的通讯录 API、以及"用户 ID 只在本企业内唯一"这类与标准 OIDC 不同的假设，
真要接就是**三套独立适配**而不是一套 OIDC 加参数。现在可以只按
Entra ID / Okta / Keycloak 这类标准 OIDC Provider 来设计，
用一个通用的 OIDC 客户端库（如 `authlib`）覆盖全部。

⚠️ **但"标准 OIDC"不等于"不用问客户"**：`groups` 声明的字段名、
它装的是组名还是组 GUID、要不要额外调 Graph API 才拿得到，
各家都不一样，而第三档的 group→role 映射完全依赖它。
**第二档开工前要拿到两样东西**：客户 IdP 的 discovery 端点
（`/.well-known/openid-configuration`）和一个**真实的 ID token 样本**。
没有样本就设计映射规则，等于照着猜。

⚠️ **第四档的 SCIM 若不配 token 吊销，是半成品。** 业界的说法是
"SCIM 立即通知每个应用去 deprovision，不用等一次登录尝试"，
而这个系统即使收到通知，已签发的 JWT 仍然有效最多 24 小时。

## 4. 阶段一详细设计

### 4.1 CSV 批量导入

**为什么是 CSV 而不是别的**：企业 IT 从 AD 导出用户列表就是 CSV/Excel，
不需要他们学新东西；而做 SCIM 要求他们在 IdP 侧配置连接器，是另一个量级的事。

```
POST /api/v1/admin/users/bulk-import
  守卫：_require_user_admin_tier（沿用现有，不新造）
  入参：CSV 文件（username, display_name, role_name, initial_password?）
  出参：逐行结果（成功 / 失败 + 原因），不是"成功/失败"一个布尔
```

**五条必须做对的**：

1. **企业归属强制用调用者自己的** —— 沿用 `admin_create_user` 已有的做法
   （`app.py`：企业管理员不管请求体里传什么 `org_id`，一律强制用自己的）。
   批量导入是同一个越权面，**不能因为走了新端点就漏掉这层**。
2. **角色校验复用 `_validate_role_assignment`** —— 不能让 A 企业的管理员
   把用户挂到 B 企业的角色上。
3. **逐行事务，不是整体事务** —— 1000 行里第 800 行错了，前 799 行不该回滚。
   企业 IT 的预期是"告诉我哪几行有问题，我改完再传一次"。
4. **幂等**：`username` 已存在时**更新**而不是报错，这样修正后重传整份文件是安全的。
   ⚠️ 但"更新"只允许改 `display_name` 和角色，**不允许改密码**
   —— 否则一次误传会重置全公司的密码。
5. **必须先 `--dry-run`**（或 API 上的 `validate_only=true`）：
   返回"将新建 N 个、更新 M 个、失败 K 行及原因"，确认后再真跑。
   **在一个能一次影响上万账号的操作上，没有预演等于没有安全网。**

### 4.1b 初始凭证：一次性激活码，CSV 里**不出现密码**（O-1 已拍板）

**约束（用户已定，2026-08-26）**：**不做邮件、不做短信**。
所以凭证的分发必然是人工的——管理员从系统里导出，再通过他们自己的渠道发给员工。

**既然分发一定是人工的，那就让被分发的东西尽可能不值钱。**
这是这一节唯一的设计原则。三个选项：

| 方案 | 被分发的是什么 | 泄露后果 |
|---|---|---|
| CSV 带明文密码 | **长期有效的密码** | 一份文件 = 全公司账号，且**没有失效期** |
| 系统生成初始密码 + 强制首改 | 长期有效的密码 | 同上，只是员工登录后失效——**没登录的那些一直有效** |
| **一次性激活码（选它）** | **单次使用、7 天过期的短码** | 过期即废；已激活的即废 |

**选一次性激活码。** CSV 里**没有密码列**，导入完成后管理端一次性展示/导出
`username → 激活码` 清单，员工凭码自行设置密码。

```
users 新增：
  activation_code_hash  TEXT NULL      -- 只存哈希，不存明文
  activation_expires_at TIMESTAMP NULL
  activated_at          TIMESTAMP NULL
users 修改：
  password_hash 去掉 NOT NULL          -- 未激活用户还没有密码
```

⚠️ **`password_hash` 去掉 NOT NULL 这一步顺带把第二档的一个阻塞解掉了**：
`CLAUDE.md` §2 记的现状是"`password_hash` NOT NULL 挡住 SSO 用户"——
SSO 用户永远不会有本地密码。这里做的这一次 schema 变更，两档共用。
去掉 NOT NULL 对存量行是非破坏性的。

⚠️ **这引入了一个新的攻击面：一个不带鉴权的兑换端点。**
`POST /api/v1/activate`（无 Authorization 头，因为用户还没有凭证）。
四条防护必须一起上，缺一条这个端点就是弱点而不是改进：
1. **只存哈希**（与 `password_hash` 同一套），泄库拿不到可用的码；
2. **码要够长**（≥ 128 bit 熵，`secrets.token_urlsafe(16)`），
   否则可以爆破——这个端点无鉴权，爆破成本极低；
3. **按 IP 与按 username 双维度限流**；
4. **恒定时间比较**，且"码不存在"与"码已过期"返回**同一个错误**，
   不泄露 username 是否存在。

**代价要说清楚**：比"CSV 带密码"多约 1 天工作量（一张表变更 + 一个端点 +
一个前端页面 + 限流）。换到的是**分发物从"永久密码"变成"7 天一次性码"**。
在一个不能用邮件短信、必须靠人工传递凭证的场景里，这个交换是划算的。

### 4.2 停用（disabled）而不是删除

现在只能删除。删除会带走 `conversations` 的归属（`conversations.user_id`），
而审计与合规要求"离职员工做过什么"要能追溯。

```
users 新增一列：disabled_at TIMESTAMP NULL
```

**生效时机是不对称的，这一点必须写清楚（O-2 已拍板：按建议不加每请求查库）。**
核实代码后发现，原来的"全部延迟 24 小时"这个说法不准确：

| 守卫 | 端点数 | 现在查库吗 | 停用何时生效 |
|---|---|---|---|
| `require_role` / `require_platform_admin` / `_require_*_tier` | **19** | **是**（`auth.py:156` 注释明确说角色现查不读 claims） | **立刻** |
| 仅 `get_current_user` | **35** | 否（`auth.py:143-152` 纯 JWT 解码） | **最长 24 小时** |

所以正确的做法不是二选一，而是**只在已经查库的那一侧加检查**：

- `require_role` / `require_platform_admin` 里加 `disabled_at` 检查 →
  **零额外查询**，所有管理端端点立刻生效。这一条**应该做**，
  它不违背 O-2 的决定（O-2 拒绝的是"为此新增每请求查库"，这里没有新增）。
- `get_current_user` **不加**查库 → 问答、会话历史等 35 个端点最长延迟 24 小时。

**这个不对称恰好是对的风险排序**：高权限面（改角色、建账号、看审计日志）
立刻关闭，低权限面（继续提问）留一个有界的窗口。
如果反过来才是问题。彻底关闭要等第四档的 token 吊销。

**删除权限收归平台管理员（O-3 已拍板：是）**：
企业管理员**只能停用**；`DELETE` 改为 `require_platform_admin` 守卫，
仅用于真正的数据清除请求（如 GDPR 删除权）。
理由是这两件事的性质不同——停用是**人事操作**，企业自己天天要做；
删除是**不可逆的数据销毁**，且会破坏审计追溯，应该有一次跨组织的确认。

### 4.3 管理端补全

现有 `UserRoleAssignment.jsx` 已能改角色，缺的是：

- 批量导入入口（上传 + 预演结果表 + 确认）
- 用户列表的**停用/启用**开关
- **最后登录时间**列 —— 客户 IT 做 license rightsizing 时第一个要的东西
  （需要 `users` 加 `last_login_at`，在 `auth.py` 签发 token 时更新）

### 4.4 席位管理（O-4 已拍板：合并进本设计）

**为什么能合并**：席位的计量单位就是账号，而账号的创建路径在阶段一之后
只有两条（管理端建号、批量导入）。**在这两条路径之外再单独做一次席位系统，
等于把同一个计数写两遍。** 合并进来只是在这两条路径上各加一次校验。

```
organizations 新增：seat_limit INT NULL     -- NULL = 不限
```

**占用规则（这一条把 O-3 和 O-4 绑在了一起）**：

> **席位占用 = 该企业下 `disabled_at IS NULL` 的用户数。停用的人不占席位。**

这不是随手定的。如果停用**仍然**占席位，客户为了腾出名额就会去**删除**
离职员工——而 §4.2 的全部理由正是"删除会带走会话归属、破坏审计追溯"。
**收费规则会直接决定客户是停用还是删除。** 让停用免费，
客户才会选那个我们希望他选的操作。

**校验点三处，一处都不能漏**：
1. 管理端建号（`admin_create_user`）
2. 批量导入——**包括 dry-run 的预演报告**，要写明"将新增 N 人，
   当前 X / 上限 Y，超出 M 人"。让管理员在传 1000 行之前就知道会撞上限，
   而不是导入到第 800 行才失败。
3. **重新启用**一个已停用的用户——这是最容易漏的一条：
   它不创建账号，却会让占用数 +1。

`seat_limit` 只有**平台管理员可写**，企业管理员只读（它是合同条款，不是配置项）。
超限时拒绝并返回当前用量与上限，不做静默截断。

⚠️ **本设计不含计费**——只做名额上限与用量口径。
按什么周期、按峰值还是按日均计费，属商业决策，不在工程设计范围内。
但**用量口径定在这里**，计费真要做时直接用这个定义即可。

## 5. 测试设计（§7.1 要求，与设计一起交付）

| # | 用例 | 判据 | 实施前会失败吗 |
|---|---|---|---|
| **T-1** | 导入时企业归属被强制覆盖 | A 企业管理员传 `org_id=B`，结果全部落在 A | ✅ 端点不存在 |
| **T-2** | 跨企业角色被拒 | A 的管理员挂 B 的 `role_id` → 整行失败且**不建号** | ✅ |
| **T-3** | 逐行隔离 | 1000 行里第 800 行非法 → 999 行成功、1 行报错 | ✅ |
| **T-4** | 幂等 | 同一份 CSV 传两次，第二次全是"更新"，用户数不变 | ✅ |
| **T-5** | **重传不重置密码** | 已存在用户的密码哈希在第二次导入后**逐字节不变** | ✅ |
| **T-6** | 预演不落库 | `validate_only=true` 之后用户数不变 | ✅ |
| **T-7** | **停用即拒绝** | 设 `disabled_at` 后，**已持有有效 token** 的请求返回 401 | ✅ 现在无此概念 |
| **T-8** | 停用不删数据 | 停用后该用户的 `conversations` 与审计记录仍在 | ✅ |
| **T-9** | CSV 里**没有**密码列 | 含 `password` 列的 CSV 被拒绝导入并明确报错 | ✅ |
| **T-10** | **激活码只存哈希** | 建号后直接读库，`activation_code_hash` ≠ 明文码 | ✅ |
| **T-11** | 激活码单次使用 | 同一个码兑换两次，第二次失败且**不改密码** | ✅ |
| **T-12** | 激活码过期 | `activation_expires_at` 已过 → 拒绝 | ✅ |
| **T-13** | **不泄露用户是否存在** | 不存在的 username 与已过期的码，返回**同一个** status + detail | ✅ |
| **T-14** | 停用者在管理端**立刻**被拒 | 设 `disabled_at` 后，持旧 token 调 `require_role` 端点 → 401 | ✅ |
| **T-15** | 席位上限拦截建号 | `seat_limit=3` 且已有 3 个启用用户 → 第 4 个被拒 | ✅ |
| **T-16** | **停用的人不占席位** | 停用 1 人后，同样的建号请求成功 | ✅ |
| **T-17** | **重新启用也要过席位校验** | 满员时启用一个已停用用户 → 被拒 | ✅ |
| **T-18** | dry-run 报告席位影响 | `validate_only` 的返回里含"将新增 N / 当前 X / 上限 Y" | ✅ |
| **T-19** | 企业管理员不能删除用户 | 企业管理员调 `DELETE /users/{id}` → 403 | ✅ 现在能删 |
| **T-20** | 企业管理员不能改 `seat_limit` | 企业管理员改自己企业的上限 → 403 | ✅ |

**这组里最重要的五条**：

- **T-5**（重传不重置密码）——防"一次误传重置全公司密码"。
- **T-13**（不泄露用户是否存在）——`/activate` 是全系统唯一的**无鉴权**端点，
  用户名枚举在这里是真实可利用的。
- **T-14**（管理端立刻拒绝）——它钉住的是 §4.2 那张不对称表；
  哪天有人"顺手把 `disabled_at` 检查从 `require_role` 挪进 `get_current_user`"
  或反过来挪走，这条会说话。
- **T-16 + T-17**（停用不占席位 / 重新启用也要校验）——
  T-16 钉住的是"客户会选停用而不是删除"这个商业前提，
  T-17 是三个校验点里最容易漏的那个。

⚠️ **T-14 与 T-7 是一对，判据不同，不能合并。**
T-7 说的是"最终会 401"，T-14 说的是"在管理端**立刻** 401"。
只写 T-7 的话，把检查从 `require_role` 里删掉它仍然是绿的。

### 需要什么 fixture

⚠️ **现有结构测不了，这个反馈必须发生在动手之前**（§7.1）。

`grep -rln "asyncpg\|POSTGRES" tests/` **命中为零** —— 本仓库从没有测试碰过
Postgres，`conftest.py` 只有 3 个路径 fixture。而上面 8 条**全都要真实的库**。

两个选择：

- **A（推荐）**：新增一个 `postgres_conn` 集成 fixture（可复用
  `docker compose` 里已有的 postgres），测试放 `tests/integration/`。
  这个 fixture 一旦有了，后续 SSO/SCIM 的测试都要用它，**是一次性投资**。
- **B**：把校验逻辑抽成纯函数（`validate_import_row(row, actor_org, known_roles)
  -> (ok, reason)`），单测覆盖 T-1/T-2/T-3/T-4/T-6，只有 T-5/T-7 留给集成测试。
  参照 `resolve_jwt_secret` 那个已验证有效的模式（11 条单测 2 秒跑完、零 fixture）。

**建议 A + B 都做**：B 让大部分逻辑能快速回归，A 让"真的会拒绝"这件事有证据。

## 6. 风险

**R-1（已存在，非本设计引入）：停用在问答侧最多 24 小时才生效**
token 24 小时不过期且无黑名单。已按 O-2 拍板：不为此新增每请求查库，
**但管理端那 19 个端点本来就查库，所以在那一侧立刻生效**（§4.2 的表）。
残留窗口只在问答等 35 个端点上，彻底关闭要等第四档 token 吊销。
**这是有意接受的风险，不是遗漏。**

**R-4（本设计新引入）：`/api/v1/activate` 是全系统唯一的无鉴权端点**
爆破、用户名枚举、限流绕过都落在这一个端点上。§4.1b 的四条防护
（只存哈希 / ≥128 bit 熵 / 双维度限流 / 恒定时间比较且错误信息不可区分）
是**一整套**，少任何一条这个端点就从改进变成弱点。T-10～T-13 各钉一条。

**R-5：席位上限可能在错误的时刻挡住客户**
满员时新员工入职会被直接拒绝。**这是想要的行为**（合同条款应该被执行），
但要保证错误信息里带上"当前 X / 上限 Y / 请联系平台方"，
而不是一句泛泛的失败——否则企业管理员会以为是系统故障来报障。

**R-2：批量导入是一个新的越权面**
它能一次创建上万账号。所有在 `admin_create_user` 上做过的防护
（企业归属强制、角色校验）**必须逐条复制过来**，且要有测试钉住。
`CLAUDE.md` §7.2：凡涉及权限的改动必须同时提交测试。

**R-3：CSV 里的明文密码**
见 §4.1 的警告与 O-1。

## 7. 已拍板（2026-08-26，四条全部有结论）

| # | 问题 | **结论** | 落在哪一节 |
|---|---|---|---|
| **O-1** | 初始凭证怎么发？ | **不做邮件、不做短信。** 改为一次性激活码（7 天过期、单次使用、只存哈希），CSV 里**没有密码列** | §4.1b |
| **O-2** | 停用要不要立刻生效？ | **按建议：不为此新增每请求查库。** 但核实后发现管理端 19 个端点本来就查库，那一侧**免费立刻生效**；问答侧 35 个端点保留最长 24h 窗口 | §4.2 |
| **O-3** | 删除权限收归平台管理员？ | **是。** 企业管理员只能停用 | §4.2 |
| **O-4** | 席位管理现在设计吗？ | **合并进本设计。** 只做名额上限与用量口径，不做计费 | §4.4 |

**O-2 的结论比原来的建议好，值得单独说一句**：原文档写的是"全部接受 24h 延迟"，
这个说法不准确。`auth.py:143-152` 的 `get_current_user` 是纯 JWT 解码不查库，
而 `require_role`（`:156`）注释里明确写着角色现查、不读 token claims。
所以**高权限那一半本来就有查库这个动作**，加一个字段检查是零成本的。
"要不要为停用付出每请求查库的代价"这个问题，对一半的端点根本不存在。

**这四条拍板把阶段一的工作量从 3–5 天推到 6–8 天**：
激活码链路 +1 天、席位三处校验 +1 天、删除权限调整与前端 +0.5 天，
测试从 8 条涨到 20 条。

## 8. 参考（2026-08-26 网络调研）

- SCIM vs JIT：JIT 是"便宜好用的生命周期"，**只能创建不能注销**；
  SCIM 才是规模化 offboarding 的唯一机制
- 业界普遍**两个都上**：JIT 管首次登录便利，SCIM 管持续生命周期尤其注销
- **IdP 是 SCIM 客户端与唯一事实来源**，企业 IT 在自己的目录里管人
- 企业客户期望**完全自助的应用内管理**：自己配身份、管用户、划权限边界
