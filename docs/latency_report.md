# 系统问答耗时分析报告

数据来源：(1) 本次会话及此前多轮测试真实产生的 `conversation_archive` 表数据（303条assistant真实回复，含真实 latency_ms/token 统计）；(2) 针对不同问题类型做的受控探测（`latency_probe.py`，读取聊天接口 SSE 流里 trace 各节点时间戳）。**本文档只做现状分析和方案建议，不修改代码。**

---

## 一、真实历史数据总览（303条assistant消息）

| 指标 | 数值 |
|---|---|
| 平均耗时 | **26.4 秒** |
| 最快 | 8.4 秒 |
| 最慢 | 67.4 秒 |
| P50（中位数） | 24.2 秒 |
| P90 | 41.1 秒 |
| P95 | 46.8 秒 |
| 平均 prompt tokens | 551 |
| 平均 completion tokens | 145 |
| 平均每个输出token耗时 | **182 毫秒/token** |

按耗时分桶后，输出 token 数和耗时明显正相关：

| 耗时区间 | 消息数 | 平均输出token | 平均输入token |
|---|---|---|---|
| 快（<15秒） | 52 | 100 | 427 |
| 中（15-35秒） | 186 | 153 | 580 |
| 慢（>35秒） | 65 | 215 | 584 |

**结论**：不管落在哪个区间，最快的一档也要 8.4 秒起步，说明存在一个跟输出长度无关的**固定开销**（意图分类+检索这部分），输出越长则额外叠加"生成阶段"的耗时——这是两段可以分开看待、分开优化的问题。

---

## 二、受控探测：分阶段耗时拆解

用聊天接口自带的 trace 时间戳（`session`→`intent`→`generate`/`workflow`→`archive` 几个节点），针对不同类型的问题各测一次：

| 场景 | 总耗时 | 首字耗时(TTFT) | 意图分类阶段 (session→intent) | 检索+生成阶段 (intent→generate) | 输出内容长度 |
|---|---|---|---|---|---|
| 闲聊（"你好，你是谁"） | 22.1s | 20.1s | **13.8s** | 8.3s | 73字 |
| 检索命中（"远程办公几天"） | 20.4s | 16.0s | 6.6s | 13.7s | 158字 |
| 检索未命中（"股票期权比例"） | 12.9s | 12.9s | 6.4s | 6.6s | 56字 |
| 发起工作流（"我要申请年假"） | 5.1s | 5.1s | 1.7s | 3.4s（走workflow节点，非generate） | 10字 |
| 长回答（"详细介绍年假+远程办公政策"） | 39.0s | 17.8s | 6.1s | **32.9s** | 682字 |
| 多知识库并行检索（6个企业KB，org_admin账号） | 17.9s | 13.5s | 5.7s | 12.2s | 183字 |

**几个明显信号**：

1. **意图分类阶段本身就要 1.7～13.8 秒**，且和问题内容/是否命中知识库无关——这一步在代码里是"结构化 LLM 一次完成指代消解 + 子查询拆分 + 四分类"（`workflow.py::_intent_node`），也就是说哪怕只是判断"这是闲聊还是要查资料"，也要跑一次完整的 LLM 生成调用，而不是一个轻量分类器。
2. **"检索+生成"阶段的耗时几乎完全由输出内容长度决定**：56字→6.6s，158字→13.7s，682字→32.9s，跟"检索到几个知识库、要不要做混合检索/重排"关系不大（6个知识库并行检索 vs 1个知识库，耗时基本持平，说明检索本身不是大头，生成阶段的 LLM 推理才是）。
3. **工作流路径明显更快**（5.1秒）——因为这条路径不需要走生成式回答，直接返回结构化的表单收集提示，验证了"LLM生成"确实是耗时主因。
4. **首字耗时（TTFT）经常等于甚至接近总耗时的大头**（比如闲聊场景 20.1s / 22.1s），意味着用户在看到任何文字反馈之前，通常要等 12～20 秒——这段时间前端目前只有一个笼统的"思考中"状态，没有分阶段的进度提示。

## 三、根因

**全栈跑在本地 Ollama 上，用同一个 7B 模型做所有 LLM 调用**（`config/settings.yaml`）：

```
llm.provider: ollama
llm.model: qwen2.5:7b          # 意图分类 + 最终生成，都用它
embedding.provider: ollama
embedding.model: nomic-embed-text
rerank.model: BAAI/bge-reranker-base   # 本地 cross-encoder
```

运行环境：本机 Apple M4（16GB 内存），`ollama ps` 确认模型是 100% GPU（Metal）加载，不是纯 CPU 推理，但终归是消费级笔记本的算力，跟生产级 GPU 服务器/云端 API 推理速度不是一个量级。

具体拆解到两笔主要开销：

1. **意图分类是一次完整的 LLM 生成调用**（不是关键词匹配或轻量分类器），每轮对话固定要付出这笔成本（约2-14秒，视 prompt 长度和模型状态而定），即使问题本身很简单（比如打招呼）也不例外。代码里已经有一部分"规则短路"优化（比如识别到"报销"这类动作词+流程关键词时跳过 LLM 分类，直接判定是 workflow 意图），但覆盖面有限，多数问题仍然要完整跑一次分类。
2. **最终生成阶段的耗时跟输出 token 数成正比**（约182ms/token），本身是模型推理速度决定的物理上限，不是代码逻辑问题——但当前 Prompt 里明确鼓励"结构化多条记录用表格呈现"，表格格式本身会显著拉长输出 token 数（同样的信息量，表格比自然语言句子要多输出很多格式符号），间接推高了生成耗时。

检索环节（embedding查询、多collection并行混合检索、文档摘要粗筛、cross-encoder重排）虽然理论上有多个步骤，但从"6个知识库并行检索"和"1个知识库检索"耗时基本持平这一点看，目前不是主要瓶颈，生成阶段的模型推理时间才是。

## 四、优化方案建议（不涉及代码修改，供评审排期）

### P0：意图分类换成更轻量的方案

- 优先扩大现有"规则短路"的覆盖面（`cross_org_direct_ask` 测试里能看到已经有"动作型前缀+流程关键词"的短路逻辑），把闲聊问候、简单是非题这类模式也纳入规则判断，不是所有问题都要经过完整的 LLM 结构化分类。
- 对确实需要模型判断的场景，评估换一个更小的模型专门做意图分类（Ollama 本机已经装了 `qwen2.5:14b`，但目前反而是用 `7b`，说明可能没有专门为"分类"这种轻任务配一个更小/更快的模型，比如 `qwen2.5:1.5b` 或更小的模型，理论上分类这种任务用小模型精度损失有限、但速度可以提升数倍）。
- 或者把"指代消解+子查询拆分+四分类"这个合并在一起的复杂结构化调用拆开：简单问题走一个轻量快速路径（比如只做分类，不做指代消解/子查询拆分），只有检测到问题里有代词/并列结构等复杂特征时，才触发完整的重量级处理。

### P0：生成阶段的输出长度控制

- 复核 Prompt 模板里"结构化数据用表格呈现"这条指引的触发范围，避免简单问题也被格式化成表格从而拉长输出——测试里能看到不少几句话就能说清楚的答案被套上了 Markdown 表格。
- 评估给 Ollama 调用设置合理的 `num_predict`（最大生成token数）上限，防止个别回答无节制地啰嗦下去（历史数据里最慢的一档平均215个completion token，仍有进一步收紧的空间）。

### P1：前端体验优化（不影响真实耗时，但改善"卡住了"的感知）

- 当前首字耗时经常达到12-20秒，这段时间用户只看到一个笼统的等待状态。可以把 trace 事件（session/intent/tool调用/generate 几个阶段）实时推给前端，展示"正在理解问题…／正在检索知识库…／正在生成回答…"这类分阶段提示，不改变真实响应时间，但能显著降低用户对"系统没反应"的焦虑感。

### P1：模型保活（keep_alive）

- 代码里已经有 `cold_start` 检测逻辑（`query_knowledge_hub.py`，初始化耗时超过500ms视为"冷启动"），说明系统本身已经意识到 Ollama 模型可能被换出显存、下次调用要重新加载的问题。建议确认当前 Ollama 的 `keep_alive` 配置是否设置了足够长的保活时间（默认5分钟，空闲后会被卸载），并考虑加一个轻量的后台保活探测（定时发一个极短的推理请求），避免真实用户请求撞上"冷启动"这种额外的几秒到十几秒延迟。

### P2：检索链路的小幅优化（非当前主要瓶颈，优先级较低）

- 文档摘要粗筛（`_narrow_by_document_summary`）是为大规模、多文档的知识库设计的粗筛机制；当前多数企业知识库单个collection只有20来篇短文档，粗筛本身的"额外一轮embedding查询"开销，相对它能省下的精排候选池收益可能得不偿失。可以考虑加一个"文档数低于阈值时跳过粗筛，直接对全量文档做精排"的判断，省掉一轮不必要的向量查询往返。

### P3：生产化部署（架构层面，成本最高，需要业务侧决策）

- 当前是本地 Mac 开发机跑 Ollama 的配置，速度上限本身就受限于消费级硬件。如果这套系统未来要支撑真实并发用户、且对响应时间有明确 SLA 要求，现有本地免费栈（Ollama + 本地 embedding/rerank）大概率撑不住——需要评估换成更强算力的自建 GPU 服务器，或接入云端托管的 LLM API（更快、但有调用成本），这是一个业务侧要不要投入预算的决策，不是代码能单方面解决的问题，本文档只做提示，不展开具体选型。

## 五、优先级排序

| 优先级 | 方向 | 预期收益 | 改动范围 |
|---|---|---|---|
| P0 | 意图分类规则短路扩面 / 换小模型 | 每轮省下数秒的固定开销，覆盖所有问题类型 | 中（workflow.py 意图节点） |
| P0 | 限制生成输出长度/收紧表格化触发条件 | 慢查询（>35s那档）平均能省下不少输出token对应的耗时 | 低（Prompt模板+推理参数） |
| P1 | 前端分阶段等待提示 | 不省真实耗时，但显著改善体验 | 中（前端+SSE事件扩展） |
| P1 | Ollama keep_alive 保活确认 | 消除偶发的冷启动延迟尖刺 | 低（配置项） |
| P2 | 小知识库跳过摘要粗筛 | 检索环节的小幅优化，非当前主要瓶颈 | 低 |
| P3 | 生产级推理算力/云端API | 从根本上解决延迟问题，但需要预算决策 | 高，架构级 |
