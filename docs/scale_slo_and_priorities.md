## 零、为什么需要这次重估

代码审计给出的 P0/P1/P2 分级，判定前提是：

> "严重程度判断要基于这个项目的实际场景：**企业内部 QA agent，小团队，
> 不是面向公众的高并发服务**"

2026-08-25 明确交付目标为 **10000+ 员工的大企业**后，这个前提失效。
一批被判为"内部工具用户数不大，不会立刻痛"的问题，在目标规模下会直接变成阻塞项。

**本文不修改原报告**（它在自己的前提下是自洽的），而是给出新场景下的重新排序。

## 一、容量测算

### 1.1 假设（可逐条推翻）

| 参数 | 取值 | 依据 |
|---|---|---|
| 员工总数 | 10,000 | 已确定 |
| 日活占比 | 30% | 内部知识工具成熟期的常见区间，**待验证** |
| 每活跃用户日提问 | 4 次 | "查资料"场景估计，**待验证** |
| 峰值小时占比 | 20% | 上班后/午后两个高峰，**待验证** |
| 小时内突发系数 | 2.0 | **待验证** |
| 单请求模型调用数 | 约 5 次 | 意图路由 → query改写 → 工具决策 → 生成 → 记忆摘要 |
| 单请求占用模型总计算 | 约 15s | 由 `latency_report.md` P50 24.2s 反推，**粗估** |

### 1.2 推算结果

```
日活用户            3,000
日提问量            12,000
峰值小时提问量      2,400
峰值 QPS(含突发)    1.33
```

**并发在飞请求数**（Little's Law：L = λ × W）：

| 场景 | 停留时间 W | 并发在飞 L |
|---|---|---|
| 当前实测 P50 | 24.2s | **32.3** |
| 若达成 10s | 10.0s | 13.3 |
| 若达成 5s | 5.0s | 6.7 |

> **一个重要推论：并发压力是延迟的函数。** 把 P50 从 24.2s 压到 5s，
> 并发在飞请求数同比例从 32 降到 7。**优化延迟本身就是在降容量需求**，
> 两件事不是并列的，是一件事。

### 1.3 模型服务吞吐——**当前部署根本跑不动目标规模**

`OLLAMA_NUM_PARALLEL` 默认值为 **1**（Ollama 官方 FAQ），即模型服务一次只处理一个请求：

| 并发度 | 吞吐上限 | 峰值需求 | 缺口 |
|---|---|---|---|
| **1（当前默认）** | 240 次/小时 | 2,400 次/小时 | **❌ 10x** |
| 4 | 960 次/小时 | 2,400 次/小时 | ❌ 2.5x |
| 8 | 1,920 次/小时 | 2,400 次/小时 | ❌ 1.25x |

而且 **16GB Mac 上跑 7B 模型根本无法支撑 `NUM_PARALLEL=8`**——显存不够，
会触发反复换入换出，实际吞吐还会更差。

**结论：这不是"调个参数"能解决的，是部署形态问题。**
业界基准线明确指出 Ollama 适用于"开发与低并发内网场景"，
**并发用户数超过个位数就该换 vLLM/SGLang**。目标规模远超这条线。

## 二、最小 SLO 提案

对应"满足**基本的、普适的**功能需求和性能需求"这个完成定义。
原则：**基本 = 核心路径可靠；普适 = 不为个别场景做特化。不追求大厂级指标。**

### 2.1 正确性（无错误预算，必须 100%）

| 指标 | 目标 | 为什么是硬性的 |
|---|---|---|
| **跨组织/越权数据泄露** | **0** | 业界基准线里唯一"不能因团队小而降标准"的一项，失效模式是数据泄露不是性能下降 |
| 身份不可伪造 | 0 已知路径 | 已修（JWT fail-fast） |
| 并发请求内容不串 | 0 | 已修（contextvars）+ 有真并发测试 |

### 2.2 回答质量

| 指标 | 目标 | 现状 |
|---|---|---|
| 有答案问题的正确率 | ≥ 90% | **无法度量**（golden set 仅 12 条） |
| 无答案时正确拒答率 | ≥ 95% | 仅 1 条用例 |
| 忠实度（论断有材料支撑） | ≥ 95% | **无度量手段**（关键词断言抓不到编造） |
| 跨主题不编造关联 | 100% | **零覆盖**，且已知有复现案例 |

> 这一节全部"无法度量"，正是业界基准线把评估体系列为**必备项第 3 条**的原因：
> **没有度量，后面所有优化都是盲改。**

### 2.3 性能

| 指标 | 目标 | 当前实测 | 差距 |
|---|---|---|---|
| **首字延迟 TTFT P95** | ≤ 3s | 未单独测量 | 未知 |
| 完整回答 P95 | ≤ 15s | 46.8s | **3.1x** |
| 完整回答 P50 | ≤ 8s | 24.2s | **3.0x** |
| 峰值承载 | ≥ 1.5 QPS | 约 0.067 QPS | **22x** |
| 可用性 | 99.5%（内部工具） | 无监控 | 未知 |

> **为什么把 TTFT 单列为最重要的一条**：流式场景下用户感知的是"多久开始出字"，
> 不是"多久全部出完"。用户此前提的"业界一般不超过5秒"更接近 TTFT 的诉求。
> 当前 `latency_report.md` 只有端到端数字，**建议补 TTFT 单独测量**。

### 2.4 容量

| 指标 | 目标 |
|---|---|
| 知识库文档规模 | 待定——需要知道企业现有 KB 有多大（见 §5-Q3） |
| 单次检索候选库数 | 当前 6 库全扇出，建议设上限 |
| 会话历史保留 | 待定 |

## 三、27+1 条发现的重新分级

**+1** = 审计未覆盖的一条新增发现（审计范围是代码，未包含部署/运行时配置）。

### 3.1 新 P0 —— 阻塞交付

#### A 类：安全（上线前必须清零，无商量余地）

| 原编号 | 问题 | 原级别 | 为什么在万人场景升级 |
|---|---|---|---|
| P1-15 | 绕过 ACL 的测试端点横跨 8+ 文件 | P1 | 万人企业里一个绕过 ACL 的端点 = 全员数据可达。靠 `RAGENT_DEBUG` 一个开关兜底不足以上线 |
| P1-10 | CORS `allow_origins=["*"]` + `allow_credentials=True` | P1 | 这个组合本身就是错的，且携带凭证 |
| P1-9 | 租户连接器凭证明文存 Postgres | P1 | 一次库泄露 = 所有企业侧凭证泄露 |
| P1-6 | trace WebSocket 无鉴权 | P1 | trace 里含检索内容与 prompt，等于旁路读取他人会话 |

#### B 类：承载（不改跑不起来）

| 编号 | 问题 | 原级别 | 依据 |
|---|---|---|---|
| **新增** | **模型服务并发形态**：`OLLAMA_NUM_PARALLEL=1`，16G Mac 单机 | 未覆盖 | §1.3，缺口约 10x。**这是最硬的一条** |
| P1-8 | 检索链路每查询重建全套组件，全链路无缓存 | P1 | 6 库企业每次提问 = 6 次 Chroma bootstrap + 6 次 BM25 磁盘反序列化，且 bootstrap 因并发崩溃被迫串行化，直接计入首字延迟 |
| P1-2 | 14 个 Store 各建连接池，上限累计约 68 | P1 | 峰值 32 并发在飞时连接争用 |
| P1-14 | 管理端 N+1（50 用户约 300 次串行查询） | P1 | 按 10000 员工线性推算 = 上万次往返，管理页直接不可用 |

#### C 类：可运维性（"提高运维水平"是明确的使用场景）

| 编号 | 问题 | 原级别 | 依据 |
|---|---|---|---|
| P1-5 | 48 处 `print()`、0 处 logger、无 request id | P1 | 万人规模下无结构化日志 = 不可调试。**一个以"提高运维水平"为卖点的系统自身不可运维，是硬伤** |
| P1-4 | `ragent_backend` + `tool_agent` 共 12,200 行零测试 | P1 | 该规模下无回归网不可接受；且 `conftest.py` 无 DB fixture 导致"写不出测试" |

**小计：10 条 P0**（含 1 条新增）。数量多是因为项目本来就是按另一个规模建的，不是因为做得差。

### 3.2 新 P1 —— 上线后很快会痛

| 编号 | 问题 | 变化 |
|---|---|---|
| P1-11 | 无 Dockerfile / CI / 依赖锁定 | 持平——但换 vLLM 后部署复杂度上升，会更痛 |
| P1-1 | `create_app()` 2976 行 / 71 端点无分层 | 持平——是"零测试"和"权限守卫难审计"的共同结构原因 |
| P1-3 | DDL 内嵌无迁移体系 | **升**：万人生产环境改表不能靠 `IF NOT EXISTS` |
| P1-12 | 配置双轨，含静默失效的死配置 | **升**：生产环境"配了没生效且无警告"是事故源 |
| P1-13 | Prompt 硬编码 | 持平——但改一句 prompt 要发版，在生产节奏下痛 |
| P1-16 | 文档与代码脱节 | 持平 |
| P1-7 | 分层倒置 + 循环依赖 | 持平 |
| P2-8 | 后台任务无优雅关闭 | **升**：生产滚动重启会丢正在跑的归档/摄入 |
| P2-7 | 四套存储手工同步，无对账 | **升**：数据量大后孤儿数据无法人工发现 |

### 3.3 维持 P2 —— 可延后

P2-1（上帝类）、P2-2（trace task 弱引用）、P2-3（扁平 State）、P2-4（scripts 混杂）、
P2-5（前端上帝组件）、P2-6（策略硬编码）、P2-9（零散问题）。

这些是**代码整洁度**问题，不直接影响交付。在"基本、普适"的完成定义下不应优先。

### 3.4 已修复

P0-1 并发串流、P0-2 JWT 密钥（均有回归测试）。

## 五、单租户 / 多租户歧义对本文结论的影响

该歧义尚未澄清（`CLAUDE.md` 已登记）。影响范围：

| 结论 | 单租户（一家万人企业内部署） | 多租户 SaaS（客户是多家万人企业） |
|---|---|---|
| §3.1-A 安全四条 | **仍全部是 P0**（部门边界同样要守） | **P0，且更严重**（跨企业泄露） |
| §1 容量测算 | 按 10,000 员工算，本文数字直接适用 | **需乘以客户数**，本文数字是"每客户" |
| P1-9 租户凭证明文 | 影响面小（自己的凭证） | **严重**（所有客户的凭证） |
| 多租户机制本身 | 可能是过度设计，可简化 | 核心资产，一分不能减 |

**本文其余结论不受该歧义影响。** 但容量部分若是多租户，所有数字要重算。

## 七、待确认

- **Q1　单租户还是多租户 SaaS？**（阻塞 §1 容量与 §5 全部结论）
- **Q2　§1.1 的容量假设是否合理？** 尤其日活占比 30%、每人每日 4 次——
  你对这家企业的实际情况了解，我只能给区间。
- **Q3　企业现有知识库有多大？** 文档数/总体积/更新频率。这决定 Chroma 是否够用，
  以及是否需要迁到 Qdrant/pgvector。
- **Q4　部署环境是什么？** 现在是 16G Mac 本地起 4 个进程 + 本地 Ollama。
  真实交付环境有没有 GPU？能不能上多机？——**这条直接决定 §1.3 那个 10x 缺口怎么解。**
- **Q5　§2 的 SLO 数字是否接受？** 特别是 TTFT ≤ 3s、完整回答 P95 ≤ 15s、
  峰值 ≥ 1.5 QPS 这三条。
- **Q6　"基本、普适"是否意味着可以明确放弃某些能力？**
  例如：不做多模态、不做实时协同、不做移动端。明确放弃能大幅缩小范围。
