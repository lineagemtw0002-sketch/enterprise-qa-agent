# 连接器主动推送告警 —— 补上"平台怎么知道出事了"这一环

> **状态：设计待确认，未实施** · 2026-08-27 · 死期 2026-11-27
> 超期未实施则删除本文，不要让一份没人执行的设计留在仓库里冒充计划。

---

## 1. 现状：链路在最前面就断了

2026-08-27 实测的完整时序：

| # | 环节 | 谁触发 | 耗时/时限 |
|---|---|---|---|
| 1 | 进程异常发生 | — | — |
| 2 | 客户监控系统采集到 | 客户侧 | 取决于客户 scrape 周期 |
| **3** | **平台知道出事了** | — | 🔴 **不存在这个环节** |
| 4 | 发起分析 | **人点按钮 / 人跟 AI 对话** | — |
| 5 | 联邦查询 | 平台 | 超时 8s/连接器，缓存 TTL 45s |
| 6 | 异常检测 + 告警关联 | 平台 | 毫秒级（纯统计） |
| 7 | RCA 根因辅助 | 7B LLM | **实测 7–10s** |
| 8–10 | 提议 → 审批 → 执行 | 人为主 | 审批超时默认 30 分钟 |

**平台只在有人问的时候才去查。** 没人问，异常可以在客户环境里躺一整天，
大屏一片绿。连接器也不会主动说话——协议里只有"平台问、连接器答"。

两个连带后果：

- **MTTR 测不到真实的"发现耗时"**。它的起点是最早那条关联告警的时间，
  而那条告警是**分析时才被查回来的**；没人点分析，这段时间根本不进统计。
- 前面所有关于耗时的讨论都失去意义——**"人什么时候想起来点一下"才是主导项**，
  可能是几小时。

## 2. 三行决策

- **决策**：连接器新增一个**主动推送**方向：客户的告警系统触发时，连接器把告警
  推给平台（新增 `alert_push` 帧），平台据此决定要不要发起分析。
- **理由**：另一条路是"平台定时扫描各连接器的告警"，但它违背 §3.1 的 BYOC 原则
  （平台不常驻拉取客户运维数据），而且 N 个连接器 × M 分钟的轮询在客户看来
  就是持续的外部探测。**推送把"何时值得关注"的判断留在客户那边**——他们的
  告警规则本来就是干这个的，平台不必重新发明一遍。
- **作废**：无（纯新增）；影响面：连接器协议（新增一个帧型和一个方向）、
  `app.py` 的 WS 接收循环、新增一张告警表或复用现有分析摘要、
  §3.1 需要补一句"告警是推送进来的，仍然不落原始指标数据"。

## 3. 协议变更（最小）

沿用现有信封，新增一个帧型，**方向是连接器 → 平台**（现有帧型除
`query_result`/`exec_result` 外都是平台 → 连接器）：

```json
{"type": "alert_push", "id": "...", "connector_id": "opsconn_xxx", "ts": ...,
 "payload": {"alerts": [
   {"ts": ..., "text": "order-service 5xx 比例超过阈值",
    "labels": {"target": "order-service", "severity": "error",
               "env": "prod", "cluster": "prod-cluster-1", "rule": "http_5xx_ratio"}}
 ]}}
```

字段跟现有 `kind=alert` 的查询结果**完全一致**——这是刻意的：告警关联那套代码
（`correlate_alerts`）不需要为推送另写一份解析。

平台回一帧 `ack`（或复用 `heartbeat` 的确认形态），**连接器收不到 ack 应当重试**
——推送丢了就等于没发生，而查询丢了顶多是这次没数据。

⚠️ **推送要限流。** 一次大面积故障可能瞬间产生几千条告警。建议连接器侧按
`rule + target` 聚合后再推，平台侧也要有上限（超过就丢弃并记一条"告警风暴，
已截断"，**不能因为告警太多把平台自己打挂**）。

## 4. 收到告警之后做什么（2026-08-27 拍板）

**事件首次打开 → 立刻自动分析一次（含 RCA）；同指纹的重复告警只更新计数，
不重新分析；界面按钮保留为"按需重新分析"。**

### 4.1 为什么需要"事件"这个概念

一个进程一直坏着，客户的告警系统会不会一直推？**业界的答案是不会**——
告警是**状态转换**的信号，不是当前状态的心跳：

| 产品 | 机制 |
|---|---|
| Prometheus Alertmanager | `group_by` 分组 + `repeat_interval`（默认 **4 小时**才重发一次） |
| PagerDuty | `dedup_key`：同 key 更新已有 incident，不新建 |
| Datadog | 按状态转换触发（OK→ALERT），renotify 有间隔 |
| Opsgenie | alias 去重 |

**共同点**：告警自带指纹，平台按指纹找**已打开的事件**，找到就更新，找不到才新建。
"判断重复"不是平台去猜，是靠指纹。

### 4.2 现在缺的正是"持续存在的事件"

`correlate_alerts` 只做**一次性分组**（19 条合成 1 个事件），事件**不落库、
没有生命周期**——每次分析都重新算一遍。所以同一次故障被分析两次，会产生两条
互不相干的摘要，而不是一条事件的两次更新。

| 概念 | 现在 | 要变成 |
|---|---|---|
| 事件 | 每次分析临时算出 | **落库，有 open / resolved 状态** |
| 指纹 | 无 | `shared_labels` + `targets` 的稳定哈希 |
| 重复告警 | 当成新数据重新分析 | 更新 `last_seen` / `alert_count`，**不触发分析** |
| 何时分析 | 每次有人点 | **事件首次打开时自动分析一次** |
| 重新分析 | — | 事件性质变了（波及新服务）或人主动要求 |

### 4.3 两层防浪费，各管各的

- **指纹去重**决定"这是不是一件新事"（业界标准，必须有）
- **统计层先筛**决定"这件新事值不值得写作文"——实测 RCA 一次 **7–10 秒**，
  而且**健康服务也要 7.24 秒**（`hr-portal` 完全正常仍跑满一次 LLM）。
  指纹是新的但检测下来其实没事（瞬时抖动）时，不该白花这 7 秒。

有了指纹之后第二层的必要性下降很多，但**两层都要**——它们挡的是不同的东西。

### 4.4 界面上的「分析」按钮保留，角色变了

从"唯一的分析入口"变成"按需重新分析"。它仍然不可替代的场景：

1. **指标劣化但没触发告警** —— 客户告警阈值和平台健康阈值是两套；
   `traffic_surge` 在平台这里是"观察中"，客户规则很可能根本不报
2. **看没告警的服务是否被波及** —— A 挂了想确认 B 有没有事，B 没告警，
   自动分析永远不会碰它
3. **要一份"现在"的结论** —— 事件打开时的分析基于当时数据
4. **客户还没接推送** —— 过渡期里按钮是唯一的路
5. **对结论不满意想重跑**

⚠️ **因此分析摘要必须记录触发来源**（`trigger_source`：`auto` / `manual` + 谁点的），
时间线上区分显示。不加的话，"这条是系统主动发现的还是有人手动查的"分不出来，
而这两件事在复盘时意义完全不同。

⚠️ 按钮要显示"上次分析于 X 前"，且刚分析过（60 秒内）再点时给确认而不是静默
重跑——白花 7–10 秒 LLM。**不禁用**：人可能确实想重跑。

### 4.5 反复重启（flapping）——指纹去重挡不住的那个洞

**场景**：进程反复重启，好→坏→好→坏。

指纹去重在这里**失效**：每次"变坏"都是一次真实的状态转换，告警系统会如实发
firing，指纹还完全相同。而按 §4.2 的规则，上一个事件已经 resolved 了，
所以同指纹的新告警会**新建事件 → 又分析一次**。一分钟抖 5 次 = 5 次 LLM 调用、
5 条时间线记录，**而且这 5 条结论几乎一模一样**（根因本来就是同一个）。

业界把这当成一类**独立的故障状态**来处理，不是当成 N 次独立故障：

| 机制 | 谁在用 | 做法 |
|---|---|---|
| `for` 持续时长 | Prometheus | 条件必须**持续满足 N 分钟**才 firing，抖一下不报 |
| `resolve_timeout` | Alertmanager | 恢复后等一段时间再判 resolved，防止立刻又坏 |
| Flapping 检测 | Nagios / Icinga | 统计最近 N 次状态变化，**超阈值就进入 flapping 状态并抑制通知** |
| 抑制窗口 | PagerDuty / Opsgenie | 同一 key 在冷却期内不新建 |

**本设计采用两条**：

1. **事件 resolved 后有冷却期**（默认 5 分钟）。冷却期内同指纹再打开 →
   **复用同一个事件**（从 resolved 拉回 open，`flap_count += 1`），**不重新分析**。
2. **`flap_count` 越过阈值时改变结论，而不是重复结论。** 反复横跳的根因跟
   "挂了一次"根本不同（多半是 OOM 反复重启、健康检查配置不当、依赖不稳定），
   值得**单独分析一次**并在时间线上标成「反复重启」——**但只分析一次**，
   之后只累加计数。

效果：一分钟抖 5 次 = **1 个事件、1~2 次 LLM 调用**，时间线上是一条
「X 在 5 分钟内反复重启 7 次」，而不是 5 条一样的记录。

⚠️ **这层抑制主要该发生在客户侧。** Prometheus 一条 `for: 5m` 就能让抖动根本
不产生告警；平台侧这层是**兜底不是主力**。§3 的协议规范里要写明这个期望：
**推送前请先按你们告警系统的规则去抖**，否则平台只能被动挨打。

## 5. 顺带要解决的两个已知问题

1. **缓存 TTL 45 秒 vs 大屏 15 秒轮询**：大屏上的服务健康最旧可能是 45 秒前的，
   而连接器状态是实时的。故障刚发生的头一分钟会出现"连接器在线、指标却是旧的"。
   告警推送进来时应当**主动失效该连接器的缓存**，否则推送来了、大屏还是旧数据。
2. **MTTR 的起点**：有了推送之后，起点应当改成**告警被推送到平台的时间**
   （而不是"分析时查回来的最早告警时间"）——那才是"平台知道出事"的真实时刻。

## 6. 不做的

- 不做告警规则配置（那是客户监控系统的职责，平台重新发明一遍必然更差）
- 不做告警去重/抑制（连接器侧或客户的 Alertmanager 更适合做）
- **不做自动执行**（无论告警多严重，动手仍然要人批准）
