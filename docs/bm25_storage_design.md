## 1. 问题（已实测，不再是推算）

`CLAUDE.md` §4 那条 P0 此前是从 20 块样本单点线性外推的。现已用四个规模点实测：

| 块数 | 索引体积 | 词表 | 字节/块 | `json.load` |
|---|---|---|---|---|
| 1,000 | 5.13 MB | 6,123 | 5,377 | 0.029s |
| 4,000 | 19.34 MB | 10,089 | 5,069 | 0.103s |
| 16,000 | 75.79 MB | 26,015 | 4,967 | 0.430s |
| 50,000 | 235.94 MB | 70,830 | 4,948 | 1.768s |

**增长指数 α = 0.997 —— 几乎完全线性。** 加载速率实测 **133 MB/s**。

> 原本指望 Heaps 定律（词表次线性）拉低总量，**这个指望被推翻了**：
> 词表确实次线性，但 postings 随文档数线性增长且完全占主导，16 倍规模下
> 单块开销只降 8%。

外推到目标数据量（单客户几个 G 文档）：

| 块数 | 索引 | 单次加载 |
|---|---|---|
| 143K（≈2GB 文档） | **672 MB** | **5.0s** |
| 358K（≈5GB） | **1.68 GB** | **12.6s** |
| 716K（≈10GB） | **3.35 GB** | **25.1s** |

**结论方向不变，量级比原推算低 3–8 倍。** 但仍然致命：
`query_knowledge_hub.py` 每次查询、每个候选库各做一次全量 `json.load`
（`_build_hybrid_search_for`，且 `_execute_local_multi` 不走带缓存包装的
`_ensure_initialized`）。一个 6 库企业每次提问 = 6 × 5s 加载、内存峰值约 4 GB，
而 SLO 是 **TTFT ≤ 3s**——**光加载索引就超预算**。

## 2. 关键洞察：真正的浪费不是"加载慢"，是"加载了不需要的东西"

索引结构（实测）：

```
metadata: {num_docs, avg_doc_length, total_terms, collection}
index: { 词条: {idf, df, postings: [{chunk_id, tf, doc_length}, ...]} }
```

**BM25 打分只需要「查询里出现的那几个词条」的 postings**，外加两个全局标量
（`num_docs`、`avg_doc_length`）。一次查询分词后通常 5–20 个词条，
而词表有 70,000 个（50K 块时）。

> **现在的做法是：为了用 20 个词条，把 70,000 个全部反序列化进内存。**
> 浪费比例约 **3500 : 1**。

这个认识改变了方案选择：**问题的正解不是"把加载做快"或"把结果缓存住"，
而是"根本不要整体加载"。**

> 🔴 **修正（2026-08-25，原型实测）**：本节原来写的是
> "一旦按词条查，加载耗时与索引总量**解耦**"。**这句话是错的。**
>
> 按词条查省掉的是"读那 70,000 个用不到的词条"，但**查询词条自己的 postings 长度
> 仍然随文档数线性增长**——"申请"这种高频词在 1K 块时 postings 有几十条，
> 50K 块时就有上万条，全都得读出来打分。实测每次查询扫描的 postings 条数
> 稳定在 **0.327 × 块数**（1K/16K/50K 三档分别是 0.3270 / 0.3262 / 0.3271），
> 查询耗时也就跟着线性涨：**0.204 → 2.719 → 8.522 ms**。
>
> 正确的说法是：**常数因子降了两个数量级（实测 139–187 倍），
> 复杂度量级没变**。内存那一半结论**成立**（实测常驻从 1417 MB 降到 13 MB）。
> 详见 §10。

## 3. 方案对比

下表**单库按 143K 块（≈2GB 文档）计**，常驻内存按 3 客户 × 6 库 = 18 库计。
方案 C 那行是**实测 + 线性外推**，其余行仍是估算。

| | 方案 | 首次查询 | 后续查询 | 常驻内存（3客户×6库） | 改动量 |
|---|---|---|---|---|---|
| A | 内存缓存现有 JSON | 5s | ~0 | **≈71 GB** ❌ | 小 |
| B | 换二进制格式 + 缓存 | 0.5–1s | ~0 | ≈71 GB ❌（同 A：反序列化后仍是 Python 对象） | 中 |
| C | **词条级查询存储（SQLite）** | **≈24 ms** | **≈24 ms**（无首次/后续之分） | **≈0.7 GB** ✅ | 中 |
| D | 引入成熟检索引擎（Tantivy 等） | ~几 ms | ~几 ms | 低 | **大**，新依赖 |

方案 C 那行的由来（实测三点 → 线性外推，详见 §10）：

| 块数 | 单库单次查询 | 6 库一次提问 | 单库常驻内存 |
|---|---|---|---|
| 50,000（**实测**） | **8.5 ms** | 51 ms | **13.2 MB** |
| 143,000（外推） | 24 ms | 0.15 s | 38 MB |
| 716,000（外推） | 122 ms | 0.73 s | 189 MB |

> ⚠️ **A/B 两行的常驻内存原本写的是 12 GB / 3–6 GB，是按"内存占用 ≈ 索引文件大小"估的。
> 实测这个假设低估了 6–7 倍**：JSON 反序列化成 Python 的 dict/str 对象后，
> 50K 块的 235.7 MB 索引文件在内存里占 **1417.5 MB**。
> 按实测比例重算，方案 A 在 143K 块时是 **≈71 GB** 而不是 12 GB——
> **A 比原先以为的更不可行**，这一点反而加固了选 C 的结论。
>
> ⚠️ 方案 C 的常驻内存**不是 0**：SQLite 的 page cache 会随访问增长
> （实测 50K 块跑完 12 条查询后是 13.2 MB）。但它是**有上界、可配置**的
> （`PRAGMA cache_size`），与索引总量不成正比，这是它和 A/B 的本质区别。

### A：只加进程级缓存 —— ❌ 不推荐

最小改动，但把问题从"每次慢 5 秒"变成"**常驻 ≈71 GB**"
（原估 12 GB，实测把 JSON 载入内存要膨胀 6–7 倍，见 §10.4）。
目标部署是 16G 机器起步，**单个 143K 块的库就要 4 GB，放不下第二个**。
**这是我最初的直觉方案，被实测数据否掉了。**

### B：换二进制格式（msgpack / pickle）+ 缓存 —— ⚠️ 治标

加载快 5–10 倍，但**每次查询仍付这个钱**，且内存问题只是缓解不是消除。
另外 `pickle` 有反序列化执行风险，**在会摄入外部文档的系统里不应采用**。

### C：词条级查询存储 —— ✅ **推荐**

用 SQLite 存倒排索引，按词条查：

```
表 terms(term TEXT PRIMARY KEY, idf REAL, df INTEGER)
表 postings(term TEXT, chunk_id TEXT, tf INTEGER, doc_length INTEGER,
            PRIMARY KEY(term, chunk_id)) WITHOUT ROWID   ← 聚簇，见下
表 chunks(chunk_id TEXT PRIMARY KEY, doc_hash TEXT, source_path TEXT,
          INDEX(source_path), INDEX(doc_hash))           ← 关联列，见 §5
表 meta(collection TEXT, num_docs INT, avg_doc_length REAL, …)
```

查询复杂度是 **O(命中词条的 postings 总条数)**——**不是** O(查询词条数)，
也**不是**与索引总量无关。实测见 §10.1。

> **原型对本节原始表结构做了两处调整**（理由见 §10.4）：
> 1. postings 用 `WITHOUT ROWID` + `PRIMARY KEY(term, chunk_id)` 聚簇，
>    而不是普通表 + `INDEX(term)`。后者的二级索引不覆盖查询，每条 posting
>    都要回表随机读一次。实测聚簇后**索引文件小 12%**（50K 块：178 vs 202 MB）。
> 2. `doc_hash` / `source_path` 放独立的 `chunks` 表，不内联进 postings。
>    同一个 chunk 会出现在几十个词条的 postings 里，内联等于把路径重复几十遍。

**为什么选 SQLite 而不是自造二进制**：
- **已是本项目依赖**（`chunk_dedup.py`、`file_integrity.py`、`image_storage.py` 都在用），零新增
- 天然支持按词条索引查询、事务、并发读
- **顺带解决删除问题**（见 §5）

### D：引入 Tantivy / Lucene 绑定 —— 暂不推荐

技术上最优，但引入重量级新依赖，且现有 `SparseEncoder`/`BM25Indexer`/
`SparseRetriever` 三层抽象都要重写。**规模真上来再考虑**，
业界基准也把"换检索引擎"列在「规模上来才需要」。

## 4. 缓存还需要吗？需要，但缓存的东西变了

方案 C 之后，**不再需要缓存索引内容**。仍然值得缓存的是：

| 缓存对象 | 理由 | 失效时机 |
|---|---|---|
| SQLite 连接 | 建连接有开销，且现在**每查询新建** | 进程生命周期 |
| `meta`（两个标量） | 每次打分都要，但极小 | 摄入/清库时 |
| Chroma client | 同属 P1-8，**每查询 bootstrap 一次**，作者记录过并发 bootstrap 会崩 | 同上 |
| `httpx.AsyncClient` | 现每次远端调用新建，不复用连接 | lifespan |

**这才是 P1-8 该修的东西**——不是缓存索引，是缓存**客户端与连接**。

> ⚠️ **修正（原型实测）**：上表第一行「SQLite 连接」的优先级**被高估了**。
> 实测 50K 档，复用连接 vs 每次新建只差 **0.2 ms**（8.522 vs 8.720 ms），
> 相对 8.5 ms 的查询本身可以忽略。**这一行可以最后做，甚至不做。**
> 表里真正值钱的是 Chroma client 和 `httpx.AsyncClient` 那两行——
> 它们的每次重建成本远高于一个 SQLite 连接。

> ⚠️ 热词条 LRU 缓存**本设计不做**：SQLite 自己有 page cache，
> 再叠一层收益未知而失效逻辑变复杂。**要做也应在实测证明不够之后再做。**

## 5. 顺带解决 `remove_document` 死代码（P0）

`CLAUDE.md` §4 有一条 P0：`BM25Indexer.remove_document` 用
`chunk_id.startswith(doc_id)` 匹配，而实际 `chunk_id` 形如
`65046ad1_0000_2a3ac7ab`（`sha256(源路径)[:8]`）、传入 `doc_id` 是文件内容 SHA256，
**恒返回 False**。`add_documents` 的"重摄入清理旧 postings"用的同一函数，
**本该防止残留的保险从未生效**。

**当前 JSON 结构里根本没有可用于关联的字段**——postings 只有
`{chunk_id, tf, doc_length}`，没有 `doc_hash` / `source_path`。
所以那个 bug 不是"匹配写错了"，是**存储结构里就没存能匹配的东西**。

方案 C 重建存储时，postings 表**显式加上关联列**（`doc_hash` / `source_path`），
删除变成一条 `DELETE FROM postings WHERE source_path = ?` —— **P0 自然消解**。

> **这是本方案最被低估的收益**：它同时解掉「旧版本片段永久残留」那条正确性 P0 的
> 唯一硬阻塞（metadata 侧的 `doc_hash`/`source_path`/`processed_at` 本来就齐，
> 卡的就是 BM25 这一处）。

## 6. 迁移路径

现有 99 个 collection 的 JSON 索引怎么办：

| 阶段 | 内容 | 可独立上线 |
|---|---|---|
| 1 | 新增 SQLite 后端 + 双写（新索引同时写 JSON 和 SQLite），读仍走 JSON | ✅ |
| 2 | 读切到 SQLite，JSON 保留作回滚 | ✅ |
| 3 | 写迁移脚本把存量 JSON 转 SQLite（幂等、可 `--dry-run`，沿用本项目既有迁移脚本的写法） | ✅ |
| 4 | 停写 JSON，清理旧文件 | ✅ |

**每阶段都可独立回滚**。阶段 1–2 之间可以用同一批查询比对两种后端的打分结果再切读。

> 🔴 **修正（原型实测）**：本节原来的验收判据是"**确保排序完全一致**"。
> **这条判据按现有代码不可能达成**——实测 16K / 50K 两档，12 条查询里
> **0 条**的 top-10 顺序完全一致。
>
> 原因不是打分错了（完整分数映射是**逐 bit 相同**的，最大绝对差 `0.000e+00`），
> 而是**现有 `BM25Indexer.query` 没有确定性 tie-break**：它只按分数降序排，
> 同分者的相对顺序取决于 `scores` 字典的插入顺序，而插入顺序取决于 postings
> 的物理排列——**任何两种存储后端都不会一致**。50K 档实测每条查询在 top-10
> 截断线上平均有 **14–19 个同分候选**在抢最后几个名额。
>
> **因此阶段 1 之前要先补一步**：给 `BM25Indexer.query` 加确定性 tie-break
> （按 `(-score, chunk_id)` 排序，且**在截断之前**排）。加完之后实测
> **12/12 完全一致**。这一步对 JSON 后端单独上线也是纯收益——
> 它让现有检索结果从"不可复现"变成"可复现"。
>
> ✅ **两步前置均已于 2026-08-25 实施完毕**（tie-break + 建索引单遍改写），
> 回归保护 `tests/unit/test_bm25_tiebreak_and_build_complexity.py`（10 条）。
> 建索引侧同语料 A/B：**α 1.70 → 0.98**，9K 块 10.30s → 1.23s（8x），
> 三档索引输出逐键一致。详见 `CLAUDE.md` §4 第 2b 条。
> **本文剩余部分（方案 C 的四阶段迁移）仍未实施。**

> ⚠️ **T-2 的原判据"耗时差 < 20%"是照着"与规模无关"这个错误前提写的，
> 实测差 41.8 倍，按原判据会判定方案 C 失败。** 判据已按实测改写为
> "绝对值达标 + 相对现状有量级改善"——这才是真正要保证的东西
> （SLO 是 TTFT ≤ 3s，不是"延迟恒定"）。

### 需要什么 fixture

现有 `tests/conftest.py` **只有 3 个路径 fixture，无 DB/LLM fixture**。本设计需要：
- **临时索引目录 fixture** —— 每个测试独立，跑完清理（可参考
  `scripts/measure_bm25_index_growth.py` 的做法）
- **可参数化规模的语料生成 fixture** —— T-2 需要两个量级

**好消息**：这套测试**不需要 LLM，也不需要 Postgres**——BM25 是纯确定性逻辑。
所以它落在 `CLAUDE.md` §2「确定性层」，可以严格断言，是最好测的那一类。

### 现有结构支不支持

支持，但有一处要为可测性调整：`BM25Indexer` 现在把存储路径写死在构造参数里，
**后端类型没有抽象**。要让 T-1 能对比两种后端，需要把"存储后端"提成可替换的接口。
**这个调整本身就是方案 C 的一部分，不是额外成本。**

## 8.1 原始待拍板问题（已全部有结论，保留备查）

1. **选 C 还是先做 B 过渡？** C 改动更大但一次到位；B 快但要再改一次。
   我倾向 **C**——B 的内存问题没解决，等于要做两次。
2. **SQLite 单文件 per collection，还是全库一个文件？** 前者隔离性好（多租户友好）、
   删库简单；后者连接少。**倾向 per collection**，与现有 `data/db/bm25/{collection}/` 布局一致。
3. **迁移期要不要保留 JSON 双写？** 保留则可回滚，代价是摄入变慢、磁盘翻倍。
4. **存量 99 个 collection 要不要全迁？** 其中大量是测试残留
   （`conv_*` 会话库、`_bm25growth_*` 已清理），可能只需迁真实业务库。
5. **热词条 LRU 要不要现在做？** 我倾向不做，见 §4。

## 9. 风险与未覆盖

- ~~**未测 SQLite 在本项目实际负载下的查询延迟**~~ —— ✅ **已测（§10.1）**。
  结论与原假设**不同**：延迟随规模线性增长（0.204 / 2.719 / 8.522 ms @ 1K/16K/50K），
  不是"与总量无关"。绝对值仍远优于现状（提速 139–187 倍），方案可行。
  **新增风险**：单库超过 ~1M 块后，单次查询要扫 30 万条以上 postings、
  逼近 200 ms，6 库并查就吃掉 TTFT 预算的三分之一。到那一步需要
  **WAND / BlockMax 之类的 top-k 提前终止**，或直接上方案 D——
  这两者本项目都没有，属于**已知的规模天花板**。
- **未测多库并行查询时 SQLite 的并发表现** —— 原型只做了**单进程单线程**，
  这条**仍未覆盖**。
- ~~**未考虑索引写入性能**~~ —— ✅ **已测（§10.3），且结论是反的**：
  SQLite 批量写不但没变慢，还比现有 JSON 路径**快 95 倍**（50K 块：4.15s vs 393.97s）。
  原因是**现有 `BM25Indexer.build` 有个二次复杂度的实现问题**
  （`for term in 词表: for stat in term_stats:`，即 O(词表 × 文档数)，
  实测增长指数 α=2.23）。外推到 143K 块，现有实现光建 BM25 索引就要 **1.1 小时**，
  716K 块要 **41 小时**——这本身是一条独立的性能 P0，
  **原先"首次摄入 1.4–3.2 小时"的估算没有把它算进去**。
- **未测增量摄入路径** —— 原型只测了全量 `build`，没测 `add_documents`。
  而 `add_documents` 现在的写法是"把整个索引读回来 + 合并 + 全量重建"，
  在上述二次复杂度下每次增量摄入都会付全量代价。这条**未验证**。
- **本方案只解决 BM25 一侧**。P1-8 里的 Chroma client 每查询 bootstrap
  是另一个独立问题（§4 已列入缓存对象，但未展开设计）。
- **实测语料约 1/3 是仓库真实中文文本、2/3 为模板扩充**。真实企业文档词表更丰富，
  实际索引可能比 §1 的外推**更大**。模板文本重复度高，还会**制造偏多的分数平局**，
  §6 提到的"14–19 个同分候选"在真实语料上大概率会少一些——
  但"缺 tie-break 导致排序不可复现"这个结构性问题与语料无关。

## 10. 最小原型验证结果（2026-08-25）

脚本 `scripts/prototype_bm25_sqlite.py`，结果
`scripts/benchmark_results/bm25_sqlite_proto_20260825_210544.json`。
**零 `src/` 改动**：JSON 侧直接调用现有 `BM25Indexer`，SQLite 侧在脚本内实现最小后端。
语料沿用 `measure_bm25_index_growth.py` 的口径（约 1/3 仓库真实中文文本 + 2/3 模板扩充），
查询是 12 条模拟企业问答、用摄入侧同一个 `SparseEncoder` 分词。

> **跑了三轮，结果文件都保留**（`..._205159` / `..._205336` / `..._210544`，
> 后者为准）。**正确性判定三轮完全一致**（L1 逐 bit 相同、L3 加 tie-break 后一致、
> `remove_document` 三轮全部返回 `False`）。
> **但耗时有机器负载带来的抖动，下面的绝对值要按"同一量级"读，不要当精确值**：
> 50K 档现有 JSON 建索引三轮分别是 **656 / 615 / 394 s**（1.7 倍差），
> SQLite 建索引 5.38 / 4.65 / 4.15 s，SQLite 查询 10.07 / 8.93 / 8.52 ms。
> 本节取最后一轮（机器最空闲、对现状最有利）的数字，
> 所以**文中的倍数是保守下界**：例如"写入快 95 倍"在另两轮是 122 倍和 132 倍。

### 10.1 Q1：查询延迟与索引规模无关吗？——**否，被推翻**

单库单次查询中位耗时（ms）：

| 路径 | 1K 块 | 16K 块 | 50K 块 | 最大/最小 |
|---|---|---|---|---|
| **现状**：每查询 `json.load` 全量 | 28.378 | 428.881 | 1595.286 | 56.2× |
| JSON 已在内存（方案 A 的上限） | 0.091 | 1.559 | 5.653 | 62.1× |
| **SQLite 聚簇 + 复用连接（方案 C）** | **0.204** | **2.719** | **8.522** | **41.8×** |
| SQLite 聚簇 + 每次新建连接 | 0.350 | 2.911 | 8.720 | 24.9× |
| SQLite 普通表 + `INDEX(term)` | 0.204 | 3.009 | 8.809 | 43.2× |
| SQLite 批量 `WHERE term IN (...)` | 0.196 | 2.902 | 9.623 | 49.1× |

**延迟随规模近似线性，不是恒定。** 解释变量很干净：

| 块数 | 词表 | 每查询扫描 postings（中位） | 扫描量/块数 | 每千条 postings 耗时 |
|---|---|---|---|---|
| 1,000 | 6,388 | 327 | 0.3270 | 0.624 ms |
| 16,000 | 26,292 | 5,220 | 0.3262 | 0.521 ms |
| 50,000 | 71,086 | 16,354 | 0.3271 | 0.521 ms |

「扫描量/块数」三档几乎完全一致 → **命中 postings 的条数随文档数线性增长**，
而单位扫描成本恒定。省掉的是"读那 7 万个用不到的词条"，
省不掉的是"高频词自己的 postings 越来越长"。

外推（按 0.521 ms/千条、0.327 条/块）：

| 块数 | 单库单次查询 | 6 库一次提问 | 现状 6 库 |
|---|---|---|---|
| 143,000 | **24 ms** | 0.15 s | 27.4 s |
| 358,000 | **61 ms** | 0.37 s | 68.5 s |
| 716,000 | **122 ms** | 0.73 s | 137.1 s |

**结论：方案 C 的"~0"是错的，但它照样把 TTFT 从"光加载就超预算"救回到
"BM25 只占 3s 预算的 5%（143K）到 24%（716K）"。**

### 10.2 Q2：打分与现有 JSON 实现一致吗？——**分数完全一致，排序另有问题**

比对分三级（只比 top-k 会把"现有实现缺 tie-break"误记成"新后端算错了"）：

| 判据 | 1K | 16K | 50K |
|---|---|---|---|
| **L1 完整分数映射逐 bit 相同**（候选集 + 每个候选的分数） | **12/12** | **12/12** | **12/12** |
| L2 现状写法（只按分数降序）下 top-10 逐条相同 | 4/12 | 0/12 | 0/12 |
| **L3 加确定性 tie-break 后 top-10 逐条相同** | **12/12** | **12/12** | **12/12** |

三档的**最大绝对分数差都是 `0.000e+00`**——不是"误差够小"，是**逐 bit 相同**。
做到这一点靠两个刻意的实现选择：

- **逐词条 `SELECT`，不用一条 `WHERE term IN (...)`。** BM25 分数是逐词条累加的
  浮点加法，不满足结合律；一条 IN 查询返回的行按 term 字典序排，累加顺序就变了，
  分数会在末位 bit 上分叉。逐词条查才能保持与 JSON 实现相同的累加顺序。
  （批量 IN 实测也**没有更快**：50K 档 9.623 vs 8.522 ms，所以没有理由为它牺牲确定性。）
- **`_calculate_idf` / `_calculate_bm25_score` 逐字照搬**，包括 `avg_doc_length == 0`
  的兜底分支。

**L2 全挂是本次最值得注意的发现**，它不是新后端的缺陷，而是暴露了现有实现的问题：
`BM25Indexer.query` 只按分数降序排，同分者顺序 = `scores` 字典插入顺序 =
postings 物理顺序。**换任何存储后端都会变。** 50K 档实测每条查询在 top-10
截断线上有 14–19 个同分候选在抢名额。处理办法见 §6。

### 10.3 Q3：写入性能可接受吗？——**可接受，而且是反过来的：快得多**

建索引耗时（秒）：

| 块数 | 现有 `BM25Indexer.build` | 单遍算法 + 写 JSON | **SQLite 聚簇** |
|---|---|---|---|
| 1,000 | 0.35 | 0.10 | **0.06** |
| 16,000 | 31.08 | 1.56 | **1.09** |
| 50,000 | **393.97** | 5.10 | **4.15** |

索引体积（MB）：

| 块数 | JSON(indent2，现状) | JSON(compact) | **SQLite 聚簇** | SQLite 普通表 |
|---|---|---|---|---|
| 1,000 | 5.17 | 2.77 | **3.75** | 4.11 |
| 16,000 | 75.72 | 40.29 | **57.17** | 64.58 |
| 50,000 | 235.69 | 125.41 | **178.17** | 201.86 |

**设计文档原先担心的"逐条 INSERT 比一次性写 JSON 慢"没有发生**：
批量 `executemany` + 单事务 + `journal_mode=OFF`，50K 块建库 4.15s，
比现有 JSON 路径**快 95 倍**。

但这个 95 倍**主要不是 SQLite 的功劳**，所以必须拆开说清楚：

- 现有 `BM25Indexer.build` 是 `for term in 词表: for stat in term_stats:`，
  **O(词表 × 文档数)**，实测增长指数 **α = 2.23**（0.35 → 31.08 → 393.97）。
- 换成单遍构建倒排（O(总 postings)）后，**仍然写 JSON** 也只要 5.10s。
- SQLite 的 4.15s 与这 5.10s 才是可比的——**SQLite 略快，属于同一量级**。

**真正的结论是：现有 JSON 建索引有一个独立的二次复杂度 P0。**
外推：143K 块要 **1.1 小时**、358K 要 **8.8 小时**、716K 要 **41.3 小时**，
而 SQLite 分别是 12s / 30s / 59s。

体积上 SQLite 比现有 JSON **小 24%**，但比紧凑 JSON **大 42%**——
**磁盘不是方案 C 的收益点**，收益点是不用把它读进内存。

### 10.4 附带验证

**常驻内存（子进程实测，不是推算）**：

| 块数 | 索引文件 | JSON 载入内存后 | 膨胀倍数 | SQLite 跑完同一批查询 |
|---|---|---|---|---|
| 1,000 | 5.2 MB | 39.0 MB | 7.5× | **1.6 MB** |
| 16,000 | 75.7 MB | 512.3 MB | 6.8× | **6.9 MB** |
| 50,000 | 235.7 MB | 1417.5 MB | 6.0× | **13.2 MB** |

必须用**全新子进程**测：第一版在主进程里取 RSS 差值，16K 档量出 **−608 MB**——
主进程此前反复分配/释放过上百 MB，分配器把空闲页留在进程内不还给 OS，
差值反映的是碎片而不是索引占用。这条已写进脚本注释，避免以后有人重蹈。

**T-3 删除（设计 §5 的 P0）**：SQLite 侧
`DELETE FROM postings WHERE chunk_id IN (SELECT chunk_id FROM chunks WHERE source_path=?)`
实测 317 条 postings → 0 条，三档全通过。
同一档上，现有 `BM25Indexer.remove_document(doc_hash)` **三档全部返回 `False`**——
**P0 在原型里稳定复现**。已核对真实调用方 `document_manager.py:201` 传的就是
`source_hash`（文档内容 SHA256），而 `chunk_id` 形如 `65046ad1_0000_2a3ac7ab`
（`sha256(源路径)[:8]`），`startswith` 恒不匹配。

**表结构两个变体的对照**：聚簇（`WITHOUT ROWID` + `PK(term, chunk_id)`）
vs 普通表 + `INDEX(term)`——**体积小 12%**（178 vs 202 MB @50K），
**延迟差 3%**（8.522 vs 8.809 ms），在 warm OS page cache 下**延迟差异不显著**。
选聚簇主要是为体积和冷缓存下的顺序读，**不要宣称它带来了延迟收益**。

**连接复用**：复用连接 vs 每次新建，50K 档 8.522 vs 8.720 ms，**只差 0.2 ms**。
§4 把"SQLite 连接"列为需要缓存的对象——**实测优先级不高**，
真正值钱的是那里列的 Chroma client 和 `httpx.AsyncClient`。

### 10.5 本次未覆盖

- **多库并行 / 多进程并发读**同一 SQLite 文件——原型是单进程单线程。
- **OS page cache 冷启动**——macOS 下无法在不 sudo 的前提下清 page cache，
  所有 SQLite 数字都建立在文件已被 OS 缓存的前提上，**首查冷盘会更慢**。
- **增量摄入 `add_documents`** 路径完全未测（见 §9）。
- **50K 以上规模未实测**，143K / 716K 全是线性外推。
- **未接 `SparseRetriever` / `query_knowledge_hub`**，端到端 TTFT 未测；
  本节所有数字都是 BM25 打分这一层的。
- **未测 SQLite 损坏恢复、并发写、WAL 模式**（建库用的是 `journal_mode=OFF`）。
- 建库时倒排表**整个驻留内存**（50K 块约几百 MB），
  真上大规模摄入需要改成分批落盘，**本原型未验证这条路径**。

### 10.6 结论

结论分三档：**已验证通过**（跑了、有断言、结果符合判据）／
**已跑通**（跑了、没挂，但判据是观测值不是断言）／
**已实现但未验证**（代码写了，没有对应实测支撑）。

| 问题 | 答案 | 结论强度 |
|---|---|---|
| Q1 延迟与规模无关？ | **否。线性增长，"~0"被推翻。** 绝对值 8.5 ms@50K、提速 139–187 倍 | **已验证通过**（判据按实测改写，见 §7） |
| Q2 打分与 JSON 一致？ | **是。完整分数映射逐 bit 相同**（三轮、三档、36 次查询，最大差 `0.000e+00`）。top-k 排序需先补 tie-break | **已验证通过** |
| Q3 写入性能可接受？ | **是，且快 95 倍**（主因是现有实现有二次复杂度 P0） | **已验证通过** |
| T-3 删除 P0 | SQLite 侧删得掉；现有实现三轮稳定返回 `False` | **已验证通过** |
| 常驻内存 1417 MB → 13 MB | 子进程实测 | **已验证通过** |
| 143K / 716K 的外推值 | 线性外推，未实测该规模 | **已跑通**（外推依据是三点实测的线性关系，本身没跑过） |
| 聚簇表 vs 普通表的选择 | 体积小 12%，延迟差 3%（warm cache 下不显著） | **已跑通**（冷缓存下的差异未测，选型理由部分是推理） |
| SQLite 后端作为生产代码 | 原型在脚本内，**没有接进 `src/`**，没有并发、没有错误处理、没有迁移 | **已实现但未验证** |
| 多库并发 / 冷缓存 / 增量摄入 / WAL | —— | **未覆盖**（见 §10.5） |

**方案 C 是否成立：成立，但论据要换。**
它不是"把复杂度从 O(索引总量) 降到 O(查询词条数)"——那是错的；
它是"把常数因子降两个数量级、把常驻内存从随索引线性增长变成有上界、
并且顺带让 `remove_document` 那条 P0 第一次有解"。

**实施顺序建议（比原 §6 多一步前置）**：
0. **先给 `BM25Indexer.query` 加确定性 tie-break**（`(-score, chunk_id)`，截断前排序）。
   独立可上线，且是后续一切对比验收的前提。
1. 顺手修 `BM25Indexer.build` 的二次复杂度（单遍构建倒排）。
   **这条与方案 C 无关、独立收益极大**（143K 块从 1.1 小时降到 15 秒），
   而且万一方案 C 被推迟，它也已经落袋。
2. 再按原 §6 的四阶段走 SQLite 迁移。

## 11. 阶段 1 实施记录（2026-08-25）

> **状态：已实施并验证通过。** 代码 `src/ingestion/storage/bm25_sqlite_store.py`
> + `bm25_indexer.py` 的双写接线；回归保护 `tests/unit/test_bm25_sqlite_store.py`（22 条）。

### 做了什么

新增 `BM25SQLiteStore`（一个 collection 一个 `.sqlite`，与现有
`data/db/bm25/{collection}` 布局一致，**不合并成全局库**——`CLAUDE.md` §3.3
把物理隔离列为已验证的隔离保证，合并会把它降级成「靠 WHERE 条件隔离」）。

`BM25Indexer` 在 `build` / `add_documents` / `remove_document` 三个写入点做影子写。
**读路径一行未改，仍全部走 JSON。** 影子写失败**不阻断摄入**，但以 ERROR 记
`bm25.sqlite.dual_write_failed` —— 阶段 1 里 SQLite 没有生产读者，拿它去阻断
正在用的老链路是本末倒置；可一旦静默，阶段 2 切读时就无从知道哪个 collection
的副本掉过队。开关 `RAGENT_BM25_SQLITE_DUAL_WRITE=false` 可关。

### 性能：三组语料给出三个差很远的答案，别只引用一个

| 语料 | 50K 块 JSON | 50K 块 SQLite | 提速 | 说明 |
|---|---|---|---|---|
| 词条近似均匀（`random.sample`） | 1230.8 ms | 0.60 ms | **2044x** | ⚠️ **不真实**，postings 恒短，查询耗时是平的 |
| Zipf + 查**最高频的 5 个词** | 1349.2 ms | 128.08 ms | **11x** | 最坏情况，扫描量 3.4 条/块 |
| 原型语料 + 真实查询词（§10） | — | 8.5 ms | 139–187x | 扫描量 0.327 条/块，最有代表性 |

**三组之间差 200 倍，差别全在「查询词命中多少 postings」。** 引用时必须带上
是哪一组 —— 只报 2044x 会严重误导。
真正确定的结论是**下界**：即使按最坏情况，50K 块也只要 128 ms，
而 JSON 侧是 1349 ms × 6 库 = 8 秒，对 3 秒的 TTFT SLO 是硬伤。
另外 SQLite 文件约为 JSON 的一半（50K 块：151 MB vs 310 MB）。

### 顺带修掉一个真实的正确性 bug（不是性能问题）

SQLite 的主键 `(term, chunk_id)` 顶出了 JSON 侧一个此前完全静默的错误：
**重摄入同一份文档会让同一个 `chunk_id` 在索引里出现两次。**

链路：`remove_document` 因为那条已知 P0（`chunk_id.startswith(doc_id)` 恒为假）
根本没删掉旧数据 → `existing_stats` 里的旧 chunk 与新 `term_stats` 里的
**是同一个 chunk_id** → 两条都进了 `combined`。

后果不是多占空间，是**打分错**。实测同一文档摄入两次后：

```
第1次 -> postings=1  df=1  num_docs=1
第2次 -> postings=2  df=2  num_docs=2   ← 真实只有 1 个 chunk
```

`df == num_docs` 时经典 IDF `log((N-df+0.5)/(df+0.5))` 为负，
该文档自己的分数变成 **-4.598**，排到了「完全不含这个词的文档」后面。

修法是 `add_documents` 按 `chunk_id` 收敛、新值覆盖旧值。
回归保护 `tests/unit/test_bm25_tiebreak_and_build_complexity.py::TestReingestDoesNotDoubleCountChunks`（3 条，去掉修复后全红）。
⚠️ **这不能替代修 `remove_document`** —— 旧文档**其他** chunk 的残留仍在，
那是 `CLAUDE.md` §4 第 1 条那条 P0。

### 一条被自己推翻的设计（记下来免得有人重走）

实施中一度给 `chunks` 表加了 `ord` 列，用来复刻 postings 在 `term_stats` 里的
原始顺序，理由是「浮点加法不满足结合律，累加顺序不同会差 1 ULP，
逐 bit 等价会失守」。**担心是对的，落点是错的**：

- 顺序敏感性实测成立 —— 20 万组真实 BM25 分数、朴素累加下 **62.8%** 的组合
  重排后会差 1 ULP；
- 但**单个 chunk 的分数累加顺序只由外层 `for term in query_terms` 决定**，
  词条内 postings 的先后只影响「哪个 chunk 先拿到这一项」，不改变任何单个
  chunk 自身的累加序列。两种后端外层都按 `query_terms` 原序走，等价天然成立。

`ord` 列已删。判别力实测：去掉 `ORDER BY c.ord` 后测试全绿 —— 这正是它多余的证据。

〔另一个坑：验证顺序敏感性时若用 `sum()` 会得出「不敏感」的错误结论 ——
Python 3.12 起 `sum()` 改用 Neumaier 补偿求和，而生产代码是朴素累加。
第一版探针就是这么测的，自检时用 `[1e16, 1.0, -1e16]` 才发现探针本身是坏的。〕

### 三句话

- **验收怎么做**：`pytest tests/unit/test_bm25_sqlite_store.py -q` 应 22 passed；
  摄入任意文档后 `data/db/bm25/{collection}_bm25.sqlite` 应出现，
  且与 JSON 侧同一查询的完整分数映射逐 bit 相同。
- **回归怎么保**：`test_bm25_sqlite_store.py`（22 条）。三条真不变量的判别力
  已逐条实测：括号位置改动 → 3 红；`repr` 换 `str` → 1 红；重复查询词去重 → 1 红。
- **什么没做**：阶段 2–4 全部未做（**存量 99 个 collection 的 JSON 索引尚未迁移，
  只有此后新写入的才有影子副本**）；`delete_by_doc_hash` 不重算 idf/df
  （阶段 1 权威值来自 JSON 全量重建，切读前必须补）；未测多库并行/多进程并发读、
  WAL 与崩溃恢复、50K 以上真实规模、端到端 TTFT。
