## 1. 问题（已实测，不再是推算）

`CLAUDE.md` §4 那条 P0 此前是从 20 块样本单点线性外推的。现已用四个规模点实测：

| 块数 | 索引体积 | 词表 | 字节/块 | `json.load` |
|---|---|---|---|---|
| 1,000 | 5.13 MB | 6,123 | 5,377 | 0.029s |
| 4,000 | 19.34 MB | 10,089 | 5,069 | 0.103s |
| 16,000 | 75.79 MB | 26,015 | 4,967 | 0.430s |
| 50,000 | 235.94 MB | 70,830 | 4,948 | 1.768s |

**增长指数 α = 0.997 —— 几乎完全线性。** 加载速率实测 **133 MB/s**。

> 原本指望 Heaps 定律（词表次线性）拉低总量，**这个指望被推翻了**：
> 词表确实次线性，但 postings 随文档数线性增长且完全占主导，16 倍规模下
> 单块开销只降 8%。

外推到目标数据量（单客户几个 G 文档）：

| 块数 | 索引 | 单次加载 |
|---|---|---|
| 143K（≈2GB 文档） | **672 MB** | **5.0s** |
| 358K（≈5GB） | **1.68 GB** | **12.6s** |
| 716K（≈10GB） | **3.35 GB** | **25.1s** |

**结论方向不变，量级比原推算低 3–8 倍。** 但仍然致命：
`query_knowledge_hub.py` 每次查询、每个候选库各做一次全量 `json.load`
（`_build_hybrid_search_for`，且 `_execute_local_multi` 不走带缓存包装的
`_ensure_initialized`）。一个 6 库企业每次提问 = 6 × 5s 加载、内存峰值约 4 GB，
而 SLO 是 **TTFT ≤ 3s**——**光加载索引就超预算**。

## 2. 关键洞察：真正的浪费不是"加载慢"，是"加载了不需要的东西"

索引结构（实测）：

```
metadata: {num_docs, avg_doc_length, total_terms, collection}
index: { 词条: {idf, df, postings: [{chunk_id, tf, doc_length}, ...]} }
```

**BM25 打分只需要「查询里出现的那几个词条」的 postings**，外加两个全局标量
（`num_docs`、`avg_doc_length`）。一次查询分词后通常 5–20 个词条，
而词表有 70,000 个（50K 块时）。

> **现在的做法是：为了用 20 个词条，把 70,000 个全部反序列化进内存。**
> 浪费比例约 **3500 : 1**。

这个认识改变了方案选择：**问题的正解不是"把加载做快"或"把结果缓存住"，
而是"根本不要整体加载"。** 一旦按词条查，加载耗时与索引总量**解耦**，
内存问题也一并消失——缓存就从"必需品"降级为"锦上添花"。

## 3. 方案对比

| | 方案 | 首次查询 | 后续查询 | 常驻内存（3客户×6库） | 改动量 |
|---|---|---|---|---|---|
| A | 内存缓存现有 JSON | 5s | ~0 | **≈12 GB** ❌ | 小 |
| B | 换二进制格式 + 缓存 | 0.5–1s | ~0 | 3–6 GB ❌ | 中 |
| C | **词条级查询存储（SQLite）** | **~0** | **~0** | **≈0** ✅ | 中 |
| D | 引入成熟检索引擎（Tantivy 等） | ~0 | ~0 | 低 | **大**，新依赖 |

### A：只加进程级缓存 —— ❌ 不推荐

最小改动，但把问题从"每次慢 5 秒"变成"**常驻 12 GB**"。
目标部署是 16G 机器起步，直接爆。**这是我最初的直觉方案，被实测数据否掉了。**

### B：换二进制格式（msgpack / pickle）+ 缓存 —— ⚠️ 治标

加载快 5–10 倍，但**每次查询仍付这个钱**，且内存问题只是缓解不是消除。
另外 `pickle` 有反序列化执行风险，**在会摄入外部文档的系统里不应采用**。

### C：词条级查询存储 —— ✅ **推荐**

用 SQLite 存倒排索引，按词条查：

```
表 terms(term TEXT PRIMARY KEY, idf REAL, df INTEGER)
表 postings(term TEXT, chunk_id TEXT, tf INTEGER, doc_length INTEGER,
            源文档标识…, INDEX(term), INDEX(源文档标识))
表 meta(collection TEXT, num_docs INT, avg_doc_length REAL, …)
```

查询：`SELECT ... FROM postings WHERE term IN (?,?,...)` —— **O(查询词条数)，与索引总量无关**。

**为什么选 SQLite 而不是自造二进制**：
- **已是本项目依赖**（`chunk_dedup.py`、`file_integrity.py`、`image_storage.py` 都在用），零新增
- 天然支持按词条索引查询、事务、并发读
- **顺带解决删除问题**（见 §5）

### D：引入 Tantivy / Lucene 绑定 —— 暂不推荐

技术上最优，但引入重量级新依赖，且现有 `SparseEncoder`/`BM25Indexer`/
`SparseRetriever` 三层抽象都要重写。**规模真上来再考虑**，
业界基准也把"换检索引擎"列在「规模上来才需要」。

## 4. 缓存还需要吗？需要，但缓存的东西变了

方案 C 之后，**不再需要缓存索引内容**。仍然值得缓存的是：

| 缓存对象 | 理由 | 失效时机 |
|---|---|---|
| SQLite 连接 | 建连接有开销，且现在**每查询新建** | 进程生命周期 |
| `meta`（两个标量） | 每次打分都要，但极小 | 摄入/清库时 |
| Chroma client | 同属 P1-8，**每查询 bootstrap 一次**，作者记录过并发 bootstrap 会崩 | 同上 |
| `httpx.AsyncClient` | 现每次远端调用新建，不复用连接 | lifespan |

**这才是 P1-8 该修的东西**——不是缓存索引，是缓存**客户端与连接**。

> ⚠️ 热词条 LRU 缓存**本设计不做**：SQLite 自己有 page cache，
> 再叠一层收益未知而失效逻辑变复杂。**要做也应在实测证明不够之后再做。**

## 5. 顺带解决 `remove_document` 死代码（P0）

`CLAUDE.md` §4 有一条 P0：`BM25Indexer.remove_document` 用
`chunk_id.startswith(doc_id)` 匹配，而实际 `chunk_id` 形如
`65046ad1_0000_2a3ac7ab`（`sha256(源路径)[:8]`）、传入 `doc_id` 是文件内容 SHA256，
**恒返回 False**。`add_documents` 的"重摄入清理旧 postings"用的同一函数，
**本该防止残留的保险从未生效**。

**当前 JSON 结构里根本没有可用于关联的字段**——postings 只有
`{chunk_id, tf, doc_length}`，没有 `doc_hash` / `source_path`。
所以那个 bug 不是"匹配写错了"，是**存储结构里就没存能匹配的东西**。

方案 C 重建存储时，postings 表**显式加上关联列**（`doc_hash` / `source_path`），
删除变成一条 `DELETE FROM postings WHERE source_path = ?` —— **P0 自然消解**。

> **这是本方案最被低估的收益**：它同时解掉「旧版本片段永久残留」那条正确性 P0 的
> 唯一硬阻塞（metadata 侧的 `doc_hash`/`source_path`/`processed_at` 本来就齐，
> 卡的就是 BM25 这一处）。

## 6. 迁移路径

现有 99 个 collection 的 JSON 索引怎么办：

| 阶段 | 内容 | 可独立上线 |
|---|---|---|
| 1 | 新增 SQLite 后端 + 双写（新索引同时写 JSON 和 SQLite），读仍走 JSON | ✅ |
| 2 | 读切到 SQLite，JSON 保留作回滚 | ✅ |
| 3 | 写迁移脚本把存量 JSON 转 SQLite（幂等、可 `--dry-run`，沿用本项目既有迁移脚本的写法） | ✅ |
| 4 | 停写 JSON，清理旧文件 | ✅ |

**每阶段都可独立回滚**。阶段 1–2 之间可以用同一批查询比对两种后端的打分结果，
**确保排序完全一致**再切读。

## 7. 测试设计（按 `CLAUDE.md` §7.1，设计阶段必交）

### 怎么验证

| # | 用例 | 判据 | 修复前会失败吗 |
|---|---|---|---|
| T-1 | 同一查询在 JSON 后端与 SQLite 后端的打分结果**逐条相同** | 排序与分数一致 | 新后端不存在时不适用 → **迁移期专用** |
| T-2 | 查询耗时与索引规模**无关** | 1K/50K 块两档的查询耗时差 < 20% | ✅ 现在是线性相关 |
| T-3 | `remove_document` 真的删得掉 | 删后再查该文档的词条，postings 为空 | ✅ **现在恒返回 False** |
| T-4 | 重摄入同名文档不产生重复 postings | 计数不增 | ✅ 现在会重复 |
| T-5 | 并发查询同一 collection 不互相干扰 | 真并发，结果一致 | 需并发方式验证（硬性规则） |
| T-6 | 摄入/清库后缓存正确失效 | 失效后读到新数据 | ✅ 现在无缓存所以"不失效"不成立 |

**T-2 和 T-3 是最重要的两条**：前者证明架构改对了，后者证明 P0 真解了。

### 需要什么 fixture

现有 `tests/conftest.py` **只有 3 个路径 fixture，无 DB/LLM fixture**。本设计需要：
- **临时索引目录 fixture** —— 每个测试独立，跑完清理（可参考
  `scripts/measure_bm25_index_growth.py` 的做法）
- **可参数化规模的语料生成 fixture** —— T-2 需要两个量级

**好消息**：这套测试**不需要 LLM，也不需要 Postgres**——BM25 是纯确定性逻辑。
所以它落在 `CLAUDE.md` §2「确定性层」，可以严格断言，是最好测的那一类。

### 现有结构支不支持

支持，但有一处要为可测性调整：`BM25Indexer` 现在把存储路径写死在构造参数里，
**后端类型没有抽象**。要让 T-1 能对比两种后端，需要把"存储后端"提成可替换的接口。
**这个调整本身就是方案 C 的一部分，不是额外成本。**

## 8. 待用户拍板

1. **选 C 还是先做 B 过渡？** C 改动更大但一次到位；B 快但要再改一次。
   我倾向 **C**——B 的内存问题没解决，等于要做两次。
2. **SQLite 单文件 per collection，还是全库一个文件？** 前者隔离性好（多租户友好）、
   删库简单；后者连接少。**倾向 per collection**，与现有 `data/db/bm25/{collection}/` 布局一致。
3. **迁移期要不要保留 JSON 双写？** 保留则可回滚，代价是摄入变慢、磁盘翻倍。
4. **存量 99 个 collection 要不要全迁？** 其中大量是测试残留
   （`conv_*` 会话库、`_bm25growth_*` 已清理），可能只需迁真实业务库。
5. **热词条 LRU 要不要现在做？** 我倾向不做，见 §4。

## 9. 风险与未覆盖

- **未测 SQLite 在本项目实际负载下的查询延迟** —— §3 表格里方案 C 的
  "~0" 是**基于 O(查询词条数) 的推断，不是实测**。实施前应先做一个最小原型验证。
- **未测多库并行查询时 SQLite 的并发表现**。
- **未考虑索引写入性能** —— 摄入时逐条 INSERT 可能比一次性写 JSON 慢，
  需要批量写 + 事务。几个 G 文档的首次摄入本来就要 1.4–3.2 小时，
  这部分若明显变慢需要单独评估。
- **本方案只解决 BM25 一侧**。P1-8 里的 Chroma client 每查询 bootstrap
  是另一个独立问题（§4 已列入缓存对象，但未展开设计）。
- **实测语料约 1/3 是仓库真实中文文本、2/3 为模板扩充**。真实企业文档词表更丰富，
  实际索引可能比 §1 的外推**更大**。
