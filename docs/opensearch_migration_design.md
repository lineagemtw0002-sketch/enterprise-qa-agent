## 1. 三行决策

```
- 决策：检索存储层（BM25 + ChromaDB）整体迁移到自建 OpenSearch，
        按 OpenSearch 惯用法设计，不做适配层把它包装成现有抽象的替身
- 理由：手写 BM25 的三个坑（全量加载 5.9s/库、6 线程 GIL convoy 103x、
        按文档删除恒失败）根因都是"用 Python 手写检索引擎"这个选型，不是实现问题；
        且 ES/OpenSearch 的确定性 _id + delete_by_query 让 P0#1 与 P0#7
        在设计上不成立，不需要写代码去修
- 作废：bm25_indexer / bm25_sqlite_store / sparse_retriever / dense_retriever /
        fusion（手写 RRF）/ SparseEncoder / ChromaDB 存储层
  影响：摄入流水线阶段 5–7、检索链路、CLAUDE.md §2 §3.3 §4、
        docs/bm25_storage_design.md（作废）
```

**为什么选 OpenSearch 而不是 Elasticsearch**：本项目是多租户 SaaS，
RBAC / 字段级安全 / 审计日志是**核心需求不是可选项**，而 Elasticsearch 把它们
连同 RRF retriever 一起放在 Platinum / Enterprise 付费层；OpenSearch 这些是基线且
Apache-2.0。两者 API 高度相似，将来要换代价不大。

## 2. 问题：三个坑都不是算法问题

全部为本机实测，不是推算。

| 问题 | 实测 | 根因 |
|---|---|---|
| **P0#2 BM25 全量加载** | 143K 块单库单次查询 **5926ms**（load 5365 + query 560），6 库串行 35.6s，而 TTFT SLO 是 3s | 每次查询 `json.load` 整个索引 |
| **GIL convoy** | 10K 块 hot 查询，6 线程 **2633ms** vs 1 线程 25ms（**103.4x**），比 JSON 还慢 | `sqlite3` 每返回一行都要释放/重取 GIL |
| **P0#7 按文档删除失效** | `remove_document` 三轮独立测试**恒返回 False** | 存储结构里没有可关联文档的字段 |
| **P0#1 旧版本片段残留** | 改一句话重传，库中两版各 1 条 | `doc_id = 文件 SHA256`，内容一变即视为新文档 |
| 常驻内存 | 143K 块 JSON 侧 **2153–3485 MB**，与查询无关、恒随索引线性 | 整份索引进 Python 堆 |

### 同规模对照（10K 块，hot 查询命中 9999/10000）

| 线程数 | 现状（SQLite） | OpenSearch |
|---|---|---|
| 1 | 25 ms | 23 ms |
| 2 | 130 ms | 72 ms |
| **6** | **2633 ms（103.4x）** | **109 ms（4.8x）** |

**单线程两者持平**——这一点很关键：OpenSearch 的优势不在算法，
就在**扫描不发生在 Python 进程里**，所以 GIL convoy 在结构上不可能出现。

## 3. 索引与多租户模型

### 3.1 两类库，两种策略

```
kb_{collection}            业务知识库：一库一 index
                           17 个，稳定，每企业 6 个左右
                           => 保留物理隔离（CLAUDE.md §3.3）
                           ⚠️ 实施时去掉了名字里的 {org}：collection 名在
                           org_collections 表里已全局唯一，拼上 org 会在
                           "库改归属"时被迫改 index 名（等于重建整个索引）。
                           企业边界仍由 _org_owned_collections() 在检索前收敛。

conv_{org}                 对话私有库：每企业一个 index，内部按对话路由
                           routing = conversation_id
                           filter  = owner_user_id（结构性保证，见 §3.3）
                           回收    = 跟随对话生命周期（主），ILM 兜底孤儿数据
                                     ⚠️ 主机制**不是**按年龄删——对话上传的文档
                                     有明确归属对象，按年龄删会导致"对话还在、
                                     文件名还看得见、问它却答不出来"的静默失效
```

**为什么 `conv_*` 不能一对话一 index**：它随使用无界增长（现有 7 个），
而每个只装一两份上传文档。这正是业界公认的 **index explosion 反模式**——
每个 index 的元数据由 master 维护、每个 shard 吃堆内存，
而推荐 shard 大小是 10–50GB，本项目的对话库比这小六个数量级。

**为什么按企业分而不是全局共享**：全局共享会把 A 公司和 B 公司的对话文档
放进同一个 index，**降级 `CLAUDE.md` §3.3 那条已验证的物理隔离**。
按企业分之后 index 数从 `O(对话数)` 变成 `O(企业数 + 业务库数)`——
3 家客户 = 3 + 18 = **21 个 index**，有界，且跨企业仍是物理隔离。

### 3.2 字段设计

```
mappings:
  content        text          # BM25，Lucene 原生
  embedding      dense_vector  # kNN；向量仍由本地模型生成（见 §4）
  source_path    keyword       # 删除/更新的锚点
  chunk_index    integer
  doc_hash       keyword
  owner_user_id  keyword       # conv_ index 用，见 §3.3
  ingested_at    date

_id = hash(source_path + chunk_index)   # 确定性
```

### 3.3 一处安全加固：把约定变成结构

现状：`acl.py::is_collection_allowed` 对任何 `conv_` 前缀**无条件返回 True**，
安全性完全建立在"只有对话使用者知道 conversation_id"上。

**核查结论：当前没有漏洞。** collection 名由服务端从已校验的 `conversation_id`
拼出，客户端注入不进来；`_require_conversation_owner()` 在 **11 个端点**上都调了。

**但防护是约定式的**——ACL 层自己没有任何保护，依赖 11 个调用点各自记得先校验。
迁移时顺手改成结构性保证：`conv_{org}` index 的每次查询强制带
`filter: { term: { owner_user_id } }`，值来自 JWT 而非请求体。
**这不是修漏洞，是把"靠人记得"换成"漏了就查不到数据"。**

### 3.4 对 `CLAUDE.md` §3.3 的影响（需你确认后才改）

按 §7.1，改权限模型前要先更新 §3 并等确认。**本文只提出改法，尚未改动 §3.3**——
因为 §3.3 描述的是"当前状态"，未实施前改了就是假信息。

提议的新表述：

| 检查项 | 迁移后 |
|---|---|
| 业务知识库是否全局共享 | **否** —— 一库一 index（`kb_{collection}`） |
| 对话私有库 | **按企业分 index**（`conv_{org}`），企业间物理隔离；企业内按 `owner_user_id` 过滤 |
| 候选库范围 | 不变：`_org_owned_collections(org)` ∩ 角色 ACL |

⚠️ **这是一次隔离模型的实质变更**：对话私有库从"一对话一物理存储"变成
"一企业一物理存储 + 字段过滤"。**跨企业隔离强度不变，企业内隔离强度下降一档**
（从物理变成逻辑）。这一条必须你明确接受。

## 4. 三条已收敛的决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **embedding 保留本地生成**，写 `dense_vector`，不用 `semantic_text` | ELSER / ML node 在 ES 要 Platinum；OpenSearch 虽免费但要多跑一个模型服务。现有本地 Ollama + 启动预热已实测可用（冷热差 ≤0.5s），没有换的理由 |
| 2 | **reranker 不动** | 现用 `bge-reranker-base`，实测整个检索阶段（含重排）0.28–0.39s，工作正常。业界数据显示大 reranker 可能到 1.5–2.5s，本项目没踩到。换掉是纯风险无收益 |
| 3 | **RRF 融合暂时保留现有实现** | OpenSearch 有原生混合检索，但现有 `fusion.py` 已验证可用。先迁存储，融合作为第二步独立评估 |

**结果：迁移范围收窄为「只替换检索存储层」**，摄入的分块/embedding、重排、
融合全部维持现状。比"全面 ES 化"小得多，风险也低一档。

### 4.1 🔴 中文分析器 —— 阶段 1 实施时发现的设计缺口

**本文第一版漏了分析器这一项，而它直接决定检索质量。** 实测三种切法：

| | `年假可以顺延到次年三月` |
|---|---|
| OpenSearch `standard`（默认） | `年 假 可 以 顺 延 到 次 年 三 月` —— **逐字切** |
| OpenSearch `cjk`（内置） | `年假 假可 可以 以顺 顺延 …` —— 二元组 |
| **项目分词器**（迁移期） | `年 假 顺延到 次年 三月` —— 真分词 |
| **项目分词器**（2026-08-26 起，索引侧） | `年 假 可以 顺延 延到 顺延到 次年 三月` —— jieba 搜索模式 |

**直接用默认分析器是检索质量倒退**：单字切分会让"关键词4"匹配上"关键词0"
（共享 关/键/词）。这个缺口是写测试时红出来的 —— 第一版断言靠
`search_kb("关键词4") == []` 证明删干净了，结果查到了别的 chunk。

**决定：迁移期用 `whitespace` 分析器 + 索引侧写入项目自己分好词的文本。**

理由是**隔离变量**：这次迁移要回答的是"换存储引擎会不会出问题"，
不是"换分词器好不好"。保持 tokenization 完全不变，任何检索质量变化都能
归因到存储层；两个一起换，出了问题无法区分。

⚠️ 2026-08-26 迁移验完之后，分词**已经单独动过一次**（见下文 9b 那一节）。
`whitespace` + 自己分词这个决定没变，变的是分词规则本身。

代价是放弃 OpenSearch 的分析器生态（`analysis-ik` 插件是中文事实标准）。
**这应当作为迁移完成后的独立课题评估**，判据是黄金测试集通过率，
而不是"看起来更合理"。

⚠️ 这条也意味着 `QueryProcessor` **不能删**（本文 §1 的作废清单里没有它，
但容易被顺手清理掉）。

## 5. 部署形态

**前置条件：本项目目前无 Dockerfile / 无 CI / 无依赖锁定**（`CLAUDE.md` §4 P1）。
**在没有部署基础设施的项目里引入有状态服务，顺序是反的。**
`docker-compose.yml` 必须先于本迁移落地。

本机开发实测配置（已验证）：

```yaml
opensearch:
  image: opensearchproject/opensearch:2
  environment:
    - discovery.type=single-node
    - OPENSEARCH_JAVA_OPTS=-Xms512m -Xmx512m
    - DISABLE_SECURITY_PLUGIN=true       # ⚠️ 仅本地开发
    - DISABLE_INSTALL_DEMO_CONFIG=true
  deploy: { resources: { limits: { memory: 1g } } }
```

实测占用：

| 阶段 | 容器 RSS |
|---|---|
| 空容器 | 831.8 MiB |
| + 604 条真实文档 | 844.2 MiB |
| + 10,000 块合成语料 | **862.3 MiB** |

**数据几乎不占内存**，占用全在 JVM 本身。启动 3s，10K 块灌入 3.7s。

⚠️ **这套配置只对本机测试数据成立。** 目标规模（143K 块 × 6 库 × 3 客户）下
`scale_slo_and_priorities.md` 算过需 4.6–10.8GB 向量常驻，
**16GB 开发机在装 OpenSearch 之前就已经不够**。生产堆通常给可用内存一半，
**不要照抄本节配置**。

## 6. 测试设计（按 §7.1，设计阶段必交）

### 6.1 这个设计怎么测

| # | 用例 | 判据 | 修复前会失败吗 |
|---|---|---|---|
| **T-1** | **重摄入同一文档，旧版本片段消失** | 同 `_id` 重写后 doc count 不变、内容为新版；文档变短时多余 chunk 被删净 | ✅ **现在库里会有两版**（P0#1，已实测） |
| **T-2** | **按文档删除真的删得掉** | `delete_by_query(source_path)` 后该文档 chunk 数为 0 | ✅ **现在恒返回 False**（P0#7） |
| **T-3** | **6 库并发查询不劣化** | 6 并发挂钟 / 1 并发 < 10x（现状 103.4x） | ✅ 现在是 103.4x |
| **T-4** | **跨企业隔离**：A 企业用户查不到 B 企业任何 chunk | 真实 JWT 走完整链路，返回集合为空 | ⚠️ 现在也应通过——**这是防迁移引入回归，不是修复** |
| **T-5** | **企业内对话隔离**：同企业用户 A 查不到用户 B 的对话私有库 | 同上；**这条覆盖 §3.3 那个降级点** | ⚠️ 现在靠物理隔离天然成立，迁移后靠 filter，**必须有测试钉住** |
| **T-6** | 检索质量不回退 | 黄金测试集通过率不低于迁移前基线 | ❌ 不适用（是回归保护） |
| **T-7** | OpenSearch 不可用时的降级行为 | 明确报错，不静默返回空结果 | ✅ 现在没有这条路径 |

**T-5 是本设计最关键的一条测试**，因为它守的正是被主动降级的那道防线。

### 6.2 需要什么 fixture

现有 `tests/conftest.py` **只有 3 个路径 fixture，无 DB/LLM fixture**——
这是后端 12,200 行零测试的结构性原因（`CLAUDE.md` §7.1）。本设计需要新增：

- **`opensearch_container` fixture**：session 级，起一个 testcontainer 或复用
  已跑的本地实例；每个测试用独立 index 前缀，跑完删干净
- **`seed_corpus` fixture**：可参数化规模，复用
  `scripts/seed_large_bm25_corpus.py`（已验证语料保真度 ±5%）
- **`two_orgs_two_users` fixture**：T-4 / T-5 需要，造两企业两用户及各自 JWT

### 6.3 现有结构支不支持

**部分不支持，且必须在动手前解决**：

1. **现有 29 条 SQLite 测试全是白盒**（断言 `_index` 内部状态、postings 条数、
   逐 bit 分数），**换引擎后一条都留不下**。
   **ES 版本必须写成行为级**：给定语料和查询，期望哪些 chunk 命中、
   重摄入后旧版本是否消失、跨租户是否查不到。
   **这样下次再换引擎不用重来一遍。**
2. **T-4 / T-5 要走完整鉴权链路**，而现在 `create_app()` 3038 行、
   依赖靠闭包捕获而非注入，测一个端点就得建整个 app 并连 Postgres。
   → **这两条测试的可行性依赖依赖注入改造**，否则只能退化成"直接调
   `query_knowledge_hub` 并手工构造 ACL 参数"，覆盖度打折。
   **这个反馈必须发生在动手之前**（§7.1）。

### 6.4 判别力

每条测试写完都要问：**它在迁移前会失败吗？** T-1 / T-2 / T-3 / T-7 会（它们对应真缺陷）；
T-4 / T-5 / T-6 不会——**它们是回归保护，不是修复验证，交付时要分开报**，
不能混进"修了几个 P0"里。

## 9. 已实测支撑本设计的结论

均为 2026-08-26 本机实测，OpenSearch 2.19.6 / 512MB 堆：

- **P0#1 解法有效**：同 `_id` 重写后 count 10000 不变、`_version=2`、内容已替换
- **P0#7 解法有效**：`delete_by_query(source_path=doc_5)` 删掉 8 条，剩余 0
- **GIL convoy 消失**：6 线程 109ms vs SQLite 2633ms（**24 倍**），无超线性恶化
- **内存可控**：10K 块仅比空容器多 18MB，总计 862 MiB
- **写入吞吐**：10K 块 bulk 灌入 3.7s；604 条真实文档 147ms

### 存量迁移真跑结果

**14 个业务库通过**（13 个重叠率 100%、`mmarco` 98%），全部带 768 维向量。
13 个 `__summary` 库写入成功但**无法比对**——它们是纯向量层（只

这是正确行为不是缺口，但意味着**它们的正确性要靠 dense 侧验证，目前未做**。

### 验收判据改了两次，两次都是判据本身错了

**第一版：两边 top-20 集合相等。** `mmarco` 报 3/6 组不同。

调查时先手工比了一组 **3 词**查询得到 20/20，以为是截断边界效应——
但脚本用的是 **4 词**查询，**手工那次和脚本比的不是同一个东西**。
用真实查询重跑才看到 16/20，才追到根因。

**根因是 `k1` 没对齐**：Lucene 默认 `k1=1.2`，而 `BM25Indexer` 用 `k1=1.5`。
建 index 时显式设 `similarity {type: BM25, k1: 1.5, b: 0.75}` 之后，
top-20 重叠 **16–20/20 → 19–20/20**。
**可配置的差异必须先对齐，剩下的差异才归因得到引擎本身。**

**最终判据：总重叠率 ≥ 95%**，并打出实际数字。残余 2% 是引擎固有的——
Lucene 把字段长度**有损量化成一个字节**，长度归一化项与精确计算有微小出入，
表现为个别文档在截断线附近换位（实测：旧第 20 → 新第 23）。
这修不掉也不该修。**用"必须完全相等"去要求一个做不到的东西，
只会得出"迁移失败"的错误结论。**

⚠️ 这一点和上一轮 SQLite 迁移相反：那边能用"逐 bit 相同"，是因为同一套公式的
两种存储；这次换的是引擎，那个判据不适用。**判据要跟着被验证的对象走。**

### 🟢 发现一个既有缺陷：索引侧与查询侧分词器不一致（迁移期不修，**2026-08-26 已修**）

`sparse_encoder.py::_tokenize` 的注释写着"必须与查询侧一致，这是 BM25 匹配的
前提"。**实测不成立。** 对同一批 22 条真实 chunk 双跑两个分词器：

| | 词数 | 样例 |
|---|---|---|
| 两侧都产出 | 132（69%） | |
| 只有索引侧 | 41（21%） | `hr` `it` `主管` `丢失` `为期` |
| 只有查询侧 | 29（15%） | `3` `5` `b` `不` `为` `假` |

根因是定位不同：`SparseEncoder` 是分词器（过滤单字），
`QueryProcessor` 是关键词抽取器（保留单字、丢部分实词）。
具体后果：索引里是 `顺延到`，用户搜 `顺延` 匹配不上。
**现有 BM25 有完全相同的问题**，只是从来没被测过。

⚠️ 第一版测量把它夸大了：先量的是"查询词有多少不在某库索引里"得出 41%，
但那混淆了"分词器分歧"与"语料本来就没这个词"。重做成对同一批文本双跑才干净。

**迁移期刻意不修**，并把现状钉成测试
（`TestTokenizerMismatchIsFaithfullyReproduced`，断言的是"现状是坏的"）。
修分词会同时改变检索结果，与换存储引擎两个变量一起动就无法归因。

**2026-08-26 已单独修完**，那组"断言现状是坏的"测试已按约定整组删除，
换成正向断言 `TestIndexTokensCoverQueryTokens`。实现落在
`src/core/tokenization.py`（索引侧与查询侧唯一的分词定义处）。

三点值得记住，因为它们改变了这一节原本的判断：

1. **上表被本次测量修正了一处。** "只有索引侧 41 词" 里有相当一部分是
   `QueryProcessor` 的 `max_keywords=20` 截断造成的 —— 把整段 chunk 正文
   （而不是一句查询）喂给关键词抽取器才会触发，**真实查询不会**。
   真正影响检索的只有反方向那一半："只有查询侧" 的单字与数字，
   它们在索引里根本不存在，查询永远命中不了。
2. **`顺延到` vs `顺延` 这个例子跟"两侧不一致"无关。** 两侧都调
   `jieba.lcut` 也照样中招 —— jieba 精确模式对同一串字在不同上下文给出
   不同粒度。**"把两个分词器统一起来"修不掉它**，修法是索引侧改用
   搜索引擎模式（`cut_for_search`）产出子词。这是两个独立缺陷。
3. **契约不是"两侧输出相同"，是"索引侧 ⊇ 查询侧"。** 消融实测
   （`scripts/ablate_tokenizer_alignment.py`，mmarco 100 条人工标注）：
   统一到索引侧那一边（丢单字）recall@5 比现状还低 1 个点、且有 2 条查询
   词条数归零；统一到"索引侧更全"这一边 recall@10 83.0% → 85.0%。

代价：BM25 JSON 索引整体 1.42x（mmarco 单库 2267KB → 3398KB，
postings 15,919 → 25,696）。这是 P0 第 2 条盯着的东西，引用时要一起报。

### 两处实施中的设计修正

1. **业务库 index 名去掉 `{org}`**：collection 名在 `org_collections` 表里已全局
   唯一，拼上 org 会在"库改归属"时被迫改 index 名（等于重建整个索引）。
   企业边界仍由 `_org_owned_collections()` 收敛，隔离强度不变。
2. **影子写做成模块级函数而不是 `Pipeline` 的方法**。挂成方法时
   `test_pipeline_progress.py` 里的鸭子类型假对象直接红了——它只带需要的属性
   然后当 `self` 传给真实流水线，**任何新增的 `self.` 方法都会打断它**。
   给假对象补方法能让测试变绿，但下次加方法又会红一遍。
   参数显式化同时让这段逻辑自己可测。

### `conv_*` 与 dense 的处理

- `conv_*` 走同一条 `IngestionPipeline`，所以影子写天然覆盖——但必须**路由到
  `conv_{org}` 共享 index**，否则就是一对话一 index 的 index explosion。
  `org_id`/`owner_user_id` 从端点透传（那里 `_require_conversation_owner` 已校验），
  **缺任一个就让影子写显式失败**：写进去但没有 owner 字段 = 查询时 filter
  匹配不到，表现为"上传成功但检索不到"；将来若放宽 filter 更会变成所有人可读。
  **失败比脏数据安全。**
- dense 向量随影子写一起入 `knn_vector` 字段（768 维），存量迁移也一并带上。

  `pytest tests/integration/test_opensearch_store.py -q` 应 15 passed；

### 灰度开关

| `RAGENT_OPENSEARCH_READ` | 行为 |
|---|---|
| 不设 / `off`（默认） | 全部走旧链路。**这是回滚开关**，出问题改回 `off` 即可，不必回滚部署 |

**默认关闭且支持白名单是刻意的。** 切读是本次迁移唯一改变生产检索行为的步骤，

⚠️ 白名单是**精确匹配**，不做前缀或通配。模糊匹配在这种开关上危险：
写错一个字符就可能把一批本不该切的库带进去，而症状（检索结果变了）
不会立刻被发现。有测试钉住 `mmarc` 不匹配 `mmarco`。

新增 `OpenSearchSparseRetriever` / `OpenSearchDenseRetriever`，

cross-encoder 重排**全部复用**，符合 §4 定的收窄范围。

这不违反 §1 那条"不做适配层"：对齐的是**返回契约**（`RetrievalResult`），
不是把 OpenSearch 塞进 `BaseVectorStore` 那种会掩盖它原生能力的抽象。

回归保护：`test_opensearch_read_switch.py::TestRetrieverSignaturesMatchLegacy`

### 小数据量下 OpenSearch 更慢，是预期的

最大的库 604 条，HTTP 往返 + JSON 序列化的固定开销盖过收益。
与 SQLite/JSON 那次交叉点分析同一个道理（实测 3000 块时才反超）。
**拿"现在更快"当切读理由是错的**；切读买的是"数据长大后不崩"，
以及尾延迟更稳（p95 快 4 倍这一条现在就成立）。

### 两处测量方法的错误，已修（值得记，因为它们都会给出错误结论）

1. **从文件名瞎推 collection**：把 `golden_test_set_v2.json` 推成库名 `v2`，

2. **没预热，把冷启动算进延迟**：第一版报"p95 28.7 秒、OpenSearch 慢 18.9 倍"，
   **是假结论**。每线程首次查询 7–10 秒全花在加载 reranker/embedding 模型上，
   两条路径都一样。真实稳态差距 1.9 倍。

### 一个尚未完全解释清楚的数字

模拟的挂钟（旧 54.8s vs 新 113.3s）与 p50/p95 对不上。

而模型加载持 GIL、会互相串行化。**但这只解释了一部分，没有完全对上。**
不影响切读判断（决定切不切看的是每请求延迟，不是这个脚本的总耗时），
但**记在这里，不要当成已经查清楚了**。

## 16. 端到端验证与 conv_ 读路径（2026-08-26）

### 端到端把两个检索层测不出来的 bug 顶了出来

| | 通过 / 失败 |
|---|---|
| 旧链路 | 15 / 2 |
| **修复前新链路** | **4 / 13** ← 大回退 |
| 修复后新链路 | 15 / 2，**失败用例与旧链路完全相同、零新增** |

**bug 1：`metadata` 只带了两个字段。**
`HybridSearch` 的 `metadata_filter_post=True` 会在 RRF 融合**之后**再按 metadata
过滤一次。`_to_results` 第一版只放 `source_path`，于是层次化收窄传下来的
`{"source_ref": [...]}` 匹配不到任何东西，**融合结果被整片丢掉**。

⚠️ **这个 bug 的隐蔽程度值得单独记**：`store.search_kb` 带同样 filters 直接查
返回 2 条，经过 `HybridSearch` 变成 0 条。检索层、15 条单测、直连查询**全是绿的**。
只有走完整链路才暴露。

修法是 `_hits` 返回完整 `_source`（去掉 content/content_raw/embedding），
retriever 直接用，**不在中间层另挑字段**。

**bug 2：mapping 漏了 `source_ref`。** 同一条收窄链路上的另一个洞。
顺带修：过滤值是**列表**时必须用 `terms` 而不是 `term`（收窄传的就是多份文档
的列表），用 `term` 匹配列表同样静默返回空。Chroma 侧有对应处理（`$in`），
它的注释里也记着这个真实案例。

**bug 3：OpenSearch 写完不立即可查。** 实测写入后立即 0 条、+0.5s 仍 0 条、
+1.5s 才查到（默认 1 秒刷新间隔），而旧链路写完立即可查。
对本项目是实打实的体验回退：用户往对话里传一份文档紧接着问，会得到"没找到"。
改用 `refresh="wait_for"`（等下一次自然刷新，不像 `refresh=True` 那样强制刷新
整个 index、高频摄入时代价很大）。

### `conv_*` 读路径

`user_id` 从 workflow state（`app.py` 放进去的已校验 token 身份）一路透传：
workflow 4 处 `execute` 调用 → `execute` → `_execute_local_single` /
`_execute_local_multi` → `_ensure_initialized` → `_build_hybrid_search_for`。
`org_id` 由 `execute` 内部已有的 org 解析提供。

⚠️ **缺 `org_id`/`user_id` 时回退旧链路，不是"不过滤地查"** ——
不过滤会把同企业其他用户的对话文档一起返回（越权）；回退最多是这次没用上新后端。
retriever 内部另有一层 `assert` 兜底。
