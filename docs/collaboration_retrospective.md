## §1 每周自查清单

每周或每个大功能结束后过一遍，勾不上就是信号。

**需求侧**
- [ ] 有没有用"修改一个BUG"的说法提出过**设计变更**？
- [ ] 新增的需求有没有写验收标准？
- [ ] 有没有做大方向转向？转之前问过"会作废什么"吗？
- [ ] 有没有关键决策是口头拍板、没落到 `CLAUDE.md` 的？

**过程侧**
- [ ] 有没有两个会话同时改同一个仓库？
- [ ] 有没有发单字"继续"让 AI 无监督连续改代码？
- [ ] 最后一次提交是什么时候？现在多少脏路径？单次提交超过 15 个文件了吗？

**产出侧**
- [ ] 这周的测试/探测脚本，落进仓库了吗？还是又丢在临时目录？
- [ ] `docs/` 的状态标记跟实际实现还对得上吗？
- [ ] 标着"临时/上线前删除"的代码，又活过了一次提交吗？
- [ ] 这周改的代码，有一行自动化测试覆盖吗？

**目标侧**
- [ ] 现在能回答"什么算做完"吗？
- [ ] 这周是在"往深处钻"还是"往宽处铺"？比例合理吗？
- [ ] 有没有已发现但停在"写了文档就结束"的高危项？

## §2 好的开发流程长什么样

### 判断标准：不是"不犯错"，是"错误多快被发现"

复盘里最贵的错误是那次 36 小时的架构往返（角色↔知识库拆了又合）。
**它贵不在犯了错，而在错了 36 小时才被发现。**

对照 2026-08-25：JWT 的 fail-fast 一开始被写成 import 时抛异常，这是个设计错误——
但它在跑第一个测试时就崩了，两分钟内改掉。同样是犯错，代价差四个数量级。

> **流程该投入的方向不是"想得更周全"，是"更早撞墙"。**

### 五根支柱

每根支柱对应 §3 里一条因果链的断点。

#### 支柱一　共识要有沉淀层

最刺痛的证据：你 8-18 亲自提出的"外部知识库工具化"架构，5 天后自己问"你说的委托是什么意思"。
**这不是记性问题，是这个决策从来没被写进一个你会重新看到的地方。**

- 有**唯一事实来源**，每个会话开始必读（现在是 `CLAUDE.md`）
- 决策记录只要三行：**决策 / 理由 / 作废了什么**
- 区分**改行为**和**改名词**——判据见 §4

写在哪里比写多少重要。迁移脚本 docstring 里的决策日志质量很高，
但复盘评价是"**散落在 `scripts/` 里没人会去读**"——写在错的地方等于没写。

#### 支柱二　先定义"完成"，再开始做

「企业管理员能管知识库」被报 **13 次、跨 5 天**，每次都当新 bug 报，
**从没被当成"这条需求还没验收通过"跟踪**。

- **项目层面**先答：交付给谁 / 怎么用 / 什么算做完
  （2026-08-25 答完这三题，直接炸出**三条纯读代码审不出来的 P0**——
  它们只在特定规模、数据量、更新节奏下才成为问题）
- **需求层面**每次交付回答三句：验收怎么做 / 回归怎么保 / **什么没做**

第三句最容易跳过也最重要。此前的安全测试报告写得很详细，
**但从没说过"认证层、并发、密钥管理没测"**——而两个 P0 就躺在没测的范围里。

#### 支柱三　验证网要能证明自己有效

写完并发隔离测试 9 条全绿——**但测试通过不等于测试有效**。
于是又用旧实现跑同一套场景：

```
请求 A 实收 []                          ← 空屏
请求 B 实收 [B1, A1, B2, A2, B3, A3]    ← 混进了 A 的全部内容
```

这才证明测试抓得到那个 bug。不做这一步，可能交付的是一组新旧实现下都通过的废测试。

配套两条：**并发缺陷必须用并发方式验证**；
**注释里声称的不变量不得当作依据**——那条"多个并发请求互不串"的错误注释，
审计认为正是 P0 长期没被发现的原因。

#### 支柱四　小步存档，保住回退能力

最后一次真实提交停在 8-22，两整天工作裸奔在工作区（48 个脏路径），
单次提交达 70 文件 / +10,208 行。

**回退粒度变成"一整天的三件事"，等于没有回退能力；
这反过来又强化了"旧代码不敢删"，双实现越积越多。**

这个项目自己证明过能做好：8-13~8-14 那 12 次提交是标杆级的，
消息写根因不写现象（如 `Fix long-term memory: never wired up, three compounding bugs`）。
分界点很清晰——08-17 进入"企业化"后立刻退化。**不是能力问题，是节奏一快就丢了纪律。**

#### 支柱五　推断和事实要分开

判断分三种成色，每次都要标清楚：

| 成色 | 例子（2026-08-25） |
|---|---|
| **已实测确认** | 旧版本片段残留——真跑摄入，库里两个版本都在 |
| **推断，待验证** | BM25 索引真实数据量下达 GB 级——外推自 20 块样本 |
| **假设** | 日活 30%、每人每天 4 次 |

汇报口径同理：**已验证通过 / 已跑通 / 已实现但未验证**。

衍生原则——**先量再优化**。复盘原话："微调 1.5b 省了 5 秒，
而检索侧每查询重建的开销从未被处理"。力气花在了看得见成功信号的地方，
不是收益最大的地方。

### 什么时候可以不遵守

流程有成本。复盘保留了"高速闭环"这个优点，没有否定它——
**问题从来不是太快，是快的那部分没有任何东西沉淀下来。**

好流程不是把所有改动都变慢，是**识别出那 5% 会产生长期后果的改动，只给它们加闸**。

## §3 规则是怎么来的：四条因果链

一句话结论：**这 12 天形成的是「口述需求 → 立刻改代码 → 手工点页面验证 → 不对再口述」的高速闭环。
单轮效率很高，但这个闭环没有任何一环会产生可跨会话继承的共识——
需求活在聊天框、验证活在浏览器、共识活在上下文窗口，三样都是易失的。**

| 链 | 因果 | 断点 |
|---|---|---|
| **A** | 口述需求（中位数 28 字）以"改BUG"口吻提出架构变更 → AI 进"修 bug 模式"60 秒开工 → 7 天 4 次权限模型迁移 → 旧路径不敢删 → **双实现并存** | 支柱一 |
| **B** | 验收＝"我点一下看看" → AI 没理由写测试（12,200 行零测试）→ 只验"这次报的点" → **同一 bug 复活 13 次** | 支柱二、三 |
| **C** | 无 `CLAUDE.md`、无决策日志 → 22 个会话各自 grep 重建认知（占工具预算约 1/4）→ 新会话看不到旧决策的理由 → **不存在"当前架构"，只存在"最近一次会话留下的状态"** | 支柱一 |
| **D** | 只主动 commit 过 4 次 → 单次提交 70 文件混装三件事 → **回退在物理上不可行** → 强化"旧代码不敢删"（回到链 A） | 支柱四 |

**实用度缺口的总根源**：12 天里从未回答"交付给谁 / 怎么用 / 什么算做完"。
验收语一律是"完成了吗"——**验收的是 AI 手上的活干完没有，不是功能达标没有。**

## §4 各自要改什么

### 你这边（按优先级）

| 级别 | 问题 | 改进动作 |
|---|---|---|
| **P0** | 用"修改一个BUG"提出**架构变更** | 判据：**这句话会不会导致 `scripts/` 里多出一个 migration 脚本？** 会 → 改口为"我想改一个设计：现在是 X，想改成 Y，先告诉我影响面" |
| **P0** | 只有"完成了吗"，没有验收标准 | 提需求时带一句：**谁用什么账号，点哪里，看到什么，算通过** |
| **P0** | 关键建模决策一句话拍板不落文档 | 写三行进 `CLAUDE.md`：决策 / 理由 / 作废了什么 |
| P1 | 战略级转向不问影响面（3 次，每次推翻数天工作） | 转向前固定问："**这会作废掉哪些已完成的工作？大概多少代码？**" |
| P1 | 多会话并发改同一仓库（15 对重叠 >30 分钟） | 学习类会话可并行，**同一时刻只允许一个会话有写权限** |
| P1 | "继续"型无监督放行（13 次） | 额度将尽时改说："**列出剩余步骤，什么都别改**" |
| P1 | 从不主动要求提交（12 天仅 4 次） | 每完成一个可描述的功能就提交，单次 ≤ 15 文件 |
| P2 | 改行为和改名词用同样的粒度 | 见 §2"什么时候可以不遵守" |

### AI 这边（三类，干预手段完全不同）

#### 🟠 A 类：你的表达方式直接触发 —— **你改，收益立竿见影**

| 问题 | 怎么触发的 |
|---|---|
| 接受"BUG"框定，60 秒开工不做设计确认 | **关键证据**：同一个 AI 在 8-23 12:05 面对反向请求时做对了（复述理解→给方案→列影响面→要授权）。**能力有，差别只在那次被包装成了"BUG"** |
| 报喜口径滑移（"修复"用在只观察到现象变化上） | 没有验收标准时只能用模糊词 → 要求分三档汇报 |
| 无监督连续改代码 | 11 次"继续" |

#### 🟡 B 类：你的环境放大了，但根子在 AI —— 你改能减轻，不能根治

- **异议密度极低**：1,724 个回复只有 9 处提异议，且全是战术级，**没有一处是"这与两天前的设计冲突"**
- **追问不足**：只有 6% 的回复以问句结尾（需求中位数才 28 字）
- **临时脚手架固化**：你说了"临时、上线前删除"，但 AI **把它提交进了主干，只靠一行注释保证不上线**

#### 🔴 C 类：完全是 AI 的问题 —— **你改说话方式没用，只能靠 `CLAUDE.md` 焊死**

这一类最重要，别误以为"我再说清楚点就能避免"。

| 问题 | 为什么不是你的错 |
|---|---|
| **从未建议创建 `CLAUDE.md`** | 你不可能知道要主动要求这个基础设施 |
| **测试脚本写完即弃**（`jailbreak_test.py`/`latency_probe.py` 全库无结果） | **两份报告的数字至今无人能复现，包括你** |
| **文档写完即腐烂**（状态标记与实际相反） | **标着"已实现"的废弃架构文档，比没有文档更危险** |
| **写下与实现相反的注释** | 纯技术错误，与你怎么说话无关 |
| **零测试且从未提出** | 你没说"不用写测试"，AI 也从没说过"这里需要测试" |

## §5 做得好的，别一起改掉

1. **8-13~8-14 的提交纪律是标杆级的**——一次一件事、消息写根因。**你已经证明过自己会做。**
2. **注释记录"为什么"且附实测数据**——`MIN_RELEVANCE_SCORE=0.1` 的依据（噪音稳定在 0.03 以下、真相关稳定在 0.13 以上，两簇间有断层）。业界对标曾质疑这个阈值量纲错误，**核对后确认是对的，靠的就是这条注释**。
3. **迁移脚本 docstring 本身就是决策日志**——完整记录了谁在哪天说了什么、边界情况怎么处理。问题只在于**没人会去 `scripts/` 里读**，应上浮到 `CLAUDE.md`。
4. **迁移全部幂等可重跑** + `--dry-run` + "老列不删、回滚只需不切读路径"。
5. **对"本地小模型会编造"有系统性防御**——三处关键短路统一是"固定模板 + 完全跳过 LLM"。
6. **性能优化有数据且自我限制结论范围**——"这个结论只对这一个特定任务成立，其他子任务没验证过"。审计评价：这种自我限制**很少见**。
7. **两次范本级沟通**：8-23 12:05 的设计确认、8-24 10:22 的自我纠偏。**应该是默认流程，不是偶发。**
8. **安全测试方法论正确**——区分"模型嘴上说了什么"/"是否真检索到数据"/"与源码逐字比对"，比多数人严谨。**可惜脚本没留下来。**

## 一句话总结

- **你这边最值钱的改变**：区分"改行为"和"改名词"。判据是——**这句话会不会导致 `scripts/` 里多出一个 migration 脚本。**
- **AI 这边最值钱的改变**：动手前先验证前提是否与既有设计冲突，而不是接受给定的框定就开工。
- **两边都管不了的部分**：靠 `CLAUDE.md` 焊死。**这个项目缺的不是能力，是约束层。**
