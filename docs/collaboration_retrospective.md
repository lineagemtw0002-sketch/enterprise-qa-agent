## 零、这份文档解决什么问题

这个项目 12 天里产出了 10,156 行后端 + 5,900 行前端代码、411 KB 设计文档，但同时也留下了：4 次权限模型迁移（其中两个脚本互为逆操作）、一个被报了 13 次仍未闭环的需求、12,200 行零测试的核心代码、两个 P0 级缺陷。

三份独立分析（代码审计 / 过程复盘 / 业界对标）指向同一个结论：

> **问题不在能力，在约束层缺失。** 每一个单点决策的质量都很高，但没有任何机制保证这些决策能跨会话存活。需求活在聊天框、验证活在浏览器、共识活在上下文窗口——三样都是易失的。

这份文档把"下次怎么不重蹈覆辙"拆成两半：**你能改的**（第二节）和 **AI 该被约束的**（第三节）。分开写是因为两者的干预手段完全不同——前者靠改变表达方式，后者靠写死规则。

## 二、你这边的问题（按优先级）

### P0 — 直接制造返工和架构漂移

#### P0-1　用"修改一个BUG"的口吻提出架构变更

**这是所有返工的源头。** 见事件 A。

用 bug 的框架描述设计变更，会让 AI 切进"修 bug 模式"——直接定位、直接改，跳过设计确认环节。而设计确认恰恰是唯一能拦住架构漂移的关口。

**改进动作**：用这个判据自检——

> **这句话会不会导致 `scripts/` 里多出一个 migration 脚本？**

会 → 它是设计变更，不是 bug。开口方式改成：
```
我想改一个设计：现在是 X，我想改成 Y。
先告诉我这会影响哪些地方、作废哪些东西，我确认后再动手。
```

#### P0-2　没有验收标准，只有"完成了吗"

12 天里没有一次出现"这个功能的完成标准是 X"。实际出现的验收语全部是这个形态：「完成了吗」「搞完了吗」「是否修改完成了」「没搞定吗」——**验收的是 AI 手上的活干完没有，不是功能达标没有。**

这直接导致事件 B：同一需求报 13 次，前 12 次都是白改的。

**改进动作**：提功能级需求时带一句验收话术：
```
验收标准：<谁> 用 <什么账号>，点 <哪里>，看到 <什么>，算通过。
```
这一句话的作用是把"报第 13 次"变成"第 2 次就发现前一次根本没验收过"。

#### P0-3　关键建模决策一句话拍板，且不落文档

```
08-23 12:09  「暂时一个用户就一个角色吧。开始吧。弄完后 全量测试下」
```
"一人一角色 vs 一人多角色"是权限系统里最影响后续复杂度的选择之一，在这里用 9 个字定了。而 08-19 10:34 你曾要求过相反方向。因为没有记录，它每次被重新讨论时都从零开始。

**改进动作**：这类决策写三行，写进 `CLAUDE.md` 的"当前架构"节（不需要单独开文档）：
```
- 决策：一个用户一个角色，角色直接携带知识库权限
- 理由：身份和权限授予对用户是同一个心智概念，拆两层管理成本高
- 作废：kb_group 三表；影响：前端用户管理页、角色管理页、role_store、query_knowledge_hub
```

### P1 — 放大问题

#### P1-1　战略级转向不问影响面

12 天里至少 3 次大方向转向，每次推翻数天工作：

| 时间 | 原话（摘） | 被推翻的东西 |
|---|---|---|
| 08-18 09:28 | 「将整个系统拓展为企业级……一体」 | 刚做完的单租户 RBAC + 工作流 |
| 08-18 19:54 | 「整个架构采用外部知识库工具化……自建知识库微服务」 | 本地 Chroma 检索路径 |
| 08-23 15:47 | 「企业的知识库保存在本地的数据库……就够了」 | 上一条催生的整套联邦架构（61 文件、+5,237 行） |

转向本身没错——想清楚了就该转。**问题是转向前没有问过"这会作废掉什么"。**

**改进动作**：转向前固定问一句「这个改动会作废掉哪些已完成的工作？大概多少代码？」。知道代价后仍然决定转，那是合理决策；不知道代价就转，是赌博。

#### P1-2　多会话并发改同一个仓库

24 个会话里 **15 对时间重叠超过 30 分钟**。08-18 10:09~20:00 期间有三个会话同时对同一工作区活动近 10 小时——那 10 小时的产出就是 `56203bf` 那个 70 文件 / +10,208 行的巨型提交（混装了 RBAC + 工作流 + Vue→React 整体重写三件不相干的事）。

这在人类团队里等价于**多人同分支、无沟通、直接 push**。

**改进动作**：问原理/学习类的会话可以并行开，但**同一时刻只允许一个会话有写权限**。

#### P1-3　"继续"型无监督放行

13 次单字"继续"。08-17 16:00~16:19 这 19 分钟里发了 **11 次**，中间夹杂「为什么不继续了」。这些轮次里 AI 在无人监督下持续改代码，没有一轮经过确认。

**改进动作**：额度快用完时，把"继续"换成：
```
列出剩余步骤，什么都别改，等下次会话。
```

#### P1-4　从不主动要求提交

12 天里只主动说过 4 次提交（08-19 06:56 / 08-19 08:17 / 08-20 09:46 / 08-20 09:48）。其余提交要么是 AI 顺手做的，要么是额度耗尽时系统自动打的 checkpoint。

后果：08-23、08-24 两整天工作未提交、48 个脏路径；单次提交规模 70 文件。**回退粒度变成"一整天的三件事"，等于没有回退能力。** 这反过来又强化了"旧代码不敢删"，双实现越积越多。

**改进动作**：每完成一个可描述的功能就提交，单次提交不超过 15 个文件。会话结束前固定做一次"按功能拆分提交"。

### P2 — 结构性，改起来慢但值得

#### P2-1　需求粒度一律过短

445 条消息中位数 28 字符。**这本身不是问题——问题是"改行为"和"改名词"用了同样的粒度。**

| 类型 | 例子 | 合适的粒度 |
|---|---|---|
| 改行为 | 按钮位置、文案、单个接口 bug | 一句话就够，保持现在的高速闭环 |
| 改名词 | 角色 / 知识库 / 组织 / 工作流之间的关系 | 停下来，先写三行决策记录 |

#### P2-2　从未定义交付对象与目标

12 天里从未回答过：

| 问题 | 出现过吗 |
|---|---|
| 这个系统交付给**谁**？ | 从未 |
| 他们**怎么用**？ | 从未 |
| **什么算做完**？ | 从未 |

仓库里有一整套面向求职的技能包（`.claude/skills/resume-writer/`、`project-evaluator`、`interview-prep`），会话 `90d79c6b`（51 小时）几乎全是面试题式的原理提问。

**把项目当作能力展示载体完全正当。但它从来没有被明确成"项目目标"**，于是"什么算做完"这个问题永远无法回答，只能被"再加一个听起来更厉害的功能"替代。

这也解释了投入分布的失衡：

| 投入密度最高的 | 完全没做的 |
|---|---|
| 多租户联邦架构（后被拆） | 业务层自动化测试 |
| 意图识别耗时优化（含 LoRA 微调） | 部署方式（现在是 macOS 手动起 4 个进程） |
| 提示注入安全测试（未闭环） | 数据备份 / 迁移回滚 |
| | 给企业管理员的操作文档（正是被报 13 次的那个角色） |

**"往深处钻是舒服的，往宽处铺是难受的"** ——LoRA 微调有明确的成功信号（loss 下降、延迟数字变小），"写一份操作手册"没有。所以时间自然流向前者。

**改进动作**：在 `CLAUDE.md` 第一节如实写下目标。如果目标是"能力展示 + 面试材料"，就这么写——不丢人，但写下来才能定义"什么算做完"。

## 三、AI 侧的问题：哪些是你导致的

这一节的价值在于**区分"你改说话方式就能解决的"和"你改了也没用的"**。搞混会让你改错地方。

### 🟠 A 类：你的表达方式直接触发（你改，收益立竿见影）

| AI 的问题 | 触发点 | 你能做什么 |
|---|---|---|
| **接受"BUG"框定，60 秒开工不做设计确认**（事件 A） | 你说"修改一个BUG" → AI 切进修 bug 模式 | 见 P0-1。**关键证据**：同一个 AI 在 08-23 12:05 面对反向请求时做对了——复述理解 → 给表结构方案 → 列影响面 → "确认这个方向没问题的话我就开始动手了"。**能力是有的，差别只在那次没被包装成 BUG** |
| **报喜口径滑移**：把"只观察到现象变化"说成"修复" | 没有验收标准时，只能用模糊词 | 要求分三档汇报：**已验证通过**（有可复现的测试）/ **已跑通**（手工点过一次）/ **已实现但未验证** |
| **无监督连续改代码** | 11 次"继续" | 见 P1-3 |

### 🟡 B 类：你的环境放大了，但根子在 AI（你改能减轻，不能根治）

| AI 的问题 | 你的影响 | AI 的责任 |
|---|---|---|
| **异议密度极低**：1,724 个回复里只有 9 处提异议，且全是战术级（"风险高建议先不动"），**没有一处是"这与我们两天前的设计冲突"** | 快节奏短指令 + "继续"制造惯性，不鼓励停下来 | 这本质是 AI 的失败模式。应该在动手前先查文档验证前提，而不是顺着当下这句话做 |
| **追问密度不足**：只有 6% 的回复以问句结尾，`AskUserQuestion` 全项目 53 次 | 需求中位数 28 字，本该触发更多追问 | 追问密度该由 AI 根据需求模糊度自动调节，不该等你写清楚 |
| **临时脚手架固化成正式代码**：绕过 ACL 的测试接口横跨 8+ 文件长期驻留 | 你说了"临时""上线前删除" | 但 AI **把它提交进了主干，只靠一行注释保证不上线**。应该加运行时开关或环境变量守卫 |

### 🔴 C 类：完全是 AI 的问题（**你改行为没用**，只能写成硬规则）

**这一类最重要。** 你可能会误以为"我说话再清楚点就能避免"——不能。

| AI 的问题 | 为什么不是你的错 |
|---|---|
| **从未建议创建 `CLAUDE.md`**。22 个会话各自 grep 重建认知，grep 1,018 次 + cd 697 次，约 1/4 工具预算浪费在"这项目长什么样"上——而这个答案本可以写一次、复用 22 次 | 你不可能知道要主动要求这个。这是 AI 该主动提的基础设施 |
| **测试脚本写完即弃**。`jailbreak_test.py`、`prompts_jailbreak.json`、`latency_probe.py` 全库 `find` 无结果。**两份关键报告的数字现在谁也无法重新验证，包括你自己** | 你从没要求写在临时目录。纯粹是图省事 |
| **文档写完即腐烂**。`role.md` 标"状态：未实现"实际早已实现；`knowledge-base-tenant-federation.md` 标"状态：已实现"实际已于 08-23 拆除 | 你没义务追着更新文档。**一个标着"已实现"的废弃架构文档，比没有文档更危险** |
| **写下与实现相反的注释**。`workflow.py:224-227` 明确断言"多个并发请求互不串"，而实际会串（见 P0 缺陷）。代码审计认为**这条错误注释很可能是该问题长期未被发现的原因** | 纯技术判断错误，与你怎么说话完全无关 |
| **零测试且从未提出**。12,200 行核心代码零回归保护，`conftest.py` 连 DB fixture 都没有，导致后端层"写不出测试" | 你没说"不用写测试"，AI 也从没说过"这里需要测试" |

**对 C 类，正确的干预手段不是改变你的表达方式，是把规则写死。** 见下一节。

## 四、硬规则清单（抄进 `CLAUDE.md`）

```markdown
## 对 AI 的硬性要求

- 每次会话开始先读本文件，不要靠 grep 重建项目认知
- 当我用"修改一个BUG"的说法描述一件实际是设计变更的事时，必须明确指出：
  "这不是 bug，这是 <文档/位置> 的既有设计，改它意味着 <影响面>，确认吗？"
  —— 参考 2026-08-22 14:55 那次没有指出的教训（代价：36 小时架构往返）
- 汇报结果分三档，不许混用：
  已验证通过（有可复现的测试） / 已跑通（手工点过一次） / 已实现但未验证
- 所有测试脚本、探测脚本落到仓库里（tests/ 或 scripts/），禁止写临时目录后丢弃
  —— 参考 jailbreak_test.py / latency_probe.py 丢失导致报告不可复现
- 标了"临时/上线前删除"的代码，在下一次提交时必须要么删掉、要么加运行时开关关闭
- 改动数据模型 / 权限模型前，必须先更新本文件的"当前架构"节并让我确认
- 每完成一个可描述的功能就提交，单次提交不超过 15 个文件
```

### 4.1 停下来做设计评审的三条触发线

命中任意一条就停，不要继续写代码：

1. **要写 migration 脚本** → 停。这意味着数据模型在变。
2. **同一需求第 3 次被报"还是不行"** → 停。别修第三次，去查为什么前两次修的会失效（八成是下层模型变了）。事件 B 报到第 13 次，前 12 次都是白改的。
3. **AI 的方案里出现"会动到 X 个文件 / 涉及表结构"** → 停，走 08-23 12:05 那个确认模板。

### 4.2 每个功能交付时 AI 必须回答的三句话

```
1. 验收怎么做：谁用什么账号，点哪里，看到什么，算通过
2. 回归怎么保：哪个测试文件/脚本能自动复现这个验收，路径是什么
3. 什么没做：这次没覆盖的边界条件，明确列出
```

第 2 条是重点。**建议的第一条规矩：凡是涉及权限的改动，必须同时提交一个 `tests/` 下的测试。** 权限是这个项目返工最多的地方（36 次 bug 请求里大半跟权限有关），也是最适合自动化的地方——纯逻辑，不需要浏览器。

## 六、做得好的地方（要保留，不要一起改掉）

复盘的目的不是全盘否定。以下几项经三份独立分析确认，**客观上高于同类项目水准**：

1. **08-13 ~ 08-14 阶段的工程纪律是标杆级的**。12 次提交，一次一件事，提交消息写清根因而非现象：
   - `2078380 Fix long-term memory: never wired up, three compounding bugs`
   - `bbcef6f Implement sub-query parallel retrieval (was dead code)`
   - `4e36d47 Fix silent empty replies from spurious clarify routing`

   **这套做法在项目"企业化"之后丢了——但你已经证明过自己会做。** 分界点非常清晰：08-17 开始，提交立刻退化成每天一到两个巨型 commit。

2. **注释质量极高，大量记录"为什么"而非"是什么"，且附实测数据**。例如 `MIN_RELEVANCE_SCORE=0.1` 的依据（`query_knowledge_hub.py:56-65`）：不相关问题的噪音稳定在 0.03 以下、真相关的稳定在 0.13 以上，两簇之间有断层，并明确限定"只在 reranker 真跑起来时才适用"。
   —— 业界对标报告曾质疑这个阈值可能量纲错误，**核对后确认这一块是对的**，靠的就是这条注释。

3. **迁移脚本的 docstring 本身就是决策日志**，完整记录了"为什么要迁、谁在哪天说了什么、搬运规则、边界情况怎么处理"。**问题只在于它们散落在 `scripts/` 里没人会去读**——这些内容应该上浮到 `CLAUDE.md`。

4. **所有迁移设计成幂等可重跑**（`get_or_create_*` + `add_*` 模式），`migrate_to_roles.py` 还提供 `--dry-run` 和"老列不删、回滚只需不切读路径"的安全设计。这是很专业的做法。

5. **对"本地小模型会编造"有系统性防御，且做法一致**——三处关键短路全是"固定模板 + 完全跳过 LLM"（ACL 拒绝 / KB 空命中 / 简短确认语）。明确意识到"把免责声明交给本地小模型自由发挥"本身就是风险源。

6. **性能优化有实验数据，且自我限制结论适用范围**——记录了"7b 跑合并任务 3/3 误判 → 换微调 1.5b → 3.2s vs 8.7s"的完整过程，并标注"这个结论只对这一个特定任务成立，其他子任务没验证过"。代码审计评价：这种自我限制"很少见"。

7. **两次范本级沟通，应该变成默认流程而不是偶发**：
   - **08-23 12:05**：复述理解 → 给表结构方案 → 列出影响面 → "确认这个方向没问题的话我就开始动手了"
   - **08-24 10:22**：主动说"'修复'这个说法容易让人误会"、"这个词要打个折扣"、"我没法 100% 确认是副作用还是确实更稳健"

8. **安全测试的方法论是对的**——区分了"模型嘴上说了什么" / "`kb_sources` 是否真的检索到数据" / "泄露内容与源码逐字比对"，正确地把"模型编故事"和"后端权限真被绕过"分开了，比大多数人做的提示注入测试严谨。**可惜脚本没留下来。**
