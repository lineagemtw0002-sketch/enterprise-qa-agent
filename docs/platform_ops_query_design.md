## 1. 需求原文

平台运营方超级管理员要能查这四个问题：

| # | 问题 | 性质 |
|---|---|---|
| Q1 | 今天哪个企业用的 token 最多 | 跨企业聚合 |
| Q2 | 今天哪个用户问了问题最多 | 跨企业聚合 |
| Q3 | 今天哪个用户问的问题没有查到资料 | 跨企业聚合 |
| Q4 | 这段时间问答过程中哪个节点消耗的时间最长，是多少 | 节点级耗时 |

原始表述是「在问答这里做数据查询」（自然语言）。**v2 改为仪表盘**，理由见 §2。

---

## 2. 为什么形态从「自然语言查询」改成「仪表盘」

### 2.1 需求本身是真实且标准的

多租户 LLM SaaS 的**按租户成本归因**是成熟问题，不是这个项目特有的。
业界有现成方案（Langfuse / LiteLLM / Portkey），典型生产架构是
「配额层 + 虚拟 key + 可观测后端 + 审计」。**所以需求要做，问题只在形态和自建与否。**

### 2.2 但业界的做法是**仪表盘 + 语义层**，不是产品内的自然语言查询

两条关键判断：

- **「在数据库上直接套一个聊天界面，没有语义层就会失败」** ——
  语义层是指标定义的集中管理（"token 用量"到底算哪些行、怎么去重、
  缺失怎么处理，定义一次、所有查询共用）。**本项目现在没有语义层。**
- **text-to-SQL 在生产里有个专门的说法：quiet failure（静默失败）** ——
  小错误不会让查询崩溃，它们返回**看似合理但错误的答案**。
  比失败更危险，**因为它是安静的**。

### 2.3 🔴 这跟 §3 实测出的数据缺陷正好撞在一起

这是 v2 换形态的**决定性理由**，不是风格偏好：

> §3.1 实测：token 覆盖率 **41.9%**，且**缺失率按企业严重倾斜** ——
> 平台运营方 313 条消息里 307 条是 NULL，token 排名反而掉到第 4。

把这两件事叠起来看会发生什么：

```
超管问「今天哪个企业 token 最多」
  → 模型生成一句语法完全正确、逻辑看起来也对的 SQL
  → 返回一个言之凿凿的排名
  → 而那个排名实际反映的是「谁的日志覆盖率高」
  → 没有任何人会发现
```

**仪表盘不会有这个问题** —— 面板上写着「覆盖率 41.9%（402/960）」的时候，
**你能看见那个 41.9%**。自然语言回答里那句"Acme 用得最多"，
把置信度、口径、缺失率**全部压平成了一个自信的句子**。

⚠️ 更要命的是**归因方向**：一个自然语言的错误回答，用户会归因为"模型答错了"，
于是去调提示词；而**真正的病根在埋点覆盖率**，调提示词永远修不好它。
仪表盘把缺陷摆在明面上，反而会**推动去修埋点**。

### 2.4 结论

**先做仪表盘（把数字和它的可信度一起显示），埋点补齐后再考虑要不要加自然语言层。**
顺序不能反 —— 在一个 41.9% 覆盖率的数据源上先套自然语言，
等于把已知的数据缺陷藏进一个自信的句子里。

## 3. 数据可用性实测（v1 结论，原样保留）

**这一节决定工作量是「加个面板」还是「要先改埋点」。以下全部是 2026-08-26
对本地 Postgres 的实测结果，不是推算**（`RAGENT_POSTGRES_URL` = 本地 `ragent` 库，
实测时 `conversation_archive` 2012 行 / `audit_logs` 494 行）。

| 问题 | 结论 | 数据在哪 | 阻塞点 |
|---|---|---|---|
| **Q1 token** | 🟡 **查得出来，但答案会是错的** | `conversation_archive.total_tokens` | **覆盖率 42%，缺失率按企业倾斜** |
| **Q2 提问数** | 🟢 **现在就能答** | `conversation_archive.role='user'` + `conversations.user_id` | 仅 86% 可归属 |
| **Q3 空命中** | 🟡 **能答一半** | `audit_logs.detail->'collections' = '[]'` | 只覆盖两种空命中里的一种 |
| **Q4 节点耗时** | 🔴 **答不出来，必须先埋点** | —— 无任何持久化 | 全仓没有节点级耗时落盘 |

### 3.1 Q1 token —— 能查，但现在查出来的排名是错的

归属链路是通的：

```
conversation_archive.conversation_id → conversations.user_id → users.org_id → organizations.name
```

实测按企业聚合：

| 企业 | assistant 消息数 | total_tokens 合计 | **其中 token 为 NULL** |
|---|---|---|---|
| 测试新公司 | 243 | 251,232 | 53 |
| Acme 有限公司 | 254 | 175,846 | 118 |
| 测试审计企业 | 12 | 10,976 | 1 |
| **平台运营方** | **313** | **3,605** | **307** |
| Globex 环球集团 | 5 | 2,259 | 2 |

**看第 4 行：平台运营方消息数最多，token 却排倒数第二**，因为 313 条里 307 条是 NULL。
全局：960 条 assistant 消息只有 **402 条（41.9%）**有 token 值。

三条根因：

1. **短路路径不写 token（主因）。** `workflow.py::_generate_node` 只在真正调 LLM 的
   流式路径算 `token_usage`（`:1489`）并写 `last_turn_tokens`（`:1509`）。
   三条短路 —— 越权话术（`:1303`）、ACL 拒绝（`:1337`）、知识库空命中（`:1370`）——
   各自 `return` 的 dict **都没有这个字段**。走 `tool_subgraph` 的轮次同理。

2. 🔴 **一个独立的正确性 bug：`last_turn_tokens` 跨轮残留 → 重复计数。**
   该字段在 `schemas.py:533` 声明，**没有 Annotated reducer**，checkpointer 会把上一轮的值
   原样带到下一轮。全仓只有三处出现（声明 `schemas.py:533` / 写 `workflow.py:1509` /
   读 `workflow.py:1713`），**没有任何重置点**。
   于是：第 N 轮正常生成写入 5000 tokens → 第 N+1 轮走短路 →
   `_archive_node`（`:1713`）读到的还是 5000 → **第 N+1 轮被盖上第 N 轮的 token 数**。

   **证据强度**：`_session_node`（`workflow.py:563-570`）**显式重置了
   `tool_execution_trace`**，并在注释里写明理由——"普通字段（没有 Annotated 累加
   reducer），会被 checkpointer 原样带到下一轮"。**`last_turn_tokens` 是完全同一个
   形态，只是被漏掉了。**

   ⚠️ **这条 bug 现在就在污染线上面板**：`CostQualityDashboard.jsx`（前端「成本与质量」
   子页）展示的 `total_tokens` 正是这个字段聚合出来的。**不是"将来会有问题"，是现在正在错。**
   按 §7.1 它是 bug 不是设计变更，建议**单独修、单独提交**（§10 待确认项 O-1）。

3. **所有 token 都是估算值。** 实测 402 条有值的记录里 **402 条 `token_estimated=TRUE`**，
   即 100% 走 `workflow.py:163 _estimate_token_count` 的字符数估算（本地 Ollama 从不回传
   `usage_metadata`）。不算阻塞（估算值做**相对排名**仍有意义），
   但**面板上必须标注"预估"**。

**另一个独立缺口：133 条 assistant 消息（14%）归属不到任何企业。**
960 条里只有 827 条能跑通上面那条 join。原因是 `conversations.user_id` 有 25 行是 NULL
（`conversation_store.py:76`：加登录系统之前的历史数据），以及用户删除后的孤儿会话。
**面板必须显式显示"未归属 N 条"**，否则总量永远对不上。

### 3.2 Q2 提问数 —— 🟢 现在就能答

`role='user'` 的行就是提问，join 同上。实测：

| 用户 | 企业 | 提问数 |
|---|---|---|
| alice_acme | Acme 有限公司 | 214 |
| qa_run_company_user | 测试新公司 | 202 |
| qa_it_emp | 平台运营方 | 140 |

**四个问题里唯一一个不需要动任何埋点的。** 同样受 14% 归属缺口影响。

⚠️ 口径要先定：**"问得最多"数消息条数还是独立会话数**？两者差别很大
（546 个会话 vs 1000+ 条提问）。见 §10 待确认项 O-2。

### 3.3 Q3 空命中 —— 🟡 只能答一半，但这一半质量很好

`audit_logs` 里 `action='tool_call'` 且 `resource_type='query_knowledge_hub'`、
`detail->'collections'` 为 `[]` 的记录 = "查了但一个库都没命中"。实测 **83 条**。

**这条路比 Q1/Q2 更干净**：`audit_logs` 自带 `org_id`/`user_id`/`username`/`created_at`
（`audit_store.py:76-88`），由 `app.py::_audit_log`（`:346-372`）落库前补齐。
实测 385 条 `tool_call` 记录 **`org_id IS NULL` 的有 0 条** ——
**不需要 join，也没有 14% 缺口。**

🔴 **但只覆盖两种"没查到"里的一种。** `workflow.py:1361-1366` 的判定是
`kb_hit = any(t.get("collections") for t in tool_execution_trace if ...)`，
`not kb_hit` 有两种成因（代码注释明确写了两种都要覆盖）：

- **(a) 调了工具但没命中** → 有一条 `collections=[]` 审计 → ✅ 查得到
- **(b) think 节点判断"这问题知识库答不了"，压根没调工具** →
  **`audit_logs` 里一条记录都没有** → ❌ 查不到，**且漏多少无法估计**

⚠️ **不要用"回答正文匹配 `_KB_EMPTY_HIT_MESSAGE`"来补 (b)。** 实测该话术在
`conversation_archive` 里近似匹配只有 1 条，且那条还是考勤话术误命中。
靠回答正文做子串匹配正是 `CLAUDE.md` §5「安全复测判据自身的假阳性」踩过的坑
（命中的是回显，不是真信号）。补 (b) 需要一次小埋点，见 §6 的 I-3。

### 3.4 Q4 节点耗时 —— 🔴 答不出来，四条里唯一的硬缺口

**全仓没有任何地方持久化节点级耗时。** 逐条核实：

| 候选 | 有没有节点耗时 | 为什么用不了 |
|---|---|---|
| `trace_events`（state） | 有 `ts`，无 duration | **只活在 LangGraph checkpoint 里**，且 `app.py::_trim_checkpoints`（`:137`）每轮删旧 checkpoint |
| `_emit_trace()` | 有 start/end | **只推 WebSocket 队列**（`workflow.py:387-405`），**完全不落盘** |
| `logs/traces.jsonl` | 有 stage 计时 | **该文件当前不存在**；且 `TraceContext`/`TraceCollector` 只被 `src/ingestion/pipeline.py` 用（**摄入链路**），问答链路一次都没调用过 |
| Postgres | —— | 25 张表里没有任何 trace/span/节点耗时表 |

**现存的耗时信号只有两个，粒度都不够**：

1. **每轮总耗时** `conversation_archive.latency_ms`（`store.py:218`）——
   只有总数，**分不出 intent / retrieve / generate**。实测 673/960 有值。
2. **单个工具耗时** `audit_logs.detail->>'latency_ms'`（`subgraph.py:378`）——
   实测 `query_knowledge_hub` 362 次 avg 2467ms / max 305,842ms。
   **这是工具级不是节点级**：`intent`（`CLAUDE.md` §2 说这是最大固定开销 1.5–2.2s）
   和 `generate` 两个节点**一点数据都没有**。

⚠️ `CLAUDE.md` §2 记录的阶段构成（intent 1.5–2.2s / 检索 0.14–0.39s /
generate 1.85–12.0s）来自 `scripts/benchmark_latency.py` 的**离线基准**，
**不是线上流量，不能拿来冒充 Q4 的查询结果。**

### 3.5 一句话总结

> **1 个（Q2）现在就能答；1 个（Q1）能查但结果会误导；1 个（Q3）能答 60%；
> 1 个（Q4）完全答不出来。**
>
> **埋点是工作量大头，面板是小头。**

## 4. 自建 vs 接现成（Langfuse / LiteLLM）

⚠️ **本节的外部产品信息来自协作方提供的调研摘要与既有知识，
本轮无联网、未核实。下表标「待核实」的项在拍板前必须实际验证** ——
按 `CLAUDE.md` §7.2「注释里声称的不变量要么验证、要么标为未证实假设，不得当作依据」。

### 4.1 硬约束先行：数据限本地存储

用户明确要求**数据限本地存储**。这一条直接淘汰所有 SaaS 托管形态
（Portkey 托管仪表盘、Langfuse Cloud）。**只有能自托管的才进入对比。**

### 4.2 对照表

| | 自建（本设计） | Langfuse（自托管） | LiteLLM（自托管） |
|---|---|---|---|
| **定位** | 复用现有仪表盘加面板 | LLM trace / 观测 / 按租户对账 | 网关：路由 + 花费追踪 + 虚拟 key |
| **能直接解决** | 无（要自己埋） | **Q1 Q4**（trace 原生带节点耗时与 token） | **Q1**（按虚拟 key 归因花费） |
| **解决不了** | —— | Q2/Q3 是业务语义，仍要自己算 | Q2/Q3/Q4 同左 |
| **数据出网** | 否 | 否（自托管） | 否（自托管） |
| **许可** | —— | 待核实（核心 OSS，部分企业功能另计） | 待核实 |
| **运维成本** | **0 个新服务** | **+1 服务 +1 Postgres/ClickHouse** | +1 服务（进程内网关） |
| **侵入性** | 改 `workflow.py` 埋点 | 需在 LLM 调用点接 SDK | **要把 Ollama 调用改走网关** |

### 4.3 建议：本阶段自建，但**埋点按可迁移的方式做**

理由三条：

1. **它们解决的是"埋点"，不是"面板"。** 接了 Langfuse 仍然要自己回答
   "Q3 空命中怎么定义"——那是本项目的业务语义，没有现成品。
   **接现成 ≠ 需求自动满足。**
2. **运维成本与当前阶段不匹配。** 目标客户 1–3 家（`CLAUDE.md` §1），
   为四个运营指标引入一个带独立数据库的观测服务，比自己加一张表重。
   且 `CLAUDE.md` §4 P1 已记录「无 Dockerfile / CI / 依赖锁定」——
   **这个项目现在没有承载"+1 个有状态服务"的部署能力。**
3. **LiteLLM 的侵入点恰好在最敏感的地方。** 它要求 LLM 调用走网关，
   而本项目正在 `_intent_node` 用 LoRA 微调的 1.5b + 7b 双模型
   （`CLAUDE.md` §2），且 `app.py` 有一整套 Ollama keep-alive 保活逻辑
   （`:491-520`）。**改走网关会同时动到双模型路由和保活，风险面远超收益。**

⚠️ **但要诚实说明这条建议的反面** —— `CLAUDE.md` 的教训正好相反方向：
手写 BM25 踩了三个坑（全量加载 / GIL convoy / 按文档删除恒失败），
**根因都是"用 Python 手写检索引擎"这个选型**，最后还是换了 OpenSearch。
用户记忆里也明确写着「优先选成熟的现成组件而不是自己造轮子」。

**为什么这次判断不同（这是本节最需要用户复核的一点）**：
BM25 那次自建的是**算法引擎**（倒排索引、打分、并发扫描——难点在实现，
且有成熟替代）；这次自建的是**四条 SQL + 一个面板**，难点在**业务语义定义**，
而语义定义没有任何现成品能替你做。
**真正该警惕的是 Q4 的埋点**——那确实是"trace 基础设施"，是 Langfuse 的主场。
所以：

> **建议 Q1/Q2/Q3 自建；Q4 的节点耗时埋点，如果将来要做全链路 trace，
> 就该认真评估 Langfuse，而不是自己长出一套 span 体系。**
> 这也是 §6 的 I-4 建议**先用最小形态、不要自造 trace 模型**的原因。

见 §10 待确认项 O-3。

```
  workflow.py（§6 埋点改动）。
```

## 6. 埋点方案（工作量大头，可排期拆分）

**无论什么形态都绕不过这一节。** 四项改动，按依赖与收益排序：

| # | 改动 | 解决 | 位置 | 规模 | 依赖 |
|---|---|---|---|---|---|

## 9. 后续可选项：自然语言查询（**前提未满足，现在不做**）

**不删掉这条路，但写明前提。**

### 9.1 前提：先有语义层

「在数据库上直接套聊天界面，没有语义层就会失败」。语义层 = 指标定义一次、
集中管理（"token 用量"算哪些行、怎么去重、缺失怎么处理）。

**本项目现在没有语义层。** 但 §7.3 那四个方法**就是语义层的雏形** ——
它们把口径固化成了代码。所以路径是：

```
面板（口径固化进 4 个方法）→ 埋点补齐（§6）→ 口径稳定 →
才谈得上在其之上加自然语言层（让 LLM 选 metric，而不是让 LLM 写 SQL）
```

⚠️ **就算将来做，也不该做 text-to-SQL**，而应是「LLM 从受控枚举里选一个
metric + window」—— 本质是给已有面板加一个自然语言入口，
**quiet failure 的面积小得多**（模型选错指标是可见的，写错 SQL 是不可见的）。

### 9.2 若将来做 NL 才适用的分析（v1 的内容，移到这里存档）

**以下全部标注「若将来做 NL 才适用」，当前形态不涉及**：

- **工具层权限闸门**：闸门必须在 handler 第一行、任何 SQL 之前，
  复用 `OrgStore.is_platform_admin`。身份只能来自 `subgraph.py:270-274` 的
  服务端注入（`args["user_id"]` 覆盖 LLM 编造值，且 `user_id` 从不出现在
  暴露给 LLM 的 schema 里），state 里的 `user_id` 来自 `app.py:2666/:2717`
  的 JWT 身份。
  🔴 **不能依赖话术检测** —— `CLAUDE.md` §4 第 5c 条实测：软性越权话术能让模型
  口头答应（"好的，我将帮助您导出所有部门的知识库内容"），**最后是 ACL 兜住的**。
  设计必须接受"模型可以答应"，但工具层查不到。
- **路由稀释风险（原 T-6）**：`workflow.py:657` 的
  `available_tools = self._tool_registry.to_openai_tools()` **不按用户过滤**，
  新工具 schema 会进入**每个用户**的意图分类提示词。
  `CLAUDE.md` §4 P1 已记录 1.5b router 训练样本仅 91 条、`tool` 占 68%、
  "拿不准就判 tool"，且 `intent.py:411` 里 `query_knowledge_hub` 已经吃了
  "查询"这个通用词。**再加一个含"查询/统计/数据"的工具很可能加剧误判**，
  必须有路由回归对照组，且**基线要在加工具之前先跑**。

**改成仪表盘后，以上两条风险全部消失** —— 端点鉴权是确定性的，
且不往意图分类提示词里加任何东西。**这是换形态顺带拿到的收益。**
