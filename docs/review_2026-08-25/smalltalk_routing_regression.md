## 1. 执行摘要

**根因一句话**：`qwen2.5-1.5b-router` 的 LoRA 训练集里**一条闲聊样本都没有**（91 条样本
全是业务问答/工作流，`tool` 占 68%），它面对"你是谁"这类问题会按训练出来的先验判成
`intent_type="tool"` + `target_tool="query_knowledge_hub"`，主图随后被 `_generate_node`
的知识库空命中短路（`workflow.py:1294-1314`）截住，返回固定拒绝话术、**完全不调用 LLM**。

四条必须分开说的结论：

1. **不是规则短路造成的，是模型本身判错的**（任务 A，**已验证通过**）。基准里那句
   "你好，你是谁"没被任何规则拦下，`_reconcile_intent_result` 也没改写它——**原始 LLM
   输出**就是 `{"intent_type":"tool","target_tool":"query_knowledge_hub","confidence":0.9,
   "reasoning":"单一主题，无需重写/拆分，询问用户姓名，应查企业知识库。"}`。
2. **误判范围远大于"一句话中招"**（任务 B，**已验证通过**）。21 条闲聊 × 2 次 = 42 次运行，
   当前线上配置下**误判 34 次（81.0%）**，只有 8 次（19.0%）能拿到真回答。而且失败分两种：
   撞知识库拒绝话术 23.8%、被固定澄清话术短路 **57.1%**——后者比用户报告的那种还多一倍多，
   同样是"说了句你好，系统让你补充产品名"。
3. **"告诉用户知识库里没有你是谁"这个具体症状，确实是换 1.5b 模型引入的；但"闲聊路由错"
   本身一直存在**（任务 C，**已验证通过**）。做了 2×2 对照（模型 × 链路），
   `kb_refusal` 只在 1.5b 下出现（24% / 33%），7b 在两条链路下都是 **0%**；但 7b 在
   08-23 旧链路下闲聊误判率仍有 **42.9%**（错法是澄清话术）。
   **这不是"从对变错"，是"错法变得更有害"**。
4. **对照组零误判**：4 组配置下，"该查知识库/该查考勤"的 8 次运行**全部判对**。
   **这个回归只伤闲聊，不伤业务问答**——所以性能基准和那 23 条业务基准用例都没能发现它
   （`docs/optimization_tracking.md:79-81` 记的"23 条基准用例 100% 准确率"，
   核对训练/验证集后确认其中**没有任何闲聊样本**）。

## 2. 任务 A：根因定位

### 2.1 完整链路（每一步都有行号）

```
用户: 你好，你是谁
  │
  ├─ _intent_node (workflow.py:570) → analyze_and_route (intent.py:589)
  │    ├─ Step 1.5 规则短路 _match_workflow_action_intent (intent.py:620)  → 未命中
  │    ├─ 一次结构化 LLM 调用（qwen2.5-1.5b-router）
  │    │    原始输出: intent_type=tool, target_tool=query_knowledge_hub, confidence=0.9
  │    ├─ Step 1 后置安全网 _needs_clarify_rule (intent.py:681)             → 未命中（6 字 ≥ 4）
  │    └─ _reconcile_intent_result (intent.py:685)                         → 原样透传，未改写
  │
  ├─ _route_after_intent (workflow.py:335-339): intent_type=="tool" → "tool_subgraph"
  │
  ├─ tool_subgraph 查企业知识库 → 当然零命中
  │
  └─ _generate_node 空命中短路 (workflow.py:1294-1314)
       条件: state["target_tool"] == "query_knowledge_hub" 且本轮无任何 collections 命中
       结果: 直接返回 _KB_EMPTY_HIT_MESSAGE (workflow.py:67-70)
             used_model = "n/a (empty kb hit, no LLM call)"
```

**订正任务书里的一处描述**：`generate` 节点其实**执行了**，只是在
`workflow.py:1294` 这道闸门处提前 return、没走到 LLM 调用（所以 benchmark 里
`generate` 阶段耗时 0.0s）。真正"从未执行"的是 prompt 构建和 LLM 生成
（`workflow.py:1316` 往后）。这个区别对修复方向有影响，见 §5 方案 D。

### 2.2 四个候选根因逐个排除

脚本用一个 spy 包住 `_reconcile_intent_result`，抓取**后处理之前**的原始结构化输出，
所以"模型判错"和"代码改写"可以直接分开看（脚本里的 `LLM原始` / `终判` 两列）。

| 候选 | 判定 | 证据 |
|---|---|---|
| 规则短路先把它拦成 `tool` | ❌ **排除** | 能把结果拦成 `tool` 的只有 `_detect_intent_rule_based`（`intent.py:703`），它仅在 `llm=None` 时才执行；线上有 LLM，根本不走。脚本里这条用例的 `规则短路` 列是 `-` |
| **1.5b router 模型判错** | ✅ **确认** | 10/10 次 `kb_refusal` 运行的原始 LLM 输出都是 `(tool, query_knowledge_hub)`，reasoning 直白写着"询问用户姓名，应查企业知识库" |
| `available_tools` 非空导致默认分支倾向 `tool` | ❌ **排除（不是代码默认值）** | 代码里没有"有工具就默认 tool"的分支；置信度 <0.5 的兜底反而是回退 `rag`（`intent.py:523-529`）。工具清单确实进了 prompt（`intent.py:657-658`）从而影响模型判断，但那属于"模型判断"，不是代码默认分支 |
| fallback 路径（合并调用失败退回两次调用） | ❌ **排除** | 4 组配置共 200 次运行，`[Intent] Merged analyze_and_route failed` 一次都没出现，异常计数全为 0 |
| `_reconcile_intent_result` 后处理改写 | ❌ **排除（对本条）** | 当前线上配置 42 次闲聊运行里只有 2 次发生改写，且都是"在吗，有点事想请教你"被工作流疑问句守卫（`intent.py:482-485`）从 `workflow` 降级成 `tool`，跟本条无关 |

### 2.3 一个结构性问题：四分类里**根本没有"闲聊"这一类**

`_INTENT_CLASSIFY_RULES`（`intent.py:428-439`）只有 `clarify` / `rag` / `tool` / `workflow`
四个桶，**没有任何一个桶的语义是"直接对话回答"**。所以即使模型"判对"，它能给出的最好答案
也只是 `rag`——而 `rag` 走 `_retrieve_node`（`workflow.py:1066`）只搜
`conv_{conversation_id}`（本次对话上传的附件），查到 0 条后 generate 正常调 LLM 生成回答。

**这条"歪打正着"的路径正是 2026-08-23 那 73 字正常回答的来源**，而且还不是走的 `rag`：
实测 7b 在旧链路下对"你好，你是谁"输出的是
`intent_type="clarify"` **但 `need_clarify=False`**（自相矛盾），
`_route_after_intent` 的 clarify 分支（`workflow.py:340-355`）把这种自相矛盾结果
交给 tool_subgraph，而主图 `target_tool` 为空 → 不触发空命中闸门 → generate 正常生成。

> **所以"优化前是对的"这个印象本身就不准确**：08-23 那次拿到正常回答，靠的是
> "分类器输出自相矛盾 → 落进一条兜底分支 → 恰好没踩到闸门"这条链，不是设计上有闲聊分支。

### 3.1 发现的规律

1. **≤3 个字的句子 100% 被规则拦成澄清，跟模型完全无关。**
   `_needs_clarify_rule`（`intent.py:577`）的判据是 `len(rewritten_query.strip()) < 4`。
   "你好"(2) / "在吗"(2) / "谢谢"(2) / "好的"(2) / "再见"(2) / "早上好"(3) / "辛苦了"(3) /
   "你是谁"(3) 八条**在 4 组配置里全部命中**。这是**最大的单一误判来源**（16-18/42），
   而且是纯规则问题——**换任何模型、重训任何 LoRA 都修不掉这一半**。
2. **含"你/你的"+ 能力/属性疑问词的 4~8 字句子，最容易被 1.5b 判成查知识库。**
   "你会什么"(4) / "你能做什么"(5) / "你好，你是谁"(6) / "你是怎么工作的"(7) /
   "你用的是什么模型"(8) —— 全部 `kb_refusal`。模型把"你"当成了"公司的某个待查实体"，
   reasoning 里能直接看到（"询问用户姓名，应查企业知识库"）。
3. **句子越长越安全，但原因不体面。** "介绍一下你自己"(7) / "非常感谢你的帮助"(8) /
   "在吗，有点事想请教你"(10) 在线上配置下判成 `answered`，但看原始输出，
   它们要么是 `tool` 但 `target_tool` 没填（闸门只认 `target_tool`，所以侥幸躲过），
   要么是 `clarify` 但 `need_clarify=False`（落进自相矛盾兜底分支）。
   **没有一条是"分类器判对了"，全是"错得刚好没踩到闸门"。**
4. **"含问号的短句更容易中招"这个假设不成立。** 用例里带疑问语气的
   （"你的回答准确吗""你能帮我查东西吗"）反而多数落进 `clarify` 而非 `kb_refusal`；
   决定终态的是**句长**和**是否被填进 `target_tool`**，跟疑问语气没有观察到的相关性。
5. **结果高度稳定**：4 组配置、25 条用例、各重复 2 次，**没有任何一条出现两次结果不一致**。
   这不是概率性抖动，是确定性误判——好消息是修完容易验证，坏消息是每个用户每次都会踩到。

## 4. 任务 C：是不是换 1.5b 模型引入的

**结论：症状是新的，病根不是。**（**已验证通过**，2×2 对照）

| 问题 | 答案 | 依据 |
|---|---|---|
| "回知识库拒绝话术"是换模型引入的吗？ | ✅ **是** | `kb_refusal` 在 1.5b 两条链路下是 24%/33%，在 7b 两条链路下**都是 0%**（表 3、表 4） |
| 闲聊路由错本身是新引入的吗？ | ❌ **不是** | 08-23 基线配置（7b·两次）闲聊误判率仍有 **42.9%**，只是错法是澄清话术（表 3） |
| 那是微调模型的泛化问题，还是 prompt/规则问题？ | **两者都有，且可切分** | 见下 |

**切分**：42 次闲聊运行的误判可以干净地拆成两块——

- **约 40%（16-18/42）是纯规则问题**：`_needs_clarify_rule` 的 `< 4` 字长度阈值，
  4 组配置下命中数几乎一样（16/18/14/18）。**跟模型完全无关，重训不解决。**
- **剩下的是模型问题，且两个模型的失败模式不同**：
  - **1.5b（微调）**：倾向判 `tool` + `query_knowledge_hub` → 泛化问题。
    核对训练集（`router_lora_data/train.jsonl` 81 条 + `valid.jsonl` 10 条）确认：
    **闲聊样本 0 条**，intent 分布 `tool` 55 / `workflow` 15 / `rag` 6 / `clarify` 5
    ——`tool` 占 68%，模型学到的先验就是"拿不准就判 tool"。
    这与 `docs/optimization_tracking.md:79-81` 记载的"23 条基准用例 100% 准确率"不矛盾：
    那 23 条基准同样没有闲聊样本，**测的和训的是同一个分布**。
  - **7b（通用）**：倾向判 `clarify` → 不是泛化问题，是 prompt 问题
    （四分类里没有"闲聊"桶，模型只能在四个都不合适的选项里挑一个）。
    顺带独立复现了 `workflow.py:616-625` 记的那个已知现象：7b 跑合并 prompt 时
    分类质量明显变差（`clarify` 从 43% 涨到 95%）。

**所以修复方向不是二选一，是三件事都得做**（见 §5）：规则阈值、分类体系、模型训练数据。
