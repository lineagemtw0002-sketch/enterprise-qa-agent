# BYOC 连接器协议规范

> **状态：现状描述（对应代码 2026-08-27）** · 面向要在自己环境里实现连接器的客户
>
> 本文所有字段名、常量、时限都是**从代码里核对的**，不是从设计意图写的。
> 冲突时以代码为准，并请提 issue——文档过期比没有文档更危险。

---

## 0. 先明确边界：平台不做什么

| 平台做 | 平台**不**做 |
|---|---|
| 发出抽象查询（"给我 order-service 最近一小时的错误率"） | 不知道你用的是 Prometheus 还是 Datadog |
| 发出抽象修复指令（"重启 order-service"） | 不知道你用的是 k8s 还是 systemd |
| 存分析结论和依据引用 | **不存任何原始运维数据** |
| 强制审批流程 | **不持有你的任何凭证** |

**连接就是外向的**：连接器主动连平台，平台永远不主动连你的环境。你不需要开放
任何入站端口。

⚠️ **这意味着修复能力完全由你的连接器决定。** 平台发的 `restart_service` 只是
一个意图；怎么重启、重启什么、用什么权限，全在你这边。**不实现连接器，这个
模块就只是个审批台。**

## 1. 握手与令牌

### 1.1 建立连接

```
WSS  /ws/ops/connector/register?connection_id=<连接器ID>&token=<一次性注册码>
```

两个查询参数**都是必需的**。少传一个的表现是 **HTTP 403，而且服务端日志里
连一条连接记录都没有**——排查时很容易误判成"平台没起来"或"token 不对"。
（浏览器/客户端原生 WebSocket 握手阶段带不了自定义 header，所以走查询参数。）

`connection_id` 和一次性注册码由企业管理员在「连接器管理」里生成。

**校验发生在 `accept()` 之前**，不满足直接关闭：

| 关闭码 | 含义 |
|---|---|
| `4404` | 连接器不存在 |
| `4403` | 该企业未开通智能运维模块 |
| `4401` | 注册码无效 / 已用过 / 已过期 |
| `4409` | 冲突（同一连接器重复注册等） |

### 1.2 三层令牌

| 令牌 | 时效 | 用途 | 注意 |
|---|---|---|---|
| **注册码** `register_token` | **10 分钟**，单次使用 | 只用于握手 | 平台只存哈希；用过即废 |
| **会话令牌** `connector_session_token` | **1 小时**（JWT） | 标识本次连接 | 用**从主密钥派生的独立密钥**签名——防止它和用户登录 token 互相冒充 |
| **刷新令牌** `refresh_token` | **30 天**，单次使用即轮换 | 续期 | ⚠️ 见下 |

握手成功后平台回一帧 `registered`，`payload` 里带 `session_token` 和 `refresh_token`。

⚠️ **刷新令牌重放会导致该连接器全部会话被撤销并强制断线。** 用过的
`refresh_token` 再次出现，平台判定为凭证泄露，不是"重试"。**所以务必保证
轮换后立即持久化新的那个**——旧的丢了顶多要重新握手，用错了要重新登记。

### 1.3 心跳

**每 10 秒**发一帧 `heartbeat`。平台在 **30 秒**（3 个周期）无心跳后判定离线。

⚠️ **"在线"是按平台库里的心跳时间算的，而能不能真正查询取决于 WebSocket
握在哪个后端进程手里。** 单后端部署下两者一致；如果你在开发环境同时跑多个
后端实例连同一个库，会出现"显示在线却查不到数据"。

## 2. 帧格式

所有帧统一信封：

```json
{
  "type": "query_request",
  "id": "关联请求与响应的唯一 id",
  "connector_id": "opsconn_xxx",
  "ts": 1787831141.5,
  "payload": { }
}
```

**响应帧必须原样带回请求帧的 `id`。** 平台按 `id` 把响应派发给等待中的调用方，
**对不上的 id 会被静默丢弃**（表现为调用方超时，而不是报错）。

帧类型：`registered` · `heartbeat` · `refresh` · `query_request` · `query_result`
· `exec_request` · `exec_result` · `error`

出错时回 `error` 帧，`payload.detail` 写人能看懂的原因——它会出现在平台的
"数据不可用"提示里给运维人员看。

## 3. 查询（`query_request` → `query_result`）

### 3.1 请求 payload

| 字段 | 说明 |
|---|---|
| `kind` | `metric` / `log` / `alert` / `service_health` |
| `target` | 服务名。**`service_health` 和 `alert` 允许为空**，表示"整个企业范围" |
| `metric` | `kind=metric` 时的指标名，如 `error_rate` |
| `start_ts` / `end_ts` | UNIX 秒 |
| `filters` | 标签过滤，字典 |
| `limit` | 最多返回多少条 |

### 3.2 响应 payload

```json
{"points": [{"ts": 1787831141.0, "value": 0.081, "text": "", "labels": {}}],
 "truncated": false}
```

- 指标：用 `value`
- 日志/告警：原文放 `text`，结构化字段放 `labels`
- **命中 `limit` 时 `truncated` 必须为 `true`**——平台会把这个标志显示给用户，
  谎报"没截断"会让人以为看到的是全部数据

### 3.3 告警要能被合并

平台按"跟上一条的时间差"给告警分组降噪。**同一次故障产生的告警，时间要挨得近、
`labels` 要一致**（尤其 `target`）。散在一小时里的 19 条会被切成 19 个事件——
那不是平台的问题，是数据形态问题。

建议 `labels` 至少带：`target` · `severity` · `env` · `cluster` · `rule`。

## 4. `service_health`：你要回答的最难的一个问题

这个查询问的是"**你那边有哪些服务、它们现在怎么样**"。

### 4.1 格式

**每个服务回若干个数据点**，靠 `labels.service` + `labels.metric` 区分：

```json
{"points": [
  {"ts": ..., "value": 0.081, "labels": {"service": "order-service", "metric": "error_rate"}},
  {"ts": ..., "value": 2400,  "labels": {"service": "order-service", "metric": "p95_latency_ms"}},
  {"ts": ..., "value": 6,     "labels": {"service": "order-service", "metric": "instances"}},
  {"ts": ..., "value": 1,     "labels": {"service": "search-index",  "metric": "discovered"}}
]}
```

认得的 `metric` 取值：

| 值 | 含义 |
|---|---|
| `error_rate` | 错误率，**比例不是百分比**（0.081 = 8.1%） |
| `p95_latency_ms` | HTTP P95 延迟，毫秒 |
| `queue_latency_ms` | 队列/消费延迟，毫秒。**跟 HTTP 延迟分开判**，阈值宽一个数量级 |
| `instances` | 当前实例数。⚠️ 见 §4.3 |
| `discovered` | 只表示"这个服务存在"，不带指标值 |

没有 `labels.service` 的点会被**跳过，不猜**。

### 4.2 「哪些算关键业务服务」由你决定，平台不管

一台机器上有几百个进程（systemd、sshd、内核线程…），**平台没有任何配置项让
企业声明"我只关心这 20 个"**——它完全信任连接器回什么就是什么。

⚠️ **这是当前设计的一个已知取舍**：平台自己不维护服务清单（手工清单必然腐烂，
新服务上线没人补就永远看不到），代价是**判断口径全落在你这边**。

推荐口径，按优先级：

1. **照抄你已有监控系统的 scrape/service 配置** —— 你既然已经在用
   Prometheus/Datadog，那套配置里已经回答过"哪些要监控"这个问题了
   （Prometheus：`label_values(up, job)`；Datadog：Service Catalog）
2. **k8s 环境用编排对象** —— Deployment / StatefulSet 就是服务单位，
   系统进程根本不在这一层
3. **声明式清单** —— 每个仓库放一份 catalog 文件（Backstage 那套）

**不推荐**：按进程名正则筛。跑起来第一天就对，第二周就开始漏。

### 4.3 `instances` 会被用来限制扩容上限，**要如实上报**

扩缩容的越界判定是：`目标实例数 ≤ 你上报的 instances × 管理员配置的倍数`。

⚠️ **平台不采信 AI 提议里自报的基线**——那是"被约束方自己填自己的约束"。
基线**只认这里上报的实测值**。

⚠️ **不上报 `instances` 的后果是扩缩容一律被拒**，不是"放行"。测不到就不放行
是刻意的默认：回退到自报值等于让这个防护在最需要它的时候失效。

## 5. 执行（`exec_request` → `exec_result`）

### 5.1 请求 payload

```json
{"action_id": "remact_xxx",
 "plan": {"action_type": "restart_service", "target": "order-service"}}
```

V1 支持四类 `action_type`（**平台硬编码，当前不可扩展**）：

| 类型 | `plan` 里的字段 |
|---|---|
| `restart_service` | `target` |
| `scale_instances` | `target` · `target_instances` |
| `clean_disk` | `target` · `path` |
| `rollback_deployment` | `target` · `target_version_offset`（1 = 回上一个版本） |

### 5.2 响应 payload

```json
{"succeeded": true, "detail": "order-service 已重启，新进程 PID 48127，健康检查通过"}
```

**`detail` 会原样显示给运维人员**（失败时显示为红色原因）。写清楚实际发生了
什么——"已重启"和"重启了但健康检查没过"对下一步决策完全不同。

### 5.3 连接器**不需要**自己校验审批状态

审批是平台强制的：动作必须走到 `approved` 才会有 `exec_request` 发过来，
且平台在下发前会**重新校验一次白名单**（提议到执行之间可能隔 30 分钟，
管理员完全可能把目标摘掉了）。

连接器再查一遍是纵深防御的候选项，**V1 刻意不做**——做了反而会掩盖"平台侧
这道闸如果漏了会怎样"。

## 6. 平台侧的错误码

调用失败时平台内部用这几个码，会以"数据不可用"的形式显示给用户：

`ERROR_OFFLINE`（连接器不在线）· `ERROR_TIMEOUT`（超时未响应）·
`ERROR_UNAUTHORIZED`（跨企业访问，**请求根本不会发出**）·
`ERROR_UPSTREAM`（连接器回了 error 帧）· `ERROR_TRANSPORT`（传输层故障）

⚠️ **它是演示件不是产品交付件**，刻意不做这些真实连接器必须做的事：

## 8. 已知缺口（如实列出）

1. **动作类型不可扩展** —— 四类硬编码在平台侧。客户特有的修复动作
   （"重跑数据同步任务"之类）目前加不进来。
   业界（AWS SSM / Rundeck / ServiceNow）的做法是**动作由客户注册、平台只约束
   "谁能在什么范围内做"**，不枚举能做哪些。改成那样是设计变更，未实施。
2. **平台不知道你出事了** —— 现在只有"平台问、连接器答"，连接器**不能主动
   说话**。所以异常可以躺很久没人发现——平台只在有人点分析时才去查。
   补法见 `docs/alert_push_design.md`（新增 `alert_push` 帧，未实施）。

   ⚠️ **那份设计对连接器有一条明确期望，现在就可以照着准备**：
   **推送告警前请先按你们自己告警系统的规则去抖**（Prometheus 的 `for: 5m`
   之类）。进程反复重启时如果把每次状态转换都原样推过来，平台侧只能被动
   兜底抑制，效果远不如在源头按规则压掉。
3. **服务清单口径无指导** —— §4.2 那个问题平台不给任何配置项，
   本文的"推荐口径"是建议不是约束
4. **本文档未经真实客户实现验证** —— 目前唯一的实现是演示探针，
   它由写平台的同一批人写，**没有第三方按本文档独立实现过一次**。
   第一个真实客户接入时大概率会暴露本文没说清的地方
